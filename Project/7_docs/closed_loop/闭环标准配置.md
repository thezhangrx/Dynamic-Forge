## 1c. 精度改造（2026-10-21 下午，**已实现待验证**）

起因：静止场景下量了一下重复性——缺口边界 1σ 只有 1.3/1.0 px，但**墙行中心 1σ=8.0 px**（p90 11.9）。
也就是"缺口量得准、墙在第几行不准"，`|Δy|` 全从这来。四条针对性改造：

| # | 改动 | 为什么 | 状态 |
|---|---|---|---|
| 1 | VT 输入 320×240 → **640×480**（`--cam-w/--cam-h`） | 页面宽 640，喂 320 时 1 个页面像素只剩 0.41 输入像素，墙只有 3.3 px 高 | 已实现，单帧 A/B 通过 |
| 2 | 墙行中心改**亮度加权的亚像素质心**（`row_ev` 连续权重） | 硬阈值会让带子上下沿随阈值跳 2–8 行 | 已实现，单帧 A/B：y 424.5→424.0 |
| 3 | **锁相机曝光/白平衡**（`v4l2-ctl`：`exposure_auto=1`、`white_balance_temperature_auto=0`） | 场景有亮灯斑，自动曝光逐帧调增益，墙的辉光厚度跟着变 → 中心漂 | 已写进 `start_cam.sh` |
| 4 | 多帧中位数从 2–4 帧 → **8 帧**，`--tol-vy 7 → 16` | tol-vy 卡 7 而噪声 1σ=8，等于把好帧剔掉、留下有偏样本 | 已实现（参数） |

**已测（40 帧静态画面，640×480 输入，真实相机）：**

| 量 | 改前（320 输入 + 硬阈值） | 改后（640 输入 + 亚像素质心） |
|---|---|---|
| 墙行 `vy` 重复性 1σ | 0.00 / 0.81 px（*640 输入下本来就好*） | **0.10 / 0.11 px** |
| 墙行偏差 `Δy` | +2.50 / +7.96 px | **+1.95 / +6.42 px** |
| 缺口边界 `gl` 1σ | 3.19 / 2.01 px | 1.97 / 2.69 px |

（历史问题：320×240 输入时 `vy` 1σ=8.0 px，因为墙只有 3.3 像素高 —— 这才是当初
`|Δy|` 的来源。改为 640 输入后行重复性直接降到亚像素。）

**闭环实测（acc9，2026-10-21 08:57）**：到达、**碰撞 0**、最小间隙 **+17.43**、
覆盖 **23/24**（漏 wall@1480）、**`|Δy|` 平均 1.4 px（max 2.3）**、VT 12.0 帧/s。
对比上一版 std9：`|Δy|` 3.1（max 14.7）。

另外三项新发现（都影响"看得见"而不只是精度）：
- 查看器必须 `--viewer-fullscreen`：窗口化时 WSLg(RAIL) 下会被别的窗口压住，
  而全屏 + `--content 1280x960` 能**同时**满足"不被压住"和"页面还落在相机调好的那块矩形上"（quad 前后差 <0.05 px）。
- 查看器 `--idle-exit` 在开跑前要放大（默认 8 s 会在"相机闸门"期间自己退出）。
- "相机闸门"期间必须持续 `publish()` 页面帧，否则查看器是黑屏、闸门必然失败。

注：quad 已按新分辨率重推（`inputs 1×`，四角 `73.0 37.7 558.7 23.0 599.2 396.5 64.7 424.2`），
**y 标定需要在新输入下重跑**（自动标定会在每轮结束时重算）。

## 1d. 2026-10-21 晚：y 二次模型试过，**回退**

**动机**：整轮数据里 16 行墙的 y 残差随 vy 呈弧形（679 应是 640、836 应是 780、
1578 应是 1620），线性模型残差 9.2 px（max 40）。板子的世界模型因此出现"错位的墙"，
规划器以为走廊被堵死 → `act=0` 停住不动（demo3/demo4/demo5 卡死都是这个）。

**做法**：`calib_y.fit_quad()` 拟合 `world = (py-half) + a + b·vy + c·vy²`，
`board_agent.vt_world_y()` 增加二次项（`q_c`）。

**结果（必须回退）**：用 demo3 的整轮数据拟合，残差确实降到 **q_rmse 1.2 px**，
但同一批数据重跑闭环 —— `demo6`：**200 s 未到达、4 次盲穿、min_clearance −10**。
原因：**拟合并不能修复几何**。demo3 那些"错位行"本身就是线性模型下量错的，
拿它们去拟合二次项等于把误差拟合进模型；同时 `x_bias` 也从 1.94 跳到 8.09，
把横向对准一起带偏了。

**结论**：y 仍用**静态标定**（40 帧固定画面 + 真值，rmse 0.17）的线性模型：
`scale 0.97095 / bias 6.111 / x_bias_a 1.943 / x_bias_b 0.04143`。
要真正消掉"行位置的弧形残差"，得按第 3 步用 **ArUco 亚像素角点 + 一阶畸变**从
几何上修，而不是在标定系数上补。

（`q_c` 参数保留，默认 0；以后有了干净的畸变模型再启用。）

## 2. 链路（谁在做什么）

```
板子 /dev/video0 ──ffmpeg（640x480 → fps=12 → 320x240 rgb24）──> 板端 vt_sparse
      └─ 同时写 /tmp/cam.jpg（只给主机取快照，不进决策）
板端 vt_sparse → /tmp/vt.jsonl（每帧：walls[{y,gl,gr}]、player、n、fast）
板端 board_agent ──读 vt.jsonl + 收 @POSE──> 暂停采样/一致性 → 写 @STATE 给 field_cli_board
板端 field_cli_board（Dijkstra 代价场）──> @MOVE <act> ──> 主机
主机 platform_host：推进虚拟平台 + pygame 渲染页面 + 回 @POSE（只此 4 个数）
```

### 板子独立完成的部分

- **取像**：板子自己的 `/dev/video0`
- **视觉**：板端 `vt_sparse` 找墙行、量缺口、找角色（`board_vt.jsonl` 里 `"fast":1,"no_gap":n`
  这组字段只有稀疏版会写，可用来确认跑的是新 VT）
- **决策**：板端 `field_cli_board`，障碍只来自**它自己学到的墙**
- **动作**：板端输出 `@MOVE`，主机只负责执行

主机**不**发墙、不发缺口、不发图像；`--vt-feed`（PC 渲染帧 → 板端 VT）已彻底删除。

### 板子依赖主机的部分（如实记录，用户已确认接受）

1. **`@POSE <seq> <x> <y> <r>`**：平台真实位姿。板子用它把"帧内 vy"换算成场地 y、并知道自己在哪。
   没有它，墙的位置落不到世界坐标。这是执行器反馈，不是墙图，但它是真值。
2. **y 换算系数**：`data/fpga/calib_y.json` 里的 `scale/bias` 是主机用 `configs` 的
   `walls_y` 对板端 VT 行做鲁棒最小二乘拟合出来的**一次性标定**（相机/窗口动了才重算）。
3. **页面四角 `quad`**：主机用相机里的 ArUco 标记算出、下发 8 个数字（纯几何，不含图像/真值）。
4. 场地本身是主机 pygame 渲染、相机拍摄——这是用户定的"主机提供平台场地"。

```sh
ffmpeg -hide_banner -loglevel error \
    -fflags nobuffer -flags low_delay -probesize 32 -analyzeduration 0 \
    -f v4l2 -input_format mjpeg -video_size 640x480 -i /dev/video0 \
    -filter_complex "fps=12,scale=320:240,split=2[a][b]" \
    -map "[a]" -f rawvideo -pix_fmt rgb24 - \
    -map "[b]" -update 1 -q:v 5 -y /tmp/cam.jpg \
  | /root/tools/vt_sparse --w 320 --h 240 --frame-roi 0 0 320 240 \
        --quad-file /tmp/quad.json --quad-state /tmp/qb.txt \
        --jsonl /tmp/vt.jsonl > /dev/null
```

低延迟三件套（`-fflags nobuffer -flags low_delay -probesize 32 -analyzeduration 0`）
是必需的：没有它，VT 帧比真实位姿落后 ~2 s，暂停采样法就失效。
`> /dev/null` 也必需：VT 每帧往 stdout 写 921 KB，漏出去一轮能灌 771 MB 日志。

## 5. 已知坏点 / 别开的东西

1. **`board_agent --collect-moving`**：机制已修好（能学到墙），但实测**不如停车法**：
   `std4` 覆盖率 11/24、|Δy| 6.0，同一套修复下的停车法是 24/24、2.7。**标准配置不启用**。
   历史：`sparse7`（`run_20261020_225152_sparse7`）的 `reached=True` 是 90 Hz `resume`
   空转导致的假到达（穿了 24 道墙），**永久作废**。
2. **残留渲染窗口**：`platform_host` 若带 `--hold` 留在后台，冻结页面会一直挂在屏幕最前面，
   相机就拍那张冻结图（历史上就这么被问题过一次）。跑之前 `--check` 会报进程数；现在
   `platform_host` 已支持 SIGTERM/SIGINT 协作退出，`kill -TERM <pid>` 就能收干净。
3. **`vt_board`（旧稠密 VT）不再作为标准**：同一批真实帧上它 405 ms/帧、4 道墙里 2 道是页面白框幻影，
   y 误差 −15…+22 px；新 `vt_sparse` 11.5 ms/帧、2 道墙全真、y 误差 +3.5/+7.5 px。
4. **动作间隙 16 px（`--gap-margin`）** 是刻意的保守收缩：板端缺口宽度因此比真值窄 ~21 px，
   换来的是穿越时有余量；不要为了"看起来准"把它调小。

## 5b. 斥力（公式 5.5 的 U_rep）进 M1 的代价场（2026-10-23）

口径：**加在决策的代价场里，不新增控制层**。实现在 `core/board/field_m1.hpp`：

```
U_rep(p) = ½·η·(1/d − 1/rr)²        仅 d < rr
F(p)     = travel_到目标(p) + w_rep · rr² · U_rep(p)
```

`d` = 格中心到**未膨胀**墙矩形表面的距离（chamfer 用膨胀网格，斥力用几何精算）；
travel 仍是波前测地距离（会绕缺口）；`w_rep` 的单位是"等效场地距离"。
`--repel-weight 0` 时**逐位等于旧行为**（默认 0，现有测试不受影响）。

本机实测（`field_loop.py --board local`，120 Hz 锁定步长，场景 `20_walls_alt_24_dy140_y120`，
60 s 上限，`speed 2`）：

| w_rep | 到达 | 用时 | 碰撞 | 最小间隙 | 动作切换 |
|---|---|---|---|---|---|
| 0（旧行为） | ✅ | 20.0 s | 0 | **1.40** | 54 |
| 2 | ✅ | 22.2 s | 0 | 11.76 | 155 |
| 3 | ✅ | 23.1 s | 0 | 14.55 | 119 |
| **4（标准）** | ✅ | **23.3 s** | **0** | **17.54** | 118 |
| 6 | ❌ 卡住 | 60 s | 0 | 22.19 | 641 |

结论：**w_rep=4**（间隙 1.4→17.5，代价 +3.3 s、切换 54→118）；6 会卡住（APF 局部极小，
正如 `势函数方案.md` 记的那条代价）。板端 `board_agent.py` 默认就传
`--repel-weight 4 --repel-range 120`，可用 `--repel-weight 0` 做 A/B。
板上二进制已按仓库源码重编（`field_decision_cli` 与 `field_cli_board` 同一份，md5 相同）。

## 5c. 新旧融合：虚拟真值 + `@STEP` 步数位姿（2026-10-23）

口径：**老的好东西直接用，只做衔接**（用户要求，见 `core/using/README.md` §3b）。

| 环节 | 用的是哪份 | 说明 |
|---|---|---|
| 板端位姿 | `core/board/virt_truth.hpp::PlayerState` | 8 帧锁初值 / 行为门 / 残差门 / 连续 5 帧重锚，全部照搬 |
| 位姿推进 | 新增 `board_world.World.on_step(steps, act)` | 用主机回的**已执行步数**（`t_sim` 精确计数）而不是 `板秒×156.6`；实测与主机真值差 ≤0.04 单位 |
| 墙表 | `virt_truth.hpp::WallQueue` | 相对量契约（`rel = 视觉−视觉角色`，再 `+ 虚拟角色`）+ 4 帧稳定冻结 + cap4，**冻结后视觉不再刷新** |
| 墙 y 换算 | `World.rel_to_world_y()` | `(py−half)+scale·vy+bias` 的**逐值等价**写法，`py` 换成虚拟真值角色位姿 ⇒ 链路延时/画面滞后不再进 y |
| 决策 | `field_m1.hpp` | 斥力见 §5b |
| 通信 | `@STEP <步数> <act>`（主→板） | `@ACK <ver> <act>` 保持原义（板→主，`field_decision_cli --echo`） |

**这一版还没在平台上跑整轮**（2026-10-23 用户要求本轮不启动平台），只做了接口级
验证：位姿步进逐位一致、墙 4 帧冻结/冻结后不被刷新、相对量契约抵消公共 y 偏移、
`py_compile` / `g++ -Wall` 全绿。所以 §1 里 std7/std9/acc9 的数字仍是**老口径**
的证据，新口径的数字要等下一轮平台跑出来。

## 6. 变更纪律

改任何一项（fps、settle、margin、VT 算法、标定方式）都必须：

1. 先跑一轮留 `run_*/` 证据；
2. 改完再跑一轮，用 `check_run_logs.py` 的数字对比（到达/碰撞/覆盖率/\|Δy\|/VT 帧率）；
3. 没有数字改善就回退；改善了就把本文和 `loop_standard.sh` 一起更新。

## 5d. 拍摄延迟 Δ 的在线估计（方案 A，2026-10-23 夜）

**为什么要**：画面里那道墙对应的是**过去**某一刻的位姿。不补偿，整帧的 y 会被
平移 `v·Δ`（v≈200 px/s，Δ≈0.3 s ⇒ 60 px ≈ 半行墙距），缺口就会配到隔壁那行 ——
fuse6/fuse7 都到达、24/24、但都在 row 960 各吃一次 −10，形状与此一致。

**怎么估**（`board_world.bootstrap_delta`，不依赖任何冻结墙，与冻结同一个 Δ̂）：
墙在世界系静止 ⇒ 同一道墙在相邻帧串成链后 `y(Δ) = pose_at(t−Δ) + S·vy + B`
对整条链必须恒定，扫 Δ 取“链内 y 极差中位最小”。

### 实测（`smoke_agent.py --inject-lag`，本机，信息丰富的起停日程 `--cycles 10`）

| 注入 L | Δ̂ | 误差 | 残差(px) | 备注 |
|---|---|---|---|---|
| 0.0 | −0.04 | −0.04 | 1.29 | 零点，平台 [−0.06,−0.02] |
| 0.2 | 0.10 | −0.10 | 1.51 | 平台宽 ~0.14 |
| 0.4 | 0.29 | −0.11 | 1.08 | 平台 [0.26,0.32] |
| 0.6 | 0.45 | −0.15 | 2.39 | 平台 [0.42,0.48] |

拟合 **Δ̂ ≈ 0.82·L − 0.03**：单调、零点准、残差只相当 6~12 ms 的运动量，但
**系统性少报约 18%**。所以冒烟判据写成“零点 + 实测斜率带 `0.06+0.25L`”，
不再声称 ±0.05（±0.05 在这套数据上过不去，如实记录）。

### 走过的弯路（不再走）

1. **匀速段对 Δ 零信息**：匀速时 `y(Δ)=W+v(L−Δ)` 与 Δ 无关，信息只在**起停**处。
   以前冒烟日程只有 2 个起停，估计器只拿到 2 条链、曲线是一整帧宽平台、argmin
   在平台边缘乱跳 —— 那是**注入信息不够**，不是算法错。真机一轮 gap_measure 起停
   17 次，所以改成周期性起停日程。
2. **链内静止帧要剔掉**：不剔，链内极差被“动帧占比”稀释，实测斜率 0.65 ≈ 日程
   动帧占比 9/15——看着像“只估出 65%”。
3. **位姿样本必须在收到 `@STEP` 时打戳**：以前在主线里用 `now_m` 打戳，等于把
   agent 自己的处理延迟算进时间轴，实测恒定 ~0.12 s。这是真 bug（生产里同样有害）。
4. 注入的**画面内容必须是连续位姿**（`steps_cont`）：注入用取整台阶、估计器用线性
   插值，两者永远对不齐（残差下限卡在半个台阶 ≈8 px）。

### 生产口径

- `board_agent` 在 `Δ̂>0` 时用 `py_at(t−Δ̂)` 做映射与冻结（同一把尺子）。
- 由于少报 18%，补偿会略微不足（Δ=0.3 时剩 ~10 px ≈ 行距的 7%），仍远好于不补。
- 诊断开关：`--delta-scan-lo -0.4` 可让 Δ 取负，用来判断“是否存在常数参考偏置”
  （默认 0，生产别开）。

## 5e. L1（把测量闸门从"画面静止"改成"位姿静止≥Δ̂+pad"）——**试过，否掉，已回退**（2026-10-23 夜）

起因：`run_20261023_174738_delta1` 撞在 row 1660 之前，板子在地图里**缺 1520/1660/1800
三行**、`known` 卡在 10 长达 100 s、那段停占比 97%（27/28 次恢复是 `timeout`），
实际速度 6.9 单位/s（名义 200 的 3.4%）。

当时的假设：闸门的 `settled`（画面停止变化 ≥ content_hold=0.8 s）是脆弱代理 ——
静止帧对里"墙数变化"占 10%、">2 px 抖动"占 5%，平均 0.6 s 就重置计时器，所以
`settled` 几乎永不成立。

**离线投影（用这一轮的真实记录算新判据，不开相机）结果：卡死区 106 s 的 27 次暂停，
新判据每个窗口放行 0 帧。** 由此否掉 L1，并改判根因：

1. 该区 `landmark=True` 只占 **3%**，`|implied_py − py_cap|` 中位 **276 单位**
   （`fresh_tol=8`）—— 绑定的是**地标检验**，不是 `settled`（`settled=True` 还有 34%）。
2. **不是屏幕冻结**（2026-10-23 夜用 `cam_rec.mkv` 反证）：录像帧里页面、墙、角色都在，
   画面是活的；页面内相邻帧差中位 **19.8（0~255 灰度）** 而整段没有任何"几乎不动"的区间
   —— 那个差值是**传感器噪点**（画面本身噪点很重），不是内容变化。主机 `render.jsonl`
   也 **7953 条、无 >1 s 空档**。⇒ 渲染、采集、相机三层都正常。
3. **真正的元凶是"排序条件"这句判据本身**：`settled` 要求"画面最后一次变化不早于位姿
   最后一次变化"。可是**机器人停稳、画面也已经正确的时候，画面本来就不会再变** ——
   于是 `since_content` 永远小于 `since_pose`，判据把"已经正确"读成"还没追上来"。
   量化：2705 条 reject 里，**203 条**两项时长都够、**只因排序条件**被否决；在
   "地标已判画面=当前位姿"的 632 帧里，**234 帧（37%）** 是被这一条杀掉的。
   停顿越稳、VT 读数越干净，这个判据越会拒 —— 正好反了。
4. 次要但同样致命：`--landmark-win` 默认 **400 px ≈ 384 单位 ≈ 2.7 行**（行距 140），
   远大于 docstring 自己写的 150。地图一出现多行空洞，观测就会配到 2~3 行之外：
   卡死区 1216 条 reject 全由这种配对产生（`|vy−vp|` 中位 288 px，配对行距当前位姿
   中位 380 单位），自检于是给出"画面不对"而不是"我不知道"，空洞永远填不上。
5. **两处必须一起修**（离线投影，同一轮真实记录）：该段可测帧 0.14 → 只收窗口 1.42 →
   窗口 150 + 位姿静止≥Δ̂+pad 判据 **3.21 帧/s**，且**第一次暂停**即放行 35 帧
   （够 consensus=4）⇒ 1520/1660/1800 三行本可以在撞之前就入表。
   只做 L1 不改窗口 = 0 帧（这就是 L1 被单独否掉的原因：必要但不充分）。

## 5f. G1（主机给最小绝对位置，像 GPS）——**第一条实现方式被数据否掉**（2026-10-23 夜）

用户口径：可以给角色当前的绝对位置，但要给得极少，类似 GPS。据此实现：

- 主机 `platform_host.py`：`@GPS <idx> <y>`，`--gps-dt 1.0`（≈1 Hz）、
  `--gps-quant 20`（取整到 20 场地单位），值 = **刚交给屏幕那一帧的仿真位姿**；
  不含速度/朝向，**不含任何墙信息**。
- 板端 `board_agent.py`：解析 `@GPS` → `board_world.gps_delta()` 用
  **速度加权最小二乘**拟合 `y_gps ≈ py_at(t−Δ)`（静止样本权重 0）。

**实测否掉的点**：拟合稳定给出 **Δ≈0**，三个注入值（L=0/0.2/0.4）都是 0.00。
原因不是算法，而是**信息通路错位**：

```
GPS   : 主机 → TCP → 板端            延迟 ≈ 0（毫秒级）
画面  : 主机 → MJPEG → page_view 呈现 → 相机 → VT → 板端   延迟 0.16~0.19 s（正常）/ 2.76 s（卡顿时）
```

用 GPS 和板子自己的位姿对齐，量到的是**前者**，与画面无关。所以它既不能
替代 Δ̂，也不能识别"这张图是哪一刻"。合成数据里我给 GPS 真加了滞后才得到
0.32（且 1 Hz + 频繁起停时只有 ~6 个有效样本，精度很差）。

**保留的东西**（可回退、默认关闭）：`--gps-dt/--gps-quant`（主机侧）、
`@GPS` 解析、`gps_delta()`；板端 `--gps-anchor` **默认 0**，旧链路逐位不变
（冒烟复核：Δ̂=0.29、墙冻结正常）。

**要让 GPS 真正有用，必须让它带上"呈现时刻"**，两种走法：
1. `page_view` 把 (seq, 呈现时刻) 回传给主机 → 主机发 `@GPS <t_present> <y_q>`
   → 板端对齐主机/板端时钟后按呈现时刻映射（残余只剩相机自身延迟 ~1 帧 ≈3 单位）。
2. 干脆把位姿**印在画面里**（尺子/条码带），板端每帧自己读 —— 与延迟完全无关。

另一条**不依赖 GPS**、且已被离线投影验证的路：地标"配不上就别否决"
（`--landmark-win` 400→150）+ "位姿静止≥Δ̂+pad 才测"，同一轮数据上可测帧
0.14→3.21 帧/s，且第一次暂停就有 35 帧可用（见 §5e）。

### 5f-1. 第一轮 G1 上线 → **回退**（gps1，2026-10-23 夜）

`run_20261023_192850_gps1`：到达 ✅、碰撞 **1**（min −10）、覆盖率 **20/24**、|Δy| 3.4 px，
地图 25 行但只有 11 行的 y 对得上真值（重复入表：2079.7/2081.9；错行：
845.0/1128.5/1715.1…，偏差 18~67 单位）。规划器拿着错缺口去撞 row 680 的墙，
还出现 act 4（−y）12 次、act 1（−x）8 次 —— 用户看到的"往回走、碾压墙"。

**两个原因，都是本次改动引入的**：

1. `--landmark-win` 400→150。本意是"配不上就别否决"，实际效果是**未经验证的帧
   直接进表**（`page_stale` 92%→21%、`resume accepted` 34 次），错行因此混进 known。
   这正是原 docstring 警告过的"配不上就放行"漏洞 —— 我用离线投影只量了**可测帧率**，
   没量**入表精度**，这是我的失误。
2. 用"呈现位姿"做映射，但位姿是拿"呈现时刻 T 之前的最后一次提交"回查的。MJPEG
   有缓冲，回查到的帧比真正画在屏幕上的**新**，位姿偏 20~67 单位（v·缓冲时长）⇒
   同一行以不同 y 重复入表。**"呈现位姿稳定"并不能证明"画面就是那个位姿"**，
   这条前提本身不成立。

**回退**：`--gps-present 0`、`--landmark-win 400`（回到 delta1 时的行为；冒烟复核
Δ̂=0.29 与旧链路逐位一致）。GPS 管线（`@GPS` 发送/解析/`gps_delta`）保留但默认关。

**要继续 G1，必须补的一步**：`page_view` 回传**帧序号**（不只是时刻），主机维护
`seq → 位姿`，板端按序号取位姿 —— 不能用"时刻回查"。另外任何"放行未验证帧"的
改动都必须同时报**入表精度**（`入表行误差`），否则就是把错行写进世界模型。

### 5f-2. G1 第二轮：呈现位姿打通，但**入表精度压不住**（gps4/gps5，2026-10-23 夜）

修掉三个真 bug 后，`@GPS` 终于走的是"屏幕上那一帧"（gps5：`src=present_seq` 占 99%，
`hit=True`；自检日志、动态端口、回退覆盖都已修）。对照：

| 一轮 | 地图行数 | 命中真值(±15) | 重复行 | \|误差\| 中位 | max | `page_stale` | 停占比 | 碰撞 |
|---|---|---|---|---|---|---|---|---|
| base2（基线） | 24 | **24/24** | 0 | **2.0** | 6.8 | 87% | 78% | 1（擦边 9 单位） |
| gps4（20 单位量化） | 34 | 15/24 | 8 | 23.4 | 67.3 | 20% | 72% | 1 |
| gps5（10 单位 + 漂移闸 + 相机延迟 0.2 s） | 36 | 21/24 | **11** | **4.2** | **64.9** | 45% | 72% | 1（**瞄错侧**：x=348.7，真值缺口 200~294） |

**结论（可证伪）**：G1 把可测帧率从 13% 提到 55%，但入表精度与地图卫生**同时变差**，
验收指标（到达/覆盖率/碰撞）**与基线完全一致**（都是 24/24 + 1 次碰撞）。也就是说
按现在这条路，G1 **没有换来任何验收改善**，反而把"擦边"变成了"瞄错侧"。

**为什么压不住**：位姿要除以"这张图有多老"才准，而这个老的程度取决于
**相机链（ffmpeg→VT）的缓冲**，它是**可变**的（正常 0.16~0.19 s，卡顿时 2.7 s），
主机侧的呈现位姿流**观测不到它**。我试了三种近似（时刻回查、相机延迟 0.2 s、
漂移闸 ≤1.5×量化），都只能压平均值、压不住尾部（max 仍 65 单位）。

**要真正解决，只有两条**：
1. **让画面自带标识**（渲染时把帧号/位姿编进画面，板端读出来）——延迟完全不影响映射；
2. **把相机链延迟做成有界且可测**（缓存固定 1 帧 + 板端上报，主机按"呈现时刻"发 GPS）。

标准配置已回退到 base2（`--gps-present 0`、量化/漂移闸参数保留但不启用）；
`@GPS` 管线与 `gps_delta` 保留，供上面第 2 条继续用。

## 5g. 画面自带标识（A 路）——基调（2026-10-23 夜，含实测）

### 三条硬事实（都实测，不是估计）

1. **光学**：相机端 **0.87 相机像素/场地单位**（quad 宽 556px / 640 单位，纵向 0.80）。
2. **噪声**：静止期连续两帧求差 → **σ ≈ 19.5 灰度**；页面亮度 均值 30、p95 110。
   ⇒ **单像素判据不可靠**，任何标识都必须沿长边做像素平均，最小特征 ≥ **8 场地单位 ≈ 7 相机像素**。
3. **没有边带可放尺子**：场地右缘在相机里已经到 x≈578~624（幅面 640）。按 50 单位外推的
   刻度柱直接落到画面外（实验里剖面全是 0~0）。想在场地外立"尺子"，必须先**缩小画面 ~6%**
   （0.87 → 0.82 px/单位，墙从 8px 变 6.5px），这是真实代价。

### 标识怎么选（可读性实验，σ=19.5、真实四边形透视、加模糊）

| 码元尺寸（单位） | 相机像素 | 码带宽度 | 解码成功率（20 次） |
|---|---|---|---|
| **8×10** | 7×9 | 64 单位 | **20/20**（压在墙上也 20/20） |
| 10×14 | 9×12 | 80 单位 | 20/20 |
| 12×18 | 10×16 | 96 单位 | 20/20 |
| 16×20 | 14×17 | 128 单位 | 4~7/20（太宽，透视漂移） |

**关键**：码必须能与墙分离。灰度上墙(p95 110)与亮码分不开（实验里整条带被墙"连成一片"），
改用**颜色分离**（墙暖白 BGR≈200,240,255；码青 BGR≈235,235,60，取 **B−R** 通道）后
**压墙也 20/20**。另外青色码的 `min(R,G,B)=60 < 195`，不会触发视觉链现有的"亮块"判据，
**不会把角色检测挤掉**（这是 `standard/fiducial.py` 里曾遇到的问题）。

### 放在哪：挂在**角色标记**下沿，而不是场地边上的尺子

理由：① 角色永远在视口中心、画在**最后一层**（不会被墙盖住）；② 它就是"需要定姿的那个物体"，
**编码与位姿天然同期**，相机延迟再多也不影响（这是它比 GPS/呈现位姿强的根本点）；
③ 不需要改页面布局与标定（比"缩小画面立尺子"省掉 6% 分辨率）。

- 位置：角色圆心正下方 **+18 单位**，码元高 10 单位（比墙厚 8 更高，便于与墙行区分）。
- 内容：**该帧角色绝对 y**（取整到 20 单位），8 位二进制 + 两端各 6 单位护带（共 76 单位宽）。
- 覆盖范围：8 位 × 20 单位 = 5120 > 场地 3420 ⇒ 无歧义。
- 精度：±10 单位（10 位×10 单位可到 ±5，按需再调）。

### 板端怎么读（"标识计数"→"绝对距离"）

1. 用现有角色检测拿到圆心（原链路不动）；
2. 在圆心下方取 ROI，按 **B−R** 通道做一维剖面（沿 y 平均，压噪声）；
3. 用**两端护带**锚定码带跨度（不能用"最长亮段"，bit=0 会把带切碎——这是实验里踩的问题）；
4. 每码元取中间 50% 求均值 → 位 → 8 位码 → `y_tag = code × 20`；
5. 3 帧多数表决；`y_tag` 一旦可用，**墙/缺口的映射直接用 y_tag，不再用任何位姿推断**。

### 验证顺序（每一步都有数）

1. 渲染器加码带（主机），板端先**只读不用于映射**，日志里同时打 `y_tag` 与自积分位姿；
   两者应恒差 ≤±10（这一轮就能证明"标识读对了"）。
2. 本地用 mock 解码器过真实四边形 + σ=19.5（本基调已做：20/20）。
3. 切映射到 `y_tag`，判据：**入表行 |误差| ≤5 单位、无重复行、覆盖 24/24、碰撞 0**。
4. 有效才同步 `core/using`。

### 5g-1. 第一步已落地：共享契约 + 渲染 + 解码算法（2026-10-23 夜）

- **共享契约** `core/standard/tagstrip.py`（与 `standard/fiducial.py` 同一套路）：
  `GUARD=6 / CELL=9×10 / BITS=9 / STEP=10 / OFFSET_Y=−18 / COLOR_RGB=(60,235,235)`，

3. 解码必须**用角色位置给 ROI**（码元是分开的小块，用"最大连通域"会失败）。
