## 现在已经到哪了（**实测，不是目标**）

**P2 验收已过：RTL 与 C 参考模型在真实录像的 320 帧上逐位一致。**

```
$ cd core/fpga/cosim && make && ./obj_dir/Vvision_top /tmp/stim_color 320
=== 协同仿真结果 ===
比对项 221605083，不符 0，有差异的帧 0
```

每帧比对的内容（`cosim/tb_vision.cpp`）：

| 比什么 | 怎么比 |
|---|---|
| 灰度 / 墙 / 亮 三张掩膜 | 直接读 RTL 内部帧存，逐像素 |
| 行直方图 | 逐行 |
| 行带 y0/y1、场地 x 范围、各类计数 | 调试口 |
| 墙段（障碍）9 个字段 × n、缺口 9 个字段 × n | 调试口 |
| 角色位置/半径/包围盒/面积 | 调试口 |
| **几何帧字节流（含 CRC32）** | 逐字节 |

### PS 面向接口（AXI4-Lite）也走通了

`vision_axi.v` 把 `vision_top` 包成 PS 能直接访问的从机：写阈值 → 写 CTRL 启动
→ 轮询状态 → 读帧长 → 读几何帧窗口。同一条协同仿真链路（`cosim/tb_axi.cpp`）
验证了配置寄存器读写回、CTRL/状态位、窗口字节与 C 参考模型逐字节一致：

```
$ ./obj_dir/Vvision_axi /tmp/stim_color 20
=== AXI 协同仿真结果 ===
比对项 11341，不符 0
```

地址映射见 `vision_axi.v` 头部的表（有契约测试与 tb 的枚举逐项核对）。

### 不接相机也能验：PL 自检图案

相机通路（USB/SDI/MIPI）通常最后才通，但"PL 综合出来的东西到底对不对"
必须能提前回答。`vision_selftest.v` + `vision_tpg.v` 就是干这个的：
生成一个**几何完全已知**的合成场地（墙带 24 行、缺口 60 px、角色圆盘 r=10），
跑完整条流水，把结果从调试口读出来。

```
$ ./obj_dir/Vvision_selftest 8 --verbose
场景 0 (wall_y=60 gap_x=200 player=(300,280)): 184 字节，全部与手算一致
...
=== 自检图案结果 ===
比对项 403，不符 0
```

**这一条比"RTL == C 模型"更硬**：前两个测试台都拿 C 模型当参照，两边一起错是
测不出来的；自检图案把手算的墙带行范围、缺口中心、角色质心直接写进断言，
给 PL 通路一个**独立参照**。板上跑 `auto_run=1`（内部节拍自转，不需要外部激励），
PS 只读调试口。

复现（帧数由环境变量控制，默认只跑 4 帧以保持套件快）：

```bash
# 先导真实帧激励（彩色 PPM —— 灰度会让 R-B 判据恒为 0，墙根本测不出来）
python core/fpga/ref/export_frames.py --video data/vision/run4/screen.mp4 \
    --out /tmp/stim_color --frames 320 --start 200 --stride 2 --width 640 --color
FPGA_COSIM_FRAMES=320 python -m pytest core/fpga/tests/test_cosim.py -q
```

## 设计取舍（与 C 参考模型逐条对应）

* **多遍，不硬凑单遍**：行带要先知道"哪些行墙够多"，场地 x 范围要先知道
  "哪些列墙够多"，墙列判据又在这两者之后。C 参考模型是两遍（先存整帧掩膜、
  再按需回读），RTL 是同一批遍、顺序执行。
  存整帧是**允许**的：PL BRAM 9.3 Mb ≈ 1190 KB，灰度 300 KB + 两张 1 bit
  掩膜 77 KB ≈ 32%（见移植规划 §2.1 的订正）。真正的单遍流式版（只存游程）
  留到需要压时延的时候再做。
* **逐列投影**：C 的列投影是 `for x { for y }`，RTL 照抄列主序。好处是列内的
  Σy 与"持续台阶"各只要**深度为 k 的移位寄存器**（k=2 就是两级），不需要
  640 深的行延迟线。
* **几何量全整数定标**（Q6 = 1/64）：连 `atan2` 都是两边共用的一串整数运算
  （9 点 arctan 表 + 一次除法，见 `vision_ops.vh`）。**逐位一致是构造出来的，
  不是测出来的** —— 只要 C 侧还有一步走 double，最后一位就得靠运气。
* **并查集顺序查找**：链长最坏到标签表深度，组合展开就是 256 级级联比较器；
  顺序走只多花几拍。

## 两个真踩过的坑（写在这里省得再踩）

1. **Verilator：把函数调用直接写进"数组元素"的非阻塞赋值 RHS，可能算错。**
   实测 `obs_words[n*9+8] <= vo_atan2_q6(a, b);`（同一函数在 `$display` 里也调了
   一次）落库的值和打印出来的值不一样，改成先算到一根组合 wire 上再赋就好了。
   现象很隐蔽：**中间量打印全对，只有落库的字节错**。定位方法是"把表达式提成
   wire"，而不是加更多打印。
2. **帧长会多 1 字节**：`dout_vld` 用 `state == S_PACK` 驱动时，`S_PACK → S_DONE`
   那一拍它还挂着，于是多发一个字节。最后一字节必须显式拉低 `dout_vld`。
3. **`dout_last` 每帧拉高了两次**：早先写成"payload 最后一字节 **或** CRC
   最后一字节"。纯字节流看不出（消费方只数 `dout_vld`），但包装层拿它定帧长就
   会算成 4 字节 —— **这个 bug 一直到写 AXI 路径的协同仿真才暴露**，
   `tb_vision` 跑了 320 帧都没发现。现在 `tb_vision` 也加了"每帧恰好一次"的守卫。
   教训：**"最后一字节"标记要么不用，要么就有一条专门测它的用例**。
3. **`seg_limit` 提前 +1 会吐假段**：`seg_push` 只在"段长 ≥ `min_seg_px`"时才
   真的把 `n_segs` 加一，而收尾那拍写成了 `seg_limit <= run_in ? n_segs + 1 : n_segs`。
   于是"最后一段比 `min_seg_px` 还短"时，`seg_limit` 比真实段数大 1，`S_SEG` 去读
   一条**没写过**的 `seg_x0/seg_x1`，吐出一个 `x=[0,0]`、`ln=0` 的假段，`n_obs`
   和帧长都跟着错。**620 帧语料里只有第 216 帧（语料 A）触发**，而且在判据修对
   之前根本没出现。修法是多一拍、用已提交的 `n_segs` 结算。
4. **判据要和 Python 逐项一致，不能只和 C 模型一致**：C 与 RTL 曾一起把
   墙的 G 下限写成 110（Python 是 60）、亮色少了 `max-min < bright_spread`。
   `tb_vision` 全绿 —— 因为两层错得一样。现在有测试钉住三方默认参数一致。

## 唯一不需要仿真器的 RTL 检查

`../tests/test_rtl_contract.py`（13 项）从 `vision_pkg.vh` / `vision_ops.vh` 里
解析宏与角度表，和 `core/standard/vision/vision_frame.py: describe_vision_protocol()`
以及 C 侧的表逐个比对。**HDL 与 Python 一旦漂移，症状是"PS 解出来的字段整体错位"
或"CRC 永远不过"，在板上极难定位**；这个测试让漂移在提交时就报错。
已验证它真能抓到：把 `VISION_Q_DIV` 从 64 改成 32、`VISION_OBSTACLE_BYTES`
从 36 改成 32，立刻挂 2 项。

## 还没做的（诚实清单）

| 项 | 说明 |
|---|---|
| **上板** | 一次都没在 Vivado 里综合过。`vision_ccl.v` 的标签表是 256×~150 bit ≈ 37 kbit，**Vivado 会推 BRAM 还是寄存器阵列需要实测**；`vo_scale_round` / `vo_atan2_q6` 里的 `/` 会被推成除法器；`frame_mem` 的字节写要用带字节使能的 BRAM。资源与时序都要看了才知道。 |
| **AXI 的 CDC** | `vision_axi` 是**单时钟**的，像素输入必须与 `clk` 同步。真实相机的像素时钟与 AXI 时钟不同源，跨时钟域 FIFO 要另加 —— 本模块没假装自己有 CDC。 |
| **AXI 读写不并发** | 从机把读写串行化（对方走完才抬高自己的 ready）。裸机驱动按"写 → 轮询 → 读"访问没问题；接 DMA/多主机要改成真正的双通道。 |
| **帧窗口无缓冲** | 几何帧写在一块 BRAM 里，PS 必须"启动一帧 → 等完成 → 读窗口"。**改成连续采集就会撕裂**（现在靠"一次 frame_start 只跑一帧"保证）。要连续跑就得双缓冲或上 DMA。 |
| **相机前端** | 只有"像素流进"的接口；RGB→灰度在 RTL 内部做，但 Bayer 去马赛克 / YUV 转换没写。阈值已可配，**但还没有自动曝光/白平衡那条自适应链**（Python 侧有，见 docs/vision/adaptive.md）。 |
| **自检图案只覆盖"理想输入"** | TPG 画的是无噪声、无抗锯齿、无光照变化的几何。它证明的是"通路对"，**不能替代真实录像的逐位对账**（那是 `tb_vision` / `tb_axi` 的活儿）。 |
| **`E`(绿) 掩膜** | 三路分类算了 `green`，但下游（墙 + 角色）还没用它 —— 协议里保留着。 |
| **时序/资源报告** | 没跑过 `synth_design` / `report_utilization`，`移植规划 §2.2` 的带宽估算仍是估算。 |
| **帧同步** | `din_sof` 必须由外层给出（相机前端/wrapper 合成）。真实相机通常只有行/场有效，`sof` 要自己拼。 |
| **上限边界没测** | 320 帧语料里标签表最多用 3 项、障碍最多 14 条、缺口最多 7 条 —— `MAX_LABELS=256` / `MAX_OBS=32` / `MAX_GAPS=16` 这些**上限本身没被触发过**。触发后的降级语义与 C 一致（照抄的），但没有激励验证。 |

## 与参考项目的关系

| 借什么 | 来自 |
|---|---|
| 像素流 `din_vld/dout_vld` 时序、用真实图像写 testbench 的方法 | `docs/repo/fpga/FPGA_image_process` |
| BRAM 双缓冲/行缓冲的写法、Verilator 仿真与 C++ 模型写法 | `docs/repo/fpga/fpga_image_processing` |
| 流式单遍 CCL 的**方法学**（游程 + 等价表，只存游程不存整帧） | `docs/repo/workflow/linkruncca` |
| "C 模型与 RTL 在同一进程里逐拍比对"的**框架形状** | `docs/repo/workflow/c2rtl_equivalence` |

⚠ **没有直接采用 linkruncca 的 RTL**：它在 Verilator 里能跑，但外接框坐标对不上
（期望 `(80,199,100,139)`，实得 `(0,202,0,139)`，x 整体偏 +3、`minx/miny` 读到 0，
是它内部 `latency=3` 流水线的坐标对齐约定）。我们真正要比对的是**我们自己的
C 模型**，逐位一致要求两边坐标约定完全一致 —— 所以 CCL 自己写，只借它的算法。
