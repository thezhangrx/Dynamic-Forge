# 工具链现状 —— 手里有什么、还差什么

> 起因：`docs/resource/petalinux-v2018.3-final-installer.run` 解压之后，被问
> "能不能用它测 Verilog 视觉"。
> 结论：**不能。PetaLinux 是 PS 侧（Linux/驱动/交叉编译）的工具，里面一个综合器都没有。**
> 但它有两个立刻有用的东西，见 §3。
> 本文件记录实测到的工具清单，避免下一个人重复翻。

## 0. 三十秒版本

| 你要做的事 | 需要什么 | 现在有吗 |
|---|---|---|
| 验证 Verilog 逻辑对不对 | Verilator | ✅ 有（`$HOME/.local/verilator-5.020`） |
| **综合 / 时序 / 资源** | **Vivado 2018.03 + JFM_Kits** | ❌ **没有** |
| 生成 PS 侧 Linux（rootfs/dtb） | PetaLinux 2018.3 | ✅ 有（刚解压） |
| 编译 PS 侧驱动（aarch64） | 交叉编译器 | ✅ 有（Linaro 7.3.1） |

而 C 模型和 Verilator 都看不见这四件事（见 §4）。

## 1. 安装包是什么结构（逆向出来的，便于以后重做）

```
petalinux-v2018.3-final-installer.run          7 289 606 083 B
├─ 行 1 .. 262          bash 安装脚本（含 PLNXCHECKSUM）
├─ 行 263  `##__PLNXLICENSE__`          → Xilinx EULA
├─ 行 381  `##__WEBTALKLICENSE__`       → WebTalk 条款
├─ 行 386  `##__THIRDPARTYLICENSE__`    → 第三方许可（正文最长的一段）
├─ 行 14414143  `##__ENVCHECK__`        → 环境检查脚本（282 行）
├─ 行 14414426  `##__PLNXINSTL__`       → 嵌套安装脚本
└─ 行 14414642  `##__PLNXSDK_FOLLOWS__` → 真正的载荷，6 611 017 728 B
```

抽取方式（**不要**直接跑安装器：要先过环境检查，还要交互确认三段许可）：

```bash
SKIP=$(awk '/^##__PLNXSDK_FOLLOWS__/ { print NR + 1; exit 0; }' <安装包>)
tail -n +$SKIP <安装包> | tee petalinux-installer.tar.xz | md5sum
#   bb5a0a7225c2fd504eaf973fe16eb120   ← 与脚本里的 PLNXCHECKSUM 逐字相同
tar -I 'xz -T0' -xf petalinux-installer.tar.xz -C <目标目录>   # 6.6 GB → 13 GB，约 80 s
```

**坑**：载荷是 **XZ**，文件名/直觉容易当成 gzip。`tar tzf` 会静默失败（无输出、无报错），
必须 `tar tf`（tar 自己嗅探）或 `tar -I xz`。

## 3. 所以 PetaLinux 现在能拿来干什么

1. **立刻能开工写 PS 侧驱动**，不用等下载器、不用等 Vivado：
   `aarch64-linux-gnu-gcc` 已经能编 aarch64 目标码。
   本项目的 AXI 寄存器接口（`core/fpga/rtl/vision_axi.v`：
   `A_CTRL / A_SEQ / A_FLEN / A_FRAME / A_CFG_*`）就是驱动要读写的那几个地址。
2. **下载器到了就能烧**：`tools/xsct/SDK/2018.3/bin/` 里有 **`xsct` + `hw_server`**。
   XSCT 就是干"`fpga -f design.bit` 把 bit 推进 PL"这件事的 —— **烧写软件已经在手**，
   缺的只是它要吃的那个 `.bit`。
3. 后面生成 rootfs / 设备树（`petalinux-config --get-hw-description=<Vivado 导出的 hdf>`）。
   ⚠️ 这一步**依赖 Vivado 的产物**，也就是仍然堵在 §4。
   ⚠️ 且复旦微的 `JFMQL30TAI` 不是标准 Xilinx 型号，设备树/PetaLinux 板级支持
   要不要额外打补丁 —— **待核实**，见 `开发板架构.md` §9。

## 4. 为什么 PetaLinux 帮不上 Verilog 的忙

RTL 的问题域和 PetaLinux 的问题域不重叠：

| 问题 | 谁来回答 | PetaLinux 能答吗 |
|---|---|---|
| 逻辑对不对（逐位） | Verilator + C 模型 | ❌（但已答完，见 §5） |
| **吃多少 LUT/FF/BRAM/DSP** | 综合 | ❌ |
| **最高能跑多少 MHz、WNS** | 实现 + 时序分析 | ❌ |
| **能不能生成 bit** | 实现 | ❌ |
| 驱动能不能读回几何帧 | 交叉编译器 + 板子 | 编译器 ✅ / 板子 ❌ |
| Linux 起不起得来 | PetaLinux + 板子 | 构建 ✅ / 板子 ❌ |

**C 模型和 Verilator 的原理性盲区**：它们把 RTL 当软件跑，于是天然看不见
"除法器有多大、BRAM 推断成没成、组合链有多长、能不能收敛到 200 MHz"。
`vision_top.v` 里有整数除法（判据里的比值运算）——这正是最可能在综合后爆炸的一块。
**只有 Vivado 能回答，写多少 C++ 都不能。**

### 5.1 顺带修掉的一个**假通过** bug

手跑验证时按 README 的相对路径少敲了一层，得到：

```
激励读取失败：../../data/fpga/stim_color/000000.ppm（到此为止）
=== 协同仿真结果 ===
比对项 0，不符 0，有差异的帧 0
```

**退出码 0。** 也就是说：一次什么都没验证的运行，和一次全绿通过，输出和退出码完全一样。
三个测试台都有这个毛病，已修并加了守卫：

| 修的毛病 | 旧行为 | 新行为 |
|---|---|---|
| 激励读不出来 | `break` 后报"0 比对项 0 不符"，退出 **0** | 报"只比对了 x / N 帧"，退出 **1** |
| 请求 4 帧只给 2 帧 | 比 2 帧照样报绿 | 退出 **1** |
| RTL 超时未出帧 | 只加 `g_fail_frames`，而退出码看 `g_fail` → 部分帧超时静默报绿 | 计入失败，退出 **1** |
| `Vvision_selftest 0` | 自由运行段固定给 3 个比对项 → 报"比对项 3，不符 0"，退出 **0** | 显式拒绝 0 场景，退出 **1** |

守卫在 `core/fpga/tests/test_cosim.py`（5 条）。**已做反向验证：
回退 `tb_vision.cpp` / `tb_axi.cpp` / `tb_tpg.cpp` 到 `f36c649` 重跑，5 条全部失败。**
守卫是纯增量的证据：修完后 320 帧的指纹仍是当时的 `3530c161ee7463d4`，与修前逐位相同。

> ⚠ 该指纹后来变了两次，**两次都是有意为之，都与这里的假通过守卫无关**：
> `3530c161ee7463d4` → `b8adc5714593312d`：对齐 `to_standard` 的结构性过滤
> （丢掉 <24 px 的碎片、丢掉 `half_w < half_h` 的退化段），见
> `core/fpga/tests/test_ref_robustness.py` 文件头；
> → **`5b119febe6015a37`**：带末后处理「整堵墙共用一个朝向」，见
> `core/fpga/docs/帧存改造.md` §5 与 `vision_top.v` 里 `S_ANG_INIT` 的注释。

### 5.2 C 参考模型 ↔ Python 视觉链：**在部署场景上角度也对齐了**

RTL 只跟 C 比，所以"C 对不对"要另外证明。用 `core/fpga/ref/compare_with_python.py`
在**同一批 320 帧合成场景**上跑（正是闭环里用的那个 `wall_with_gap` 场景）：

```
$ python core/fpga/ref/compare_with_python.py --stim /tmp/stim_color --ref /tmp/vision_ref --limit 320
  比较 320 帧（缺口两边都有检出的 320 帧）
  缺口条数: Python 合计 2018，C 合计 2018
  墙段/障碍记录: Python 合计 4064，C 合计 4064
  缺口中心误差(像素): 中位 0.00 p90 0.00 max 0.01
  角色位置误差(像素): 中位 0.46 max 3.28
  墙段角度误差(弧度): 中位 0.000000 max 0.000623
```

**条数完全一致、角度中位恰好为 0、最大 0.000623 rad** —— 换算成分桶键
（`round(rotation*1000)`）不到 **0.6 格**，也就是两条实现的分组**不会分家**。

> 修之前是：逐段各自拟合角度 → C 与 Python 的 `tier` **48/48 个决策时刻全不同**；
> 换成整墙共用一个朝向后 → **0/48**。

⚠ **换到真实照片（`data/vision/*.jpg`，32 张）上就没这么好看了**：
角度中位 0.0055、最大 0.215 rad。原因是真实照片里同一"墙带"会出现 **>2 段**
（C 用"首段心→末段心"的弦，Python 用全部段心的 TLS 主方向），而且两边偶尔多检/少检
一段。**部署场景是合成渲染的 `wall_with_gap`（每堵墙恰好 2 段，实测 38/38），
那里两者精确等价**；>2 段的一般化留给以后。

> **2026-10-13 补**：上面这段之前**没有任何自动护栏** —— `compare_with_python.py`
> 只被手工跑过。现在有了 `core/fpga/tests/test_ref_vs_python.py`（7 条）：
> 部署场景（录像导帧）钉**硬指标** —— 缺口中心 ≤0.1、角度 ≤1e-3 rad（桶键不跨档）、
> 条数**完全一致**、角色位置中位 ≤1 px；真实照片只钉**量化上限**（角度中位 ≤0.02、
> max ≤0.8；条数分歧 ≤50%），防止这个已知分歧悄悄变坏。
>
> 补测时又量了一组（32 张 **640×360 居中裁剪**的真实照片，与上面 640×480 那组
> 语料不同，数字不可直接比）：缺口中心中位 0.00 / max 0.01；角度中位 0.004137 /
> max 0.397022；缺口 15 vs 18、墙段 55 vs 59。
> **角色位置是双峰的**：25 帧两边都检出，其中 9 帧误差 ≤ 0.4 px、16 帧 60~610 px ——
> 说明**矩/质心的算术是对的**，分歧在"哪个连通域当选"（CCL 合并/选优），
> 与"偶尔多检/少检一段"同源。

### 6.1 Vivado 装在哪：**Windows 原生**，不要装进 WSL

`30TAI使用教程.pdf`（本地 `docs/resource/2026嵌赛FPGA开发/20260916/`）是这么写的：

| 教程原文 | 说明什么 |
|---|---|
| `Vivado版本：2018.03` · `器件：xc7z030ffg676-2` | 版本与器件是钉死的 |
| `source E:/JFM_Kits/ip_patch/run.tcl` | **Windows 盘符路径** |
| "注意命令中不要出现反斜杠" | 典型的 Windows 路径→Tcl 转义坑 |
| 步骤 1.2 设"**用户环境变量**" `JFM_PATH` | Windows 环境变量语义 |
| `add_hook_tcl_to_prj` · `replace_7z030ai_file` · `reset_database_to_default` | JFM_Kits 注入的自定义 Tcl 命令 |

且 `JFM_Kits` 里全是**平台无关的数据文件**（`unisim.btl` / `zynq.lib` / `zynq.rtd` /
`xc7z030ai.paspd` / `unisim_comp.v` / `*.tcl`），**没有一个 `.exe`/`.so`/`.bat`**，
所以 Windows 和 Linux 的 Vivado 用的是同一份补丁。

**结论：Windows 装原生 Vivado 2018.03 即可，WSL 在这条路上没有位置。**
WSL 唯一"不可替代"的能力是 Linux 用户态，而 Vivado 不需要它；
反过来 WSL **最弱的一环恰好是 USB**（JTAG），见 §6.2。

### 6.2 板子下载/调试：把 `hw_server` 放在 Windows

不要用 `usbipd-win` 把 JTAG 线映射进 WSL —— 要 `chmod 777 /dev/bus/usb/`，
插拔一次就可能失效。改成官方文档认可的模式：

```
Windows：Vivado → 启动 hw_server（监听 3121）→ 直接吃本机 USB 栈 → JTAG 线
   ↑ TCP 3121
WSL / 任意 Linux：xsct 或 Hardware Manager → connect_hw_server -url <host>:3121
```

**这套软件现在就在手里**：PetaLinux 自带
`tools/xsct/SDK/2018.3/bin/hw_server`（以及 `xsct`）。
WSL2 若是镜像网络模式可直接 `localhost:3121`；NAT 模式用主机 IP，
并在 Windows 放行：`New-NetFirewallRule -DisplayName "Xilinx hw_server" -Direction Inbound -LocalPort 3121 -Protocol TCP -Action Allow`。

### 6.3 建议的第一步：跑综合（不需要下载器、不需要板子）

装 Vivado 2018.03（Windows 原生）+ 打 `JFM_Kits`，按教程的仪式：

1. 设环境变量 `JFM_PATH` 指向 `JFM_Kits` 目录
2. Vivado Tcl Console：`source $::env(JFM_PATH)/ip_patch/run.tcl`
3. `add_hook_tcl_to_prj`
4. `replace_7z030ai_file`（**首次使用 30TAI 必须做**，换回普通器件要 `reset_database_to_default`）
5. 新建工程：器件 `xc7z030ffg676-2`，**关闭 IP cache**
6. 把 `core/fpga/rtl/` 五个文件加成 design source
7. **直接点 Generate Bitstream**（教程明确：依次点 Run Synthesis / Run Implementation / Generate Bitstream 可能出问题）

然后取四个数：

1. LUT / FF / BRAM / DSP 占用
2. WNS / TNS
3. 最高频率（除法那一级会不会是瓶颈）
4. BRAM 推断有没有失败（`vision_top.v` 里那几张掩膜帧存）

⚠️ **待核实**：XC7Z030 在 Vivado 2018.03 免费版（WebPACK）范围内是否可用，
以及 Windows 11 下 2018.03 安装是否顺利 —— 这两条都要装完实测。

在此之前，`./obj_dir/Vvision_selftest 8` 是上板 bring-up 的第一条命令：
不接相机、不用数据文件、不用 C 模型，和手算几何比。

## 7. 综合实测（2026-10-12，Vivado 2018.3 / `xc7z030ffg676-2`）

工作目录 `D:\FPGAWORKS\vivado_vision_test`，脚本 `synth_plain.tcl`。

### 7.1 不需要 `-sv`：Verilog-2001 合规已经补上

早先用 `read_verilog -sv` 才过得去，报的是：

```
ERROR: [Synth 8-1549] a function must have at least one input [vision_top.v:229]
WARNING: [Synth 8-2644] root scope declaration is not allowed
```

根因是 `band_limit()` 是**无输入参数**的 `function` —— Verilator 容忍，
Vivado 默认（Verilog-2001）模式直接报错。补了 `input [15:0] pct` 之后：

```
$ vivado -mode batch -source synth_plain.tcl      # 刻意**不加** -sv
Synthesis finished with 0 errors, 0 critical warnings and 74 warnings.
```

**"Verilator 过 + 逐位对账过"不等于"综合器过"** —— 这条只有真的跑一遍综合才发现。

### 7.2 时序：setup 达标

| 量 | 值 |
|---|---|
| **WNS** | **+3.272 ns**（目标周期 5 ns，即 `create_clock -period 20.000` 之外那级） |
| WHS | **-0.034 ns**（34 ps 的保持违规，需要小修） |
| TNS | 0.000 ns，失败端点 0 |

早先 WNS 是 **-85.904 ns**，根因是**组合除法器**（`vo_scale_round` / `atan2` 里的 `/`）。
拆出 `vision_div.v`（恢复余数法、每拍 1 位、WN=40/WD=20）之后：`-46.498 → -11.728 → +3.272`。

> **保持违规 34 ps** 是另一类问题（不是逻辑深度），常规做法是在实现阶段加
> `set_clock_uncertainty` 或让工具插延迟；本次只跑到综合，**还没做实现**。

### 7.3 面积：**仍然装不下**，这是现在唯一挡住上板的事

| 资源 | 占用 | 器件有 | 利用率 |
|---|---|---|---|
| **Slice LUTs** | **116 979** | 78 600 | **148.83%** |

### 7.3.1 已定位的一处大浪费：`obs_words` / `gap_words` 变成了寄存器

综合日志里两条：

```
WARNING: [Synth 8-4767] Trying to implement RAM 'obs_words_reg' in registers.
WARNING: [Synth 8-4767] Trying to implement RAM 'gap_words_reg' in registers.
Reason is one or more of the following :
    1: RAM has multiple writes via different ports in same process.
    2: Unable to determine number of words or word size in RAM.
    3: No valid read/write found for RAM.
RAM "obs_words_reg" dissolved into registers
RAM "gap_words_reg" dissolved into registers
```

这两个数组是 `vision_top.v:217,218` 的 **512 × 32 bit** 几何帧暂存
（`reg [31:0] obs_words [0:511]` / `gap_words [0:511]`），Vivado **没能推断成
BRAM 或分布式 RAM，直接摊成了触发器 + 巨量读多路器**。512 深 × 32 位的读多路
器是 512:1，LUT 消耗极大。

两条立刻能做的：

1. **把深度改对**。实际只用 `n_obs*9 <= 288` 与 `n_gaps*9 <= 144` 个字，
   `[0:511]` 是白扔的（`obs_words` 少 44%、`gap_words` 少 72% 的位）；
2. **让它能被推断成 BRAM**：写口只留一个（现在多个状态往不同下标写）、
   读口改成**寄存读**（打包器 `byte_of(obs_words[pk_widx], pk_byi)` 现在是
   组合读，BRAM 做不到）。

### 7.3.2 ⚠ 一个我搞错过的判断（留档，避免重犯）

我第一次看到这份报告时，拿它跟工作目录里 20:14 那份 `util.rpt`（69 118 LUT /
WNS -11.728）比，得出"**`-sv` 与不加 `-sv` 综合出不同硬件**"的结论，还把这条
写进了文档。**这是错的。** 后来在同一份 RTL 上把两种跑法都重跑了一遍：

| 跑法 | Slice LUTs | LUT as Logic | Slice Registers | BRAM | WNS |
|---|---|---|---|---|---|
| `read_verilog -sv` | 116 979 | 108 615 | 56 776 | 82.5 | +3.272 ns |
| `read_verilog` | **116 979** | **108 615** | **56 776** | **82.5** | **+3.272 ns** |

**逐项完全一致**，连警告集合（`8-3917` ×51、`8-6014` ×27、`8-4767` ×2、
`8-639` ×1）都一样。那个 69 118 是**另一份更早的 RTL** 的报告，跟 `-sv` 毫无关系 ——
我拿跨越了多次改动的两份报告做单变量对比，属于典型的**混淆变量**。

教训：**要比较 A 与 B，必须在同一时刻、同一份源码上各跑一次**；跨时间点捞两份
旧报告来比，比出来的多半是"源码变了"而不是想验的那个变量。
