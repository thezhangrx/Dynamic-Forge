# 判据整体右移 +42 PL 列 / +55 页面单位：**根因 = quad 失效**（不是 RTL）

> 2026-10-26 排查结论。目标里那条"板上 PL 判据整体右移"**不是 RTL bug**，
> **不需要改 RTL、不需要重定位流**。下面每条都有可复算的数字与文件。

## 1. 结论（三句话）

1. 本地 `tb_p0` 用 `cam_00`（md5 `21e84f17…`，与板上 udmabuf 逐字节相同）+ 同一份 13 个系数，
   **逐字节 bit-exact（0 mismatch，连续 3 帧）。RTL 是对的。**
2. 板上"右移 +41.3 列"的对比**两边用的不是同一份 quad**：
   板子跑的是 10-23 的老 quad，本地参考用的是新 quad。差值 41.3 列 ≈ 55.1 页面单位。
3. 用**真值缺口**验收新 quad：报告 449.7（中心）/ 106.0（宽），真值 **449.3 / 106.0** ——
   差 0.4 页面单位。**新 quad 是对的，老 quad 才是错的。**

## 2. 三条独立证据

### 2.1 同一帧、同一系数：本地 bit-exact，板上"右移"

|---|---|---|---|

| obs#1 x | 228.5 | 249.5 | +21.0 |
| obs#2 x | 499.5 | 529.0 | +29.5 |
| obs#3 x | 129.5 | 149.5 | +20.0 |
| obs#4 x | 397.0 | 428.5 | +31.5 |

y 方向差 ≤1.5 行（同一份 quad 的 y 只差一个常数偏移，见 §4）。

### 2.2 老 quad 的预测值正好等于板端的观测值

老 quad `38.28 60.05 511.86 43.35 547.97 404.16 24.18 419.71`（`quad.json.stale`，10-23 23:35）
vs 新 quad `72.98 52.06 560.92 40.14 584.33 405.85 76.84 431.56`。

—— **宽度几乎一样、整体平移 43.7 相机像素**。代入映射：

```
x_old(truth) = (43.68 + 0.77766·x) / 0.77922 ≈ x + 56.1
```

板上实测的 18 道已学墙（`board_events.jsonl` 的 `add_wall`）相对真值缺口中心：
**+49.3 … +68.1，均值 +60.4**；差值的起伏来自 quad 是梯形（上下沿 x 差 14 px）。

### 2.3 同一场景、同一 agent：基线（vt_sparse）没有这个偏移

即 quad；PL 的判据（阈值/列计数）没有引入平移（2.1 的本地 bit-exact 已经排除）。

## 3. 为什么板上一直没发现 quad 是错的

`pl_vision.cpp: Rectifier::load()` 的规则是：**文件里的 quad 只要"合理"就直接用**
（`quad_ext=1`），不去和画面比对。老的 8 个数完全"合理"（四角在画面内、面积 >10%），
所以每帧都 `quad_ext=1`，而闭环闸门只检查 `quad_ext`/有墙有角色——
**闸门看不到 quad 本身就错了**。

## 4. y 方向为什么两个 quad 都能用

新老 quad 的 **y 跨度**几乎一样（老 360.8/359.7，新 365.7/379.5），
只差一个近似常数的平移（TL 60.05→52.06 = −8 px ≈ −10.7 页面单位），
而 agent 的 `world = (py−240) + y_scale·vy + y_bias` 里 `y_bias` 正好吸收常数偏移。
所以 y 一直"看着还行"（plp0f 的 18 道墙 dy = −30…+15），
**x 没有这种吸收项**（`x_bias` 锁定 0，见 `core/using/LOCKED.md:47`），
于是 quad 的 x 错多少、墙上就错多少。

## 11. 第 4 轮：诊断寄存器落地 + 一次重建，**"帧首残留"假设被否**

新增只读寄存器 **0x958 FRMDIAG** = `{2'b0, sof_cnt[5:0], sof_wp[5:0], sof_rp[5:0], cnt[5:0], wp[5:0]}`
（`sof_*` = `in_vld && in_sof` 那一拍的 camadapt 缓冲状态）。位流重建一次
（`bd_vision_p0_diag.bit` md5 `836b6d46…`，上一版 `78f63c19…` 另存），
JTAG `default 1 0` 烧写 `PROGRAM_PL_OK`，单帧实测：

```
dd = 2637  →  wp=13  cnt=41  sof_rp=0  sof_wp=0  sof_cnt=0
```

**结论：帧首 `cnt = 0`** ⇒ camadapt 的缓冲在帧首是空的、指针在第 0 格
⇒ 「上一帧没排空导致整帧右移」**不成立**。

同时用新位流重跑同一帧，几何帧**一字不差**（walls 426.5 / 278.8，
gl/gr = 394.0/487.3、252.7/370.0；player 381.5/236.4）⇒ 偏移仍然存在。

⇒ 偏移 = **输出列与"取到的源像素"之间的固定错位**（≈37.5 列），最可能是
正交流水线**预取/行缓存在等 DDR** 时把"取源"跑在"输出列计数"前面：
仿真里存储响应是理想/极快（预取领先 ≈0），硅上是 linecache 未命中延迟（领先 ≈37 拍）。

**下一轮验证方式（不用再烧写）**：`tb_p0` 里把存储写/读延迟调大
（`vision_axi.v:475` 注释提到 tb 已有 `--w-delay`），看是否出现 **+37.5 列、宽度不变**。
复现后修：让输出列计数按"源像素实际对应的列"走（或在预取通道上补偿延迟），

## 13. 第 7 轮（续）：机制找到了 —— **`out_sof` 一辈子只响一次**

读码确认（`core/fpga/rtl/vision_camadapt.v`）：

```verilog
reg row0_done;                                   // 只在 rst_n 清（:115）
out_sof <= (ocol == 10'd0) && !row0_done;        // :160
if (ocol == WIDTH-1) row0_done <= 1'b1;          // :165 置位后再也不清
```

⇒ **`out_sof` 只在复位后的第一帧脉冲一次**。而 `vision_top` 靠 `din_sof`
清 `wr_row/wr_col` 并从 0 开始写（`vision_top.v:342`、`:1149`）。

后果：**只要任何一帧的像素数不是正好 640×360，偏差就永久留在列相位里**。
真硅上第一帧（复位后）末尾/开头多出或少掉 37 个像素，于是之后每一帧都整体右移 37 列
