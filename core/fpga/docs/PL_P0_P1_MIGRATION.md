# P0 + P1 迁移设计（正射与判据搬进 PL）

> 立于一 2026-10-25。**基线逻辑一行不动**：`board_agent` 的准入/去重/停走、M1 决策、
> `@POSE/@MOVE`、quad/calib、`task.json`、场景。本文只管"像素面搬到 PL"。
> 目标：端到端 **≤35 ms/帧**（P0）+ PL 输出与 `vt_sparse` **同判据**（P1）。

## 0. 先纠正一个口径（写下来免得再做错）

"把 `vt_sparse` 的判据搬进 PL" **不是**换一个阈值。`vt_sparse` 的核心是
**自适应亮度门限 + 稀疏行采样 + 逐行暗段找缺口**（`core/board/tools/vt_sparse.cpp:217-300`），
而 `vision_top` 现在是 **绝对 RGB 判据 + 行直方图 + 列投影 + 扫描线 CCL**。
两者是两套几何提取算法，只是测量结果接近（Δy ≤2 px）。

所以 P1 拆成两档：

| 档 | 内容 | 为什么需要 |
|---|---|---|
| **P1a（本次做）** | 把**像素级判据**改成 `vt_sparse` 的：`luma = (77R+150G+29B)>>8`，门限 = 帧内 **90 分位亮度 − 20**，夹在 `[90,200]`；掩膜改用它 | 这是 **P0 的前置**：正射搬进 PL 后，PL 直接吃相机像素，现有"绝对暖白 R−B>40"判据在相机域不成立（R−B≈−5），而 `pl_vision` 现在靠"形状染色"适配硬凑 —— 那套参数是量出来的，搬不进 RTL |
| P1b（不在本次） | 把整个几何提取换成 `vt_sparse` 的稀疏采样 + 暗段法 | 收益不确定（现在 Δy 已 ≤2 px），成本是重写整条流水线 |

## 1. 目标架构（P0 完成后）

```
板端 PS                                          PL（50 MHz, FCLK_CLK0）
 ffmpeg 640×480 RGB24 ──memcpy──▶ udmabuf(DDR)  ┌────────────────────────────┐
                                                │ AXI4 master 读（HP0）       │
 写寄存器：SRC_ADDR/STRIDE/尺寸/H[0..8] ──────▶ │  ├ 行窗口缓存(4~8 行)       │
 写 CTRL.start                                  │  ├ 正射(固定点, nearest)    │
 读 STATUS/CTRL.done ─────────────────────────  │  └ din_* ──▶ vision_top     │
 读几何帧 0x100（76~1804 B）      ◀──────────── │        （P1a 判据）         │
 写 /tmp/vt.jsonl（坐标映射不变）               └────────────────────────────┘
```

- **PS 侧只做**：memcpy 一帧进 udmabuf（921,600 B）、写 9 个 H 系数、等 done、读 76~1804 B。
- **PL 侧**：正射、判据、几何帧全部内部完成；`vt.jsonl` 的字节省 PS 只做坐标映射。
- 兼容：`vt.jsonl` 字段不变；`board_agent`/M1/协议不动；`loop_standard.sh` 只换 `CAM_VT_BIN`。

## 2. 正射的定点约定（与 C 参考同算术，逐位一致由构造保证）

坐标系与 `pl_vision.cpp:288-356` 完全一致：输出像素 `(c, r)` →
页面点 `px=(c+0.5-80)/0.75`、`py=(360-r-0.5)/0.75`，再经 `page→cam` 单应取相机坐标。

- **H**：PS 用 double 解 `field_frame::homography()` 再 `invert()`，按 `H[8]=1` 归一化，
  写成 **Q8.16 int32**（9 个寄存器）。若 `|H[8]|<1e-6` 则本帧判失败（不发 start）。
- **列/行基**：`CA = 4/3`、`CB = (0.5-80)·4/3 = -106.0`、`PY(r) = (359.5-r)·4/3`，
  全部 Q8.16。
- **每行 6 个系数**（PL 内部算，6 次乘加/行）：
  `au=h0·CA`, `bu=h0·CB+h1·PY+h2`（v、d 同理用 h3..h5、h6..h8）。
- **每像素**：`num=au·c+bu`, `den=ad·c+bd`；`|den|<2^8` → 该像素输出黑（页面外/退化）；
  否则 `u=num/den`、`v=av·c+bv / den`，都是 **Q8.16**，取整数部分查表（v1 最近邻）。
- 中间量位宽：系数/行基 int32（Q8.16，|h|≤16 保证不溢出）；乘积 int64 在 C 参考里只用
  int32+移位，RTL 用 24×18 DSP。除法 32/32 → Q8.16，流水线化，**1 像素/拍**。
- **v1 采样 = 最近邻**（`pl_vision --nearest` 同一口径）；双线性留 v2（判据对 1 px 不敏感，
  但先不引入额外乘法器）。

> **⚠ 2026-10-25 修订（R9/R10）**：分子/分母**不能共用定点格式** —— 分母 `ad/bd` 必须用
> **Q8.24**（分子仍 Q16.16），否则单应第三行的小系数只剩 1 LSB、右缘 u 差 **6 px**。
> 定稿算术与实测（0.0125 px）见 §7 的 R9/R10。

## 3. 新增寄存器（0x900 段；0x100..0x8FF 被几何帧窗口占用）

| 偏移 | 名 | 说明 |
|---|---|---|
| `0x900` | ORTHO_CTRL | 写 bit0=start（自清）；读 bit0=busy bit1=done bit8=src_fail |
| `0x904` | SRC_ADDR | udmabuf 物理基址（32 位，DDR <4 GB） |
| `0x908` | SRC_GEOM | `{h[15:0]=480, w[31:16]=640}` |
| `0x90C` | SRC_STRIDE | 源行跨距（字节，640×3=1920） |
| `0x910..0x930` | H0..H8 | Q8.16 int32，`H[8]` 正常为 65536 |
| `0x940` | ORTHO_STAT | `{miss_cnt[15:0], fetched_beats[31:16]}` 只读，诊断行窗口命中率 |

## 4. 验证四关（每关不过不进下一关）

1. **C 参考 ≡ RTL（Verilator）**：同一帧、同一组 H，正射输出 PPM **逐字节一致**。
   `core/fpga/ref/ortho_fixed.c` 是唯一 oracle（纯整数，无浮点）。
2. **正射质量**：RTL 输出 vs 现 float 版 ≤ **1 LSB**（最近邻版对 float 版不必逐位，但
   ≥99.9% 像素相同）；感知输出（掩膜/行带/墙/缺口/角色）与 float 版**逐字段一致**。
3. **与 `vt_sparse` 同判据（P1a）**：相机域 300 帧，墙 Δy 中位 ≤2 px、缺口边界 ≤3 px、
   条数与 `vt_sparse` 一致率 ≥95%（现状 ~75%，其中"贴左沿漏报"按 P1a 新判据重测）。
4. **上板**：单帧端到端 ≤35 ms（L1）；相机域 300/300 与 C 参考逐字节一致；然后 1 轮闭环（R1c）。

## 5. 顺序（为什么 P1a 在 P0 之前）

1. **P1a**：自适应亮度判据进 `vision_top` 的 classify（参考 + cosim + 相机域 300 帧）。
   此时 `pl_vision` 可以**关掉相机域适配**（形状染色），直接喂正射后的页面像素 —— 与
   `vt_sparse` 同一判据，先证明"同源"。
2. **P0**：正射 + DMA 搬进 PL。因为 P1a 后 PL 不再依赖"暖白染色的画"，搬过去才不会二次改判据。
3. 上板两轮 + 1 轮闭环。

## 6. 风险与回退

- **BRAM**：行窗口 4~8 行源像素（4×640×3=7.7 KB）远小于现占用；不需要整帧缓存。
- **AXI 带宽**：源帧 921,600 B/帧，HP0 64 bit@50 MHz 峰值 400 MB/s → 理论 2.3 ms；
  实测留 2 倍余量（≤5 ms），与 PL 计算重叠。
- **时序**：50 MHz 现有 WNS +0.9 ns；新增除法流水线需重新看时序，若不收敛降到 40 MHz 仍在预算内。
- **回退**：位流与 `pl_vision` 都按"新二进制 + 旧二进制并存"部署
  （`/root/tools/pl_vision_v2` vs `pl_vision`），`CAM_VT_BIN` 一行切回。

- 关键差异不在判据，而在**下游语义**：这种带**找不到合法缺口**（`n_gaps=0`），

  不是同一帧。脚本内部 vt/PL 吃的是同一份 raw，所以对拍本身没有错位。

**下一轮的两条路（需要用户口径）**
1. **带没有合法缺口 → 不发障碍**（与 `vt_sparse` 对齐；风险：真·满宽墙也会被丢，
   但本场景每道墙都有缺口）；

### R9（2026-10-25）：6 px 的根因找到了 —— **小系数被量化两次**

单点追踪 `(r=0, c=638)`：

```
float ： num=646.5984  den=1.096059          u=589.930
定点  ： num=646.5862  den=1.084534          u=596.188
        (分子误差 0.012 → 无害；**分母误差 0.0115，相对 1%** → u 被放大成 6 px)
```

分母错的来源：
```
h6(真实) = -1.15e-5
hq[6]    = round(h6*65536) = **-1**            ← 第一次量化：相对误差 25%
CAq      = 87381 (4/3)
ad       = (hq[6]*CAq)>>16 = (-87381)>>16 = **-2**  ← 第二次：算术右移是 floor，再 -1
真实 ad  = h6*CA = -1.53e-5 (= -1 LSB)
```
`ad` 差 1 LSB（100% 相对误差）→ `den` 差 1% → 右缘 u 差 6 px。**这不是精度不够，是
"先把小系数压成 1 LSB 再参与运算"**：第三行（`h6/h7`）本来就比 `h8=1` 小 4~5 个数量级。

**修法（下一轮照这个改，二选一）**
1. **分母单独用高精度**：`ad/bd` 用 Q8.24（h6=-1.15e-5 → -193 LSB，相对误差 0.5%），
   `u = (nu << 8) / nd`（nu 仍是 Q16.16、nd 是 Q8.24）。算过：u 误差 ≈ 0.03 px ✅
2. 整个 H 用 Q8.24 + 40 位累加（RTL 上要多 1 个 DSP 宽度，但一次到位）。

先按 1 在 python 里验到 ≤0.05 px，再决定 RTL 用哪种位宽 —— 这样 RTL 的第一版就不会
带着 6 px 出生。

### R10（2026-10-25）：修法验证通过 —— **定点 vs 浮点 0.0125 像素**

按 R9 的方案 1（分子 Q16.16、**分母 Q8.24**）重算，360×640 全域抽样：

```

```

定稿的算术（RTL 与 C 都照这个写）：

```

边界          ：|ad*c+bd| < 1024（Q8.24 的 4e-5）→ 该像素输出黑（页面外/退化）
```

**关键教训（写进 §2 的注）**：单应第三行比 `h8` 小 4~5 个数量级，
**分子/分母不能共用一个定点格式**；共用会让 `ad` 只值 1 LSB、相对误差 100%。

### R15（2026-10-25）：按"一整类宽度问题"重查 —— 27.9% → **99.66%**

**结论**：clamp 的时序**不是**原因（拆开后行为不变就证明它原本就是对的）。R30/R31 那条"读早一拍"
的推断**被自己的实验证伪**——这正是 R7 要防的：推断必须落到"改完数字会变"上，不变就是没找对。

**重新收敛后的嫌疑（下一步就查这个）**：我一直在拿 RTL 与**python 复算**比，而"expected PPM"是
**C oracle** 生成的；两者在 r≥306 处可能就已经不同。所以下一步：
1. 给 `ortho_fixed_ref` 加 `VR_DBG_UV=r,c`，把它**实际用的 u/v/addr** 打出来；
2. 与 RTL 同点（探针现成）对比；
   - 若 C 的 addr ≠ python 的 addr → 说明**oracle 自己**在尾部有特殊处理（最可能是它的
     `pyf <= 0 || pyf > PAGE_H` 行门控，rows 306+ 的 `py` 已接近 0）；
   - 若 C = python ≠ RTL → 回到 RTL。

### R33（新目标第 2 轮）：oracle 侧自证清白 —— 差异确实在 RTL 的"收商"这一级

给 `ortho_fixed_ref` 加了 `VR_DBG_UV=r[,c]`，把 oracle **实际用的** u/v/addr 打出来：

```
C   r=306 c=80：nd=17039814  u=26  v=361  addr=231066
RTL 同点     ：nd=17039814  u=26  v=359  addr=229786    ← 差 2 行
```

而上一轮已证明两边的 `uq/vq`（1768998 / 23692724）**逐位相同**。同一个 `vq` 经
`(vq-32768)>>>16` 只能得 361，RTL 却得 359 ⇒ **RTL 里 `v_abs_q` 存的不是 23692724**。

最可能的机制（下一步第一件事验证）：`st2` 发出 v 的 `div_go` 之后，`st3` 立刻看到的是
**u 那一次的 `done` 残留脉冲**，于是把 u 的商当成 v 的收下 —— 这会给出与"少 2 行"一致的量级。
验证方法：在 st3 判 `div_done` 的同时打印 `busy`（若 `done` 来了而 `busy` 还没起来，就是残留脉冲），
或在 `st2` 发 `div_go` 后**强制等 `busy` 拉高**再进 `st3`。

### R34（新目标第 3 轮）：第三条假设也失败 —— 差异对除法器握手**完全不敏感**

加了 `st6`（发 `div_go` 后先等 `div_busy` 拉高，再进 `st3` 收 `done`），专门针对"u 的 done 残留脉冲"：

```
不符 64794（首错 587760）——与前两次**完全相同**
```

连续三次改动手术后数字都不动（clamp 拆态、组合 clamp、等 busy），说明：
**这 64794 字节与除法器的时序、clamp 的相位都无关**。差异是"静态"的 ——
同一帧、同一点，两边稳定地取到相差 2 行的源像素。

**所以下一步必须换手法**：不再改 RTL，而是把 **RTL 与 oracle 的 addr 逐像素全量对比**
（一个输出像素打一行 `addr`，两列 diff），看差异是：
- 只在 v 方向（则问题在 `nv/bv/nd` 的尾部行为，尽管同点抽样看起来一致）；
- 还是 u、v 都有（则问题在地址组装或源缓冲）。

这份全量对照能一次回答，而单点探针已经连着三次把我带偏 —— 这正是 R7 说的
"由点及面"：**要看整行/整帧的模式，而不是再挑一个点猜**。

### R35（新目标第 4 轮）：差异是**行方向、且越靠下越大** —— 不是 2 行常数

全帧统计（RTL vs oracle）：

```
行 0–50    ：两边均值 48.4 / 48.4     差异像素 0
行 300–305 ：51.4 / 51.4              差异 0
行 306–310 ：53.8 / 53.7              差异 32 → 65（逐行增加）
行 350–359 ：55.7 / **112.0**         差异 478（整行）
```

**关键读数**：`行 350–359` 的 oracle 均值 112、RTL 55.7 —— oracle 采到了**相机画面底部更亮的区域**，
RTL 采到的更暗 ⇒ RTL 的 `v`（相机行）系统性偏小，且**越靠下偏得越多**（不是固定 2 行）。

这排除了"常数偏移/相位"这一整类（前面三次改动为什么数字不动，现在有解释了），
指向**行方向的比例/斜率**问题：`v` 随行号增长得比 oracle 慢。
嫌疑只剩两处，且都能直接算：
1. `py16 = PY0_16 - PS_16*r` 与 oracle 的 `PY16 - PS16*r` 是否**真的同一组常量**（tb 传参 vs oracle 内部）；
2. `bv` 里 `(h4*py16)>>>16` 在 r 增大时是否被截断（负数的算术右移方向）。
**下一步**：把 r=0/180/306/359 四个点的 `py16 / bv / nd / nv / vq` 两边列出来（探针全现成），
斜率一算就知道是常量还是截断。

### R36（新目标第 5 轮）：oracle 的 v 随行号**单调 +1/行**（59→418），RTL 底部却采到暗区

用 `VR_DBG_UV` 把 oracle 在四个行号的采样点打出来（c=80）：

| 行 r | u | v（相机行） | addr |
|---|---|---|---|
| 0 | 38 | 59 | 37798 |
| 180 | 31 | 230 | 147231 |
| 306 | 26 | 361 | 231066 |
| 359 | 24 | 418 | 267544 |

`v` 的斜率 ≈ +1.0/行（这正是"页面 y 与相机 y 的 1:1 关系"）。

而 RTL 输出在 350–359 行的**亮度只有 55.7**（oracle 112）⇒ RTL 采到的是相机**上部**的行，
即它的 `v` 在底部没有跟上这个斜率。

**下一次接手就三行代码的事**：在 RTL 的 `st3` 打印 `(r, u, v)`（clamp 后的最终值），
取 r=0/180/306/359 四个点，与上表逐项比 —— 斜率一比就知道是 `H4*py16` 的移位方向，
还是 `AV/BV` 的两个常数项。**不要再动时序**（R32–R34 已证明那三条都不是原因）。

### R37（新目标第 6 轮）：**找到真凶 —— 钳位用错了坐标系**，64794 → 3555

四点探针（RTL 侧，c=80）：

```
r=0   u=38 v=59  addr=37798     ← 与 oracle 完全一致
r=180 u=31 v=230 addr=147231    ← 一致
r=306 u=26 v=359 addr=229786    ← oracle 是 361
r=359 u=24 v=359 addr=229784    ← oracle 是 418
```

**`v` 从某一行开始卡在 359** —— 而 359 = `PL_H-1`。也就是说：`vi` 被**按页面高度（360）**钳位了，
但 `v` 是**相机行**（0..479）。于是 r≥306 之后采样点全被压到相机第 359 行（画面偏暗），
这正好解释"越靠下差得越多、底部整行都错"。

**修法（这一类）**：钳位与地址步长必须用**相机尺寸**，不是页面尺寸 ——
`vision_ortho` 新增 `SRC_W/SRC_H` 参数，`ui/vi` 用它们钳位、`pend` 用 `SRC_W` 做步长。
（`u` 之前"碰巧对"，是因为相机宽 640 恰好等于页面宽 640 —— 这类"碰巧"正是 R7 说的
"由点及面"要抓的：两条钳位不能一条用一个坐标系。）

```
不符：64794 → **3555**（首错 587760 → 676080，挪到了接近末行）
lint：新增 2 条告警（SRC_W/SRC_H 未用满），下次顺手清
```

**下一步**：尾部 3555 字节（首错在行 352 附近）—— 先打 r=352 的 `(u,v)` 与 oracle 比，
按同一思路查（很可能又是"页面/相机"某一处混用，例如行门控 `r0..r1` 与实际输出行数）。

### R38（收尾第 1 轮）：剩下的不是"尾部一批"，是**从页面左沿长出来的楔形**

按整帧模式统计（不再挑点）：

```
差异只在行 352..359；每行差异列从 **80**（页面左沿）开始，向右逐行加宽：
行352: 80..108 (29)   行356: 80..245 (166)   行359: 80..347 (268)

```

**读法**：差异区是一个**从页面左下角张开的三角**。这类"随行加宽、且从固定列开始"的形态，
通常是**某一侧越界后被钳位**（越靠下越早越界），而不是随机错位。

下一步（两点定点，探针现成）：
1. RTL 与 oracle 在 `r=359, c=80` 的 `(u,v,addr)`；
2. 同点 `r=359, c=347`（楔形右端）。
若 RTL 的 `u` 在这两点被钳到 0 / 或 v 钳到 479，就是"钳位仍用错坐标系"的残留
（例如 `c0/c1` 是**页面列**，但 `u` 的钳位该用**相机列**，两者在左沿附近不等）。

### R39（收尾第 2 轮）：两点探针**完全一致**，但同一像素的输出值不同 → 嫌疑转向"tb 的喂数相位"

`r=359` 两点（探针 vs oracle）：

c=347: RTL u=314 v=410 addr=262714  C 同值

**下一轮唯一动作**：把输出态再往后推一拍（新增 `st7` 作为"数据到达"那一拍），

### R40（收尾第 3 轮）：把"错拍"这个解释也收紧 —— 它只在尾部出现，不是全幅

复盘 R39 的证据：若真是**全幅错一拍**，前 351 行也该错（相邻像素差异足够大），但前 351 行**逐字节全对**。

### R41（收尾第 4 轮）：也不是"整体平移"——尾部采样点在两个方向上都偏

### R48（新目标②设计）：AXI4 master + 行缓存 —— 先把账算清楚再写 RTL

**数据量与时序预算**（先算，避免写出一个"能跑但超 35 ms"的东西）

```
源帧 640×480×3 = 921,600 B/帧
50 MHz 下 64 位 HP 口峰值 = 400 MB/s → 理论下限 2.3 ms/帧
（留 2 倍余量：目标 ≤5 ms，与 PL 计算 22.5 ms 重叠）
现有 mmap 逐字推：76,800 字/帧、实测 17.3 ms（4.4 M 字/s）→ 必须换掉
```

**模块划分（新增两个文件）**

| 文件 | 职责 |
|---|---|
| `rtl/vision_axi_master.v` | AXI4 读主口：给定 `base_addr + 行号`，发 INCR burst 把**一整行**（1920 B = 240 个 64 位拍）读进行缓存 |
| `rtl/vision_linecache.v` | 4 行窗口（4×1920 B = 7.7 KB，BRAM 够）：`req(addr)` → `data`（1 拍延迟），miss 时向 master 要行并**阻塞** 1~2 拍 |

**为什么是"按行取"而不是"随机 1 拍 1 像素"**：正射每个输出行的 `v` 基本是常数（±2 行），
按行取能吃掉 ≥95% 的确定性；行内 `u` 随机，用行缓存命中即可（4 行窗口足够覆盖 ±2 行）。

**接口不变**：`vision_ortho` 的 `src_addr/src_rgb/src_valid` 一个字都不改 —— 只把"谁提供数据"
从 tb/PS 换成 linecache。这样**已有的逐字节验证继续有效**（同一套 oracle、同一套 tb 逻辑）。

**验证顺序（本地，先仿真后综合）**
1. 内存模型：cosim 里用一块 `uint32_t mem[307200]` 当 DDR，master 从中读；
2. `tb_ortho` 增加 `--axim` 模式：源数据由 master+linecache 提供，输出仍与 oracle 逐字节比；
3. 通过后再进 BD（HP0）与综合。

**风险**：AXI4 读主的 `RLAST`/`RVALID` 反压处理是最容易出错的地方 —— 按 R7，先写一个
**只读不缓存的极简 version**（每拍要一个 64 位字，不复用），把功能跑通，再加行缓存优化。

### R49（新目标②开工）：`vision_axi_master.v` 写好，**lint 0**

```

```

### R63（五步目标·第 5 轮）：正射重写成流水线 —— **507 ms → 9.9 ms/帧（51×），仍逐字节 0 不符**

按 R62 的数字动手，两处改动，各自有独立的门禁：

**① 除法器流水化**（`rtl/vision_div_pipe.v`，新模块，不动 `vision_div`）

```
radix-4 恢复余数，17 级，II=1，商 34 位（= |u|·2^24 的几何上界：|u|<1024）
WQ=34 不是拍的：Q≥2^34 ⇒ |u|≥1024 ⇒ 一定被钳到 639/479，所以"溢出按饱和处理"与
"先用 64 位精确算再钳"**等价**；ovf 位就是这条等价的桥。
```

新门禁 `tb_divpipe.cpp`：20 万对随机+边界（商 0 / 商 2^34−1 / 商超宽 / den=1 / 2 的幂），
两个随机种子各跑一遍：

```
输入 200000  输出 200000  商不符 0  溢出标志不符 0  拍数 200022   ← II=1（200k 输入 200k 拍）
PASS ×2
```

**踩到的两个真 bug（都有数字指着）**：

1. `rem` 不该存 `RW=WN+2` 位 —— `{rem,nb}` 变成 68 位被截成 66 位 → 16.9 万/20 万对错。
2. **每级都直接读输入口 `num`** —— 于是每一级拿的是"当前这一拍"的被除数，不是自己那一拍
   进队的像素。单测（喂一个数、等 25 拍）看到的是**正确值**，连续喂就全部输出成
   **最后一个像素**的结果（`got=3002` 恒定）。改法：被除数低 WQ 位跟着流水线走（`num_p[]`）。
   这条正是 R7 说的"单测过 ≠ 对"：**串行喂**才暴露。

**② 行缓存 4 行 → 32 行**（`vision_linecache.v`，`NLINES=32`、`IDXW=16`）

```
填充次数  6179 → 376 次/帧（≈ 一条相机行填一次：扫描是单调的）
DDR 流量  11.9 MB/帧 → 0.72 MB/帧（AXI 90240 拍 = 376×240）
面积代价  61,440 B ≈ 14 个 BRAM36（7030 有 75 个）
```

**③ `vision_ortho` 重写成"行系数 → ISSUE → 2×流水除法 → FETCH/输出"**

```
- ISSUE 每拍一个像素，c 走 0..PL_W-1；c∉[C0,C1) 的**黑边带自己补黑**（下游 vision_top
  没有背压、靠 din_sof/eol 定位行首行尾，所以输出改成"整行 640 个"，省掉一层插黑边的胶水）
- FETCH：真实像素 2 拍（发请求 1 拍 + 收数据 1 拍），黑像素 1 拍；miss 时 ce=0 冻结整条流水线
- 每行一次行系数（SETUP 1 拍），360 行共 360 拍，可忽略
```

**踩到的第三个真 bug**：`ce = (fst==F_IDLE) || src_valid` —— F_WAIT 那一拍照样让流水线前进，
末级的下一个像素被顶掉，**每帧正好丢 1 个像素**（表现：`ocol` 停在 639、`done` 永不拉高、
tb 跑满 guard 超时）。改成 `ce = (fst == F_IDLE)`（只在"取走末级"那拍前进）。

   0x900 FRMCTL   W: bit0 像素源(1=正射) bit1 start(同时起 vision_top) bit2 清完成
                  R: {fills[15:0], 13'b0, done(粘滞), busy, src}

**Vivado 综合（`bd_pack.tcl`）抓出的问题 —— 这两个是本地 Verilator 永远看不到的**

```
ERROR: [Synth 8-3391] Unable to infer a block/distributed RAM for 'cmem_reg' ... 491520 bits ...
ERROR: [Synth 8-6156] failed synthesizing module 'vision_linecache'
```

**① `vision_linecache` 的存储方式不可综合成 BRAM。** 现在 `cmem` 是**按字节**寻址的
`reg [7:0] cmem[0:61439]`，填充时一拍写 8 个**不同地址**的字节（`cmem[wid+0..7]`）
—— 那是 8 个写口，BRAM 只有 1 个。Verilator 不在乎，Vivado 直接报错。

**改法（下一轮做）**：存**像素**（24 位）而不是字节：
```
reg [23:0] pmem [0:NLINES*640-1];   // 32 行 × 640 像素 = 491520 bit，1 写口 1 读口
填充：把 240 个 64 位 beat 重排成 640 个像素（8 字节 = 2⅔ 像素，相位只在 {0,1,2} 里循环
      → 一个 3 选 1 的移位，不是桶形移位器；用 80 位 acc + navail 计数，一拍写一个像素）
读：地址 = slot*640 + u_pix，一拍一个像素（**顺带把 R62 那个字节序问题从根上消掉**）
代价：填充 240 beat → 约 880 拍/行（376 次/帧 ≈ 331k 拍 = 6.6 ms），
      总 403k + 331k = 734k 拍 ≈ 14.7 ms @50 MHz —— 仍在 35 ms 预算内（vision_top 22.5）。
```
这条路比"64 位字 + 3 字节跨字读"简单（后者需要 2 个读口或 2 拍读）。

**② 相机域适配（`camera_domain_adapt`）必须一起搬进 PL。** 这一条是**读代码读出来的**，
不是综合报的，但它决定了 P0 能不能保住已验证的感知行为：

`core/board/tools/pl_vision.cpp:403` 在**推送前**对整张 640×360 页面图做逐行连续段重染色：
```

逐行：gray >= kAdaptDark(150) 的连续段，长度 >= kAdaptRunMin(40) → 记 is_wall
逐像素：is_wall → R=G=v, B = (v > 60) ? v-60 : 0     （暖白，喂 PL 的 R-B 判据）
        else v >= 150 → R=G=B=210                  （短亮斑=角色/反光，保持中性）

```
**为什么不能留在 PS**：它作用在**正射之后**的页面图上；PS 一旦不自己做正射，就没有这张图了。
**为什么不能用 P1a 的 luma 判据替代**：P1a（自适应阈值 + 行长门）在相机域与 `vt_sparse` 的
条数一致率只有 263/300（87.7%），而"软件适配 + 推页面"这条路是 **300/300 逐字节一致**。
闭环（⑤）要比基线，必须保住后者。

**RTL 可行性**：两趟流水就能做 —— 第 1 趟算 gray + 行长判定，写进行缓冲
（640 × {8 位 gray, 1 位 wall}）；第 2 趟读行缓冲、重染色后输出（延迟一行）。
门禁：与 C 函数逐字节对拍（直接用 `data/fpga/ortho_stim` 的真实相机帧）。

### R69（五步目标·第 8 轮）：**位流出来了** —— 卡点是 `wall_mem`/`bright_mem` 的**多写口**，不是容量

**根因（R68 的"下一轮"按计划执行，一步到位）**

它们**早就写了 `(* ram_style = "block" *)`**（`vision_top.v:250-251`），为什么还走分布式？
因为 P1a 让它们有了**三个写来源**（收帧 `S_RECV`、重分类 `S_LRC1`、形状门清 0 `S_LRC2`），
Vivado 看成多写口，而 BRAM 只有 1 个写口 → 退化成分布式 RAM（还是复制的）。
（时间线也吻合：r8 位流是在 P1a 之前出的，那时候它们只有一个写口。）

**修法（纯结构、语义等价）**：三条来源本来就是**同一个状态机的互斥分支**，所以合成一个写口：
```verilog
wire wr_recv = (state == S_RECV) && din_vld;
wire wr_lrc1 = (state == S_LRC1) && lrc_vld;
wire wr_clr  = (state == S_LRC2) && pc_valid;
wire        wm_we = wr_recv | wr_lrc1 | wr_clr;
wire [AW-1:0] wm_wa = wr_recv ? wr_addr : (wr_lrc1 ? rd_addr : pc_a);
wire        wm_wd = wr_recv ? is_wall : (wr_lrc1 ? lrc_pw : 1'b0);
wire        bm_we = wr_recv | wr_lrc1;   // bright 没有"清 0"那一路
wire [AW-1:0] bm_wa = wr_recv ? wr_addr : rd_addr;
wire        bm_wd = wr_recv ? cls_w[1] : (gray_rd >= r_luma_pthr);
always @(posedge pix_clk) begin
    if (wm_we) wall_mem[wm_wa]   <= wm_wd;
    if (bm_we) bright_mem[bm_wa] <= bm_wd;
end
```

### R70（五步目标·第 9 轮）：**P0 位流第一次上板** —— 探针一发就抓到"start 被同一块的默认赋值盖掉"

**怎么读这几个数（这就是探针的价值）**：
- `FRMCTL` bit0=1 → 像素源确实切到了正射（`frm_src` 写进去了）；bit1(done)=0、fills=0；

...

修法：把 `frm_start <= 1'b0;` 挪到**默认值那一组**（`start_pulse <= 1'b0;` 旁边，case 之前）。
（同样的坑之前 `start_pulse` 就是对的 —— 它在默认值里，所以 vision_top 能起帧、正射不能，

### R71（五步目标·第 9 轮）：上板第一帧"4.62 ms 就跑完了" —— 靠**回读寄存器**抓出整帧发黑

**四个数字把问题钉死**：
1. `fills=0` —— 一次 DDR 行填充都没有，可是"帧跑完了"（FLEN 有值、时间还很稳）；
2. `C0C1=0x00300050` —— c0=80 ✓ 但 **c1=0x30=48**（写的 560 变成了 48）；

**根因（两处，都在"位宽/打包"这一类上 —— R7 由点及面）**
- `vision_ortho` 的 `c0/c1/r0/r1` 端口写成 **`[8:0]`（9 位）**，而 `c1=560 > 511` 装不下。
  Verilator 里 tb 直接把 560 塞进 9 位字段、表达式取低位 → 48；真硅上同样截断。
  ⇒ `band=(c<C0)||(c>=C1)` 恒真 → **整帧发黑**，而帧长/CRC/时间全都"自洽"。
- `vision_axi` 里我把 c1 打包在 `w_masked[24:16]`（9 位），本意就是 9 位 —— 同一类错。

⇒ 这不是硬件错，是**探针缺只读口**；下一轮补（读译码里加这几个寄存器）。

**根因（真 bug）：`out_sof` 的语义错了。**
`vision_top` 的 `din_sof` 是**帧开始**（收到就 `wr_row<=0, wr_col<=1`），行靠 `din_eol` 推进；
而 `vision_ortho` 把 `out_sof` 做成了**每行行首**。于是每行都被打回第 0 行 → 永远收不满。
（`tb_ortho` 只比像素值、不查 sof/eol，所以本地一直没暴露；这正是"本地没有集成 cosim"的代价。）
修法：`out_sof <= (ocol==0) && (orow==r0)`，即**整帧第一像素**才拉高；`tb_ortho` 的断言同步改。

**修后**：`wr_row` 从 0 → **38**（行开始正常推进），但帧仍超时，新现象：
```
正射侧: src_line=94 src_px=36 tag=0x003e(62) fill_state={F_RX,ip=0,ph=0}
        flags={fill_busy=1,fill_done=0,axi_busy=0,axi_done=1,fstate=S_FILL}
        miss_line=94 fills=168
```
即：**主口已经跑完 burst（axi_done=1、axi_busy=0），而行缓存还在 F_RX 等 beat**；
tag 停在 62 而请求是 94 ⇒ 填充完成却没把 tag 写成 94（或 beat 少收了）。
同一版 RTL 在**没有 `hold`** 的 `tb_ortho_sys` 里仍然 **376 次填充、逐字节 0 相符 PASS**
（刚复跑确认）⇒ 嫌疑集中在 `hold`（`vision_axi` 里 `hold=~vision_top.busy`）对
"miss→填→命中"这条握手的时间线影响。

**下一轮第一件事（仍纯本地）**
在 `tb_p0` 里把 `hold` 强制接 0（或给 `vision_ortho_sys` 一个 `--hold0` 旁路）跑一遍：
- 若 0 相符 ⇒ 确认是 `hold` 引起，再查"冻结期间 cache 的 req/fill_start 时序"，修好后再上板；
- 若仍错 ⇒ 与 `hold` 无关，改查 `linefill` 的 `fill_line`/`tag` 写入口径（`fb` 那条：tag 停在旧值）。

### R80（新目标第 1 轮·续）：`hold` 洗清嫌疑；死锁点定位到 **"tb 的 AXI 从机认为 burst 已完，主口还在等 beat"**

**实验 1：`hold` 不是原因**（新增 `vision_axi` 参数 `HOLD_BYPASS`，默认 0，不影响综合/位流）
`-GHOLD_BYPASS=1` 把 `hold` 强制接 0 重跑 `tb_p0`：**结果一字不差**（wr_row=38/col=80、tag=0x3e、
fills=168、同样死锁）⇒ 与 `hold` 无关。（这条参数留着，后面定位冻结时序时还用得上。）

**实验 2：加"主口空闲才发 start"的守卫**（`vision_linefill`：`if (req && lc_miss && !m_busy)`）
死锁**照旧** ⇒ 不是"start 被丢"。

**实验 3：把 AXI 从机状态打出来（决定性）**
死锁时每 200k 拍采样：
```
AXI: ar_issued=0  ar_addr=0x2b980(=93*1920)  ar_len=239  r_phase=240  r_beats=12240
     m_rvalid=0   m_rready=1
正射: line=94 px=36  tag=0x003e(62)  flags={m_busy=1, fstate=S_FILL}  fills=168
```
即：**从机已经把这次 burst 的 240 拍全给完了（r_phase=240 > ar_len=239），而主口还 busy、
行缓存还张着嘴等 beat（m_rready=1、m_rvalid=0）**。两边 beat 记账对不上 ⇒ 死锁。
（51 个 burst × 240 = 12240 ✓ 从机侧自洽；所以差异在主口那一侧。）

**下一轮第一件事**：给 `vision_axi_master` 开一个只读调试口（`dbg_left`/`dbg_state`），
在同一死锁点打出主口的 `left` 与状态，直接看"它以为还剩几拍"。三种可能一次分清：
1. `left` 被一次**迟到/重复的 start** 重装过（S_IDLE 才装，故要查 start 时序）；
2. `m_rlast` 与 `left==1` 两套判定在最后一拍冲突（`if (m_rlast || left==1)`）；
3. 从机被 AXI-Lite 的读写"借走"了某一拍（`tb_p0` 的 `axi_read` 与 `tick` 交错）。

**门禁状态**：`tb_ortho_sys`（无 vision_top）仍然 **376 次填充、逐字节 0 相符 PASS**；
`tb_p0` 仍 FAIL（死锁）。lint 全树 0 告警。

### R81（新目标第 2 轮）：死锁的读数收敛到"主口 S_DATA/left=240 而 AR 只握过 51 次"

新加只读口（`vision_axi_master` 的 `dbg_left/dbg_state` → `FRMLINE` 低 18 位：
`{miss_line[15:2], left[15:0], state[1:0]}`，tb 用 `left=(d>>2)&0xFFFF`、`state=d&3`）。

死锁点实测：
```
AXI: ar_issued=0 ar_addr=0x2b980(=93*1920) ar_len=239 r_phase=240 r_beats=12240  m_rready=1 m_rvalid=0
主口: state=2(S_DATA) left=240          ← **一整拍都没吃**
正射: line=94 px=36 tag=0x3e flags={m_busy=1,fstate=S_FILL} fills=168
AR 轨迹（TRACE_AR）：51 个 burst 全部"AR#n → 240 拍 → 完"，每个约 940 拍，最后一拍完于 cyc≈86777
```
矛盾点很干净：**主口在 S_DATA 且 `left` 是初值 240（一拍没吃），但从机侧 51 个 burst 每拍都握手了、
`r_beats=51×240` 自洽**。⇒ 主口那次 `left<=beats` 的装载与从机认的那次 AR 不是同一件事。
嫌疑收窄到三处（下一轮按这个顺序查，都不用重建位流）：
1. `left` 的装载条件（`S_IDLE && start`）与 `beats` 的取值 —— 加 `dbg_beats` 与 `dbg_arlen` 对齐看；
2. `m_arlen` 与 `m_beats` 是否在同一拍被写（`S_IDLE` 里 `m_arlen<=beats[7:0]-1` 与 `left<=beats`）；
3. `st` 是否可能跳过 AR 直接进 S_DATA（`S_IDLE -> S_AR` 之外还有没有别的入口）。

**本轮之后仍成立的门禁**：`tb_ortho_sys` 376 次填充、逐字节 0 相符 PASS；`tb_p0` FAIL（死锁）；

### R82（新目标第 3 轮）：**P1 解决** —— 两个 bug（一个 RTL、一个测试台），P0 全链路本地逐字节 PASS

**① 真 RTL bug：`out_sof` 语义**
`vision_top` 的 `din_sof` 是**帧开始**（收到就 `wr_row<=0, wr_col<=1`），行靠 `din_eol` 推；
`vision_ortho` 却把 `out_sof` 做成**每行行首** ⇒ 每行被打回第 0 行、永远收不满。
修：`out_sof <= (ocol==0) && (orow==r0)`；`vision_camadapt` 里同样的错一并修
（`out_sof <= (ocol==0) && !row0_done`，用 `row0_done` 记住第一行已过）。
`tb_ortho` 的 sof/eol 断言同步改成"帧首/行尾"口径。

**② 测试台 bug（这才是那个"死锁"的真身）**
`tb_p0` 的 AXI 从机把**握手结算**（AR 捕获 + `r_phase` 清零）写在了"驱动"函数里，
而那个函数会在"轮询寄存器"的路径上被**同一拍调用两次**（外层一次 + `axi_read` 的 step 一次）
→ 同一个 AR 被捕获两次、`r_phase` 被重复清零 → 主口/从机 beat 记账错位 → 死锁。
它伪装成 RTL 问题：`主口 state=2 left=240`（一拍没吃）而 `从机 r_beats=51×240` 完全自洽。
修：驱动拆成 `slave_comb()`（无副作用，可多次调），握手结算只在 `tick()` 里做一次。
（R7 教训：**先把"量具"和"被测物"分开**；这次要不是先把 `left` 打出来，会一直怀疑 RTL。）

**③ P0 全链路（DDR → 寄存器 → 正射 → camadapt → vision_top → 几何帧）本地逐字节 PASS**
```

cam_01: 同上（另跑一遍确认）
```
20.14 ms = 正射(14.75) + camadapt + vision_top 打包，**远低于 35 ms 预算**（且这是串行口径）。
`pytest test_ortho+test_cosim+test_rtl_contract`：新增 `test_p0_integration_bit_exact`（两帧参数化）。

**④ P3 已接线**：`vision_axi` 里 `正射 → vision_camadapt → vision_top`，
`flush` 由 `of_done` 粘滞（把缓冲里最后 <=41 个像素吐完），`frm_start` 清。
C 参考侧 `tb_p0` 现在先对页面图做同一套适配再算几何帧（否则比的是两条不同的链）。

**门禁状态**：50 passed（含 p0 集成两例）；lint 全树 0 告警。

### R84（新目标第 4 轮）：**板上"看不见墙"的真凶 = AXI 地址没加 FRMBASE**

3. 回看 AXI 轨迹：`AR addr=0x2b980`（= 93×1920），**没有加相机帧基址**；而 PS 侧

本地复验：`FLEN=292、不符 0/292、row_count[359]=197`、20.14 ms，PASS（与非零基址前一致）。
