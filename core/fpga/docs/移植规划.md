## 0. 结论摘要

1. **项目已有的硬件边界只管"避障"，不管"视觉"。**
   `interface/protocol.py`（状态帧 v3）+ `fpga/prediction_block.py`（预测帧 `BHP1`）
   定义的是 `State → FPGA → 风险栅格 → CPU → Action`。
   视觉链路（像素 → 几何）**完全不在这个边界里**，必须新增一段契约。
2. **移植的动机是一个 4.5 倍的缺口**：相机能给 30 fps（32.8 ms/帧），
   而纯 Python 全场识别要 **~150 ms/帧**（≈6.7 fps）。硬件要补的就是这 4.5 倍。
3. **板子很宽裕，约束不在容量而在时延。** 9.3 Mb BRAM（≈1.19 MB）**放得下**整帧灰度
   （300 KB，25%）和三张掩膜（115 KB，10%）；PL 还有 400 个 DSP、4 路高速收发器。
   所以选流式不是因为"存不下"，而是因为**少一次整帧往返就少一段时延**（见 §2.1 订正）。
4. **参考库里有四件直接可用**（见 §5）：Verilator 仿真流程、BRAM 双缓冲 + 3×3 卷积 RTL、
   BMP 流式 testbench 写法、纯 C 的 AprilTag。
5. 分 6 阶段，P0–P2 **不依赖板子**就能把大部分风险消掉；板子已到，P3 之后随时可走。
   **P0–P2 已完成**：线协议跨语言冻结（`standard/vision/vision_frame.py` +
   `rtl/vision_pkg.vh`）、C 参考模型与 Python 对账通过（缺口中心 max 0.16 px）、
   **RTL 与 C 参考模型在 320 帧真实录像上逐位一致（2.2 亿次比对零差异）**。
   没做的是综合/时序报告与相机通路，都要等上板（见 §6）。

**工具链已确认**（来自官方资料 `docs/resource/2026嵌赛FPGA开发/20260916/30TAI使用教程.pdf`）：

| 环节 | 工具 | 关键事实 |
|---|---|---|
| PL 综合/实现/位流 | **Vivado 2018.03** + `JFM_Kits` 时序库 patch | 器件按 **`xc7z030ffg676-2`** 直接选 —— 就是 Xilinx 器件名 |
| PS 侧（BSP/固化/烧写） | **Procise 2025.1.1** | `Create Image` 生成 BOOT.bin |
| PS 应用交叉编译 | **Icraft 3.XX + CustomOp 3.XX** | 官方明确：**不要在板载系统上编译** |
| 启动镜像 | `BOOT_Gen/7030ai_psin.bif` + 位流 | 改 bif 里的路径（**不能出现反斜杠**） |

**三个必须写进流程的坑**（否则会在综合/启动阶段卡住）：
1. Vivado 里要**关掉 IP cache**，且每个 IP 必须 **Out of context per IP** 单独综合（不能 Global/Skip）；
2. TCL 里依次执行 `source $::env(JFM_PATH)/ip_patch/run.tcl` → `add_hook_tcl_to_prj`
   → 首次用 30TAI 还要 `replace_7z030ai_file` 加载时序库；
3. 生成位流**直接点 Generate Bitstream**，跳过 Run Synthesis/Implementation（官方注明按顺序点会有问题）；
4. 换 BOOT.bin 必须**先 mount**：SSH 到板子 root，`mount /dev/mmcblk0p1 /root/bits` 后再替换、`reboot`。
   **不挂载就直接拷进去，位流不生效**（这是个静默失败）。

**另外两个大利好**：
* **PL 侧就是 Xilinx 器件**（`xc7z030ffg676-2`），所以参考项目
  `docs/repo/fpga/FPGA_image_process`（**Vivado 2018.4**）的工程组织、IP 用法、BMP testbench
  几乎可以**直接借鉴**，版本只差 0.01。
* 官方 demo `fpai_demo_app/examples/1_single_input+ai/PLin+SingleNet+HDMI` 是一条
  **已跑通的「摄像头 → PL → AI 推理 → HDMI」流水线**，配置在
  `configs/ZG/sdicamera+yolov5+hdmi.yaml`。其中 `pipeline.camera.vtc=true` 用 **PL 内部测试图形
  发生器（VTC）**，`false` 用 **SDI 摄像头** —— 也就是说**没有相机也能先把 PL 通路跑起来**。

**PS 侧 Linux**：官方镜像 `docs/resource/icraft_v3_ubuntu20.04_aarch64_sd_image.7z`（4.2 GB），
Ubuntu 20.04 aarch64，SD 卡启动，SSH 登录账户 root。

## 1. 现状与差距（全部是本项目的实测值）

| 量 | 实测 | 出处 |
|---|---|---|
| 相机 640×480 MJPG | **~30 fps（32.8 ms/帧，纯 `read()`）** | `docs/vision/live_view.md` |
| 全场识别（绝对阈值，纯 Python） | **~150 ms/帧** | `docs/vision/README.md` |
| 全场识别（自适应分类层） | ~450 ms/帧（约 10×） | `docs/vision/adaptive.md` |
| 相机时延 | 中位 66.7 ms、抖动 33.7 ms、时戳量化 ~32 ms | `docs/vision/align.md` |
| 录像时间轴漂移 | 实测 **1.37%/秒**（掉帧，封装仍写均匀时戳） | `docs/vision/reconcile.md` §3.2 |

**由此得到的预算是硬数字**：要跟住 30 fps，一帧的总预算 33.3 ms。
其中相机 ~33 ms 已经吃满 → 必须**流水线化**（采第 n+1 帧的同时算第 n 帧），
否则无论 PL 多快都只能到 30/2 = 15 fps。

| 分项 | 预算 | 说明 |
|---|---|---|
| PL 像素处理 | **≤ 10 ms/帧** | 640×480 → ≥ 31 Mpixel/s 吞吐 |
| PL→PS 链路 | ≤ 5 ms | 一帧几何结果只有几百字节 |
| PS 定位 + 决策 | ≤ 10 ms | 单应 + `gap_avoid.plan()`（纯 stdlib，实测远快于此） |
| 相机采集 | 33 ms，**与上面并行** | 双缓冲/乒乓 |

## 2. 硬约束：先算清楚再谈架构

### 2.1 BRAM / 存储预算（**已按实际板卡订正**）

实际 PL BRAM = **9.3 Mb ≈ 1190 KB**（265 × 36 Kb）。下表按此重算：

| 数据 | 大小 | 占 BRAM | 能否进片上 |
|---|---|---|---|
| 三掩膜 1 bit（640×480） | 115.2 KB | 9.7% | ✓ |
| 单掩膜 1 bit | 38.4 KB | 3.2% | ✓ |
| 3 行灰度行缓冲（3×3 卷积） | 3×640×8 bit ≈ 15 KB | 1.3% | ✓ |
| **灰度整帧 8 bit** | **300 KB** | **25%** | **✓ 也放得下** |
| 灰度 + 三掩膜 + 行缓冲 | ≈ 430 KB | 36% | ✓ 仍有余量 |

**订正说明**（写下来是因为它改变了取舍理由）：规划早期按"中小板卡 BRAM ~1 Mbit"
假设，结论是"整帧灰度放不下，**被迫**流式"。实际板子是 9.3 Mb，**容量不再是约束**。
但**仍然选流式**，理由换成两条更实在的：

1. **少一次整帧往返就少一段时延** —— 预算只有 33.3 ms/帧（§1），
   写满一帧再读出来是 2 次 300 KB 的 BRAM 访问，白白吃带宽与时延；
2. **不需要整帧** —— 我们全部算子里没有一个是"需要看到任意行"的：
   列投影按行累加、扫描线 CCL 只需要**上一行**的等价类、3×3 卷积只需要 3 行。
   留一整帧只是把"没用到的东西"存起来。

所以照旧：**行缓冲 + 掩膜 + 乒乓**。但这条现在是**优化选择**，不是**被迫妥协** ——
如果以后某个算子确实需要回头访问整行/整帧（例如做稠密连通域或形态学），
在这个板子上**可以直接加整帧缓冲**，不用改架构。

### 2.2 带宽（PS↔PL 已无风险）

- 摄像头原始：640×480×8 bit @30 fps ≈ **74 Mbit/s**（灰度）；24 bit 彩色 221 Mbit/s。
  → **在 PL 侧就转灰度**，别把彩色传进 PS。
- PL→PS 几何帧：几十条记录 × 16 B ≈ **几百字节/帧 → < 0.1 Mbit/s**。
- **PS↔PL 通道：4× 高速 AXI 64-bit + 8 路 DMA**（§0.5）→ 就算把整帧灰度
  （74 Mbit/s）或整帧彩色（221 Mbit/s）搬过 AXI 都毫无压力。
  真正要守的是"**别整帧搬**"这条设计纪律，而不是带宽不够。

**其余片上小表**（都很小，不构成约束）：CCL 行等价表 640×16 bit ≈ 1.3 KB；
列/行投影直方图 640×16 bit + 480×16 bit ≈ 2.2 KB。

### 2.3 定点误差预算（对应 `core/cpu/docs/CPP_PORT.md` §4）

现有的纪律是：`usable_half` 的定点误差 ≤ `0.1 × margin`。视觉侧照抄同一条思路：

| 量 | 定标建议 | 依据 |
|---|---|---|
| 像素 / 掩膜 | `uint8` / 1 bit | 原生整数，无误差 |
| 行/列计数 | `uint16`（最大 640 / 480） | 无溢出 |
| 质心一阶矩 `Σx, Σy` | `uint32`（最大 640×307200 ≈ 2e8） | 无溢出 |
| 质心二阶矩 `Σx², Σxy` | `uint48` 或分块累加 | 最大 ~1.3e11，需 >32 bit |
| 亚像素补偿 | `int32`，以 1/256 像素为单位 | 与整数除法配合 |
| 场地坐标 | `S20.12`（1/4096 单位 ≈ 0.00024） | 缺口中心误差目标 ≤0.1 场地单位 |
| 单应矩阵 | `S16.15`，9 个系数 | 与 `CPP_PORT.md` §4 的坐标定标一致 |

**验收口径**：`缺口中心误差 ≤ 0.1 × 缺口半宽`（半宽 30 单位 → 3 单位），
否则会出现"该过的缺口判成过不去"（`CPP_PORT.md` §4 已经指出这个失效模式）。

## 3. PL / PS 划分

原则：**逐像素、可并行、无分支依赖 → PL；需要浮点/三角/全局优化/协议 → PS。**

| 阶段 | 现有实现 | 放哪 | 依据 |
|---|---|---|---|
| 采集 | `vision/capture.py`、`capture_one_frame.py`（V4L2） | **PL**（并行口/MIPI）或 PS（USB） | **选板第一决定因素**，见 §7 |
| 彩色→灰度 | `primitives.py` | **PL** | 逐像素加权和 |
| 三路分类（wall/bright/green） | `primitives.classify` | **PL** | 3 个比较器/像素，纯并行 |
| 墙列统计 + 边沿分支 | `wall_with_gap.detect_walls` | **PL** | 列投影 + 阈值，流水线累加 |
| 缺口提取（分带/两段闭区间） | 同上 | **PL** | 行带内相邻段判断，整数 |
| 连通域 + 填充率/长宽比 | `scanline_blobs` + `detect_player` | **PL** | 扫描线 CCL + 并行累加器 |
| 圆亚像素精修 | `subpixel.refine_circle` | **PL** | 一阶/二阶矩，整数累加后一次除法 |
| 单应 → 场地坐标 | `localize.to_world` | **PS** | 每帧只有几十个点，浮点 3×3 更省事 |
| 标定（ArUco/AprilTag 解算） | `vision/calibration.py`、`fiducial.py` | **PS** | 一次性；用 `cpu/apriltag`（纯 C）替代 `cv2.aruco` |
| 缺口跨帧身份 / 运动 | `vision/identity.py`、`motion.py` | **PS** | 关联与滤波，数据量小 |
| `gap_avoid.plan()` | `core/cpu/gap_avoid.py` | **PS 先落，后议上板** | 674 行全 double；定点化是独立一大步（`CPP_PORT.md` §4） |
| 渲染 / 可视化 | `render/`、`vision/live_view.py` | **PS（仅开发）** | 不参与交付 |

**一句话**：PL 负责"像素 → 几何"，PS 负责"几何 → 决策"。分界线画在
**单应变换**上 —— 它左边全是整数/位运算，右边才有浮点与全局逻辑。

## 4. 接口契约：复用已有纪律，补一个缺件

项目已经有一套**很好**的帧纪律（`interface/protocol.py`），视觉侧要照抄：

```
magic(uint32) | version(uint16) | flags(uint16) | step/seq(uint32) | n_records(uint32)
| 定长记录 × n | crc32(uint32)
```
- 小端、**定长步长**、每条记录字段固定；
- **CRC32 覆盖全部前置字节**；
- `frame_size(n)` / `describe_protocol()` / 「超版本拒绝」三件套齐备；
- 解码后立刻校验，非法即抛，绝不"猜着读"。

**缺件（必须新建）**：`core/standard/vision/vision_output.py` 的 `VisionFrame` 目前
**只有 `to_dict`/`from_dict`（JSON）**，没有二进制编解码 —— 而 PL 不可能吐 JSON。

**待办 P0-a**：新增 `core/standard/vision/vision_frame.py`

```
encode_vision_frame(VisionFrame) -> bytes
decode_vision_frame(bytes) -> VisionFrame
vision_frame_size(n_obstacles, n_gaps) -> int
describe_vision_protocol() -> dict
```
记录类型与现有 `GapObs` / `PlayerState` / `Obstacle` 一一对应，
定点/浮点的选择由 `units` + `flags` 表达（和状态帧同一套做法）。

**验收**：`encode → decode` 往返逐位一致；篡改 CRC 必须报错；
`frame_size` 与文档中的字节表一致（照 `test_standard.py` 的现有做法）。

## 6. 分阶段计划

**P0–P2 不依赖开发板**（板子已到，但先把能离线消掉的风险消掉，这是本规划的核心判断）；
**P3 起随时可走**。

### P0 冻结接口（板卡已定，无需板）
- **已完成**：板卡与相机事实（§0.5）、逐条核对（§7）。
- **工具链已确认**（§0.5 表：Vivado 2018.03 + JFM_Kits + Procise 2025.1.1 + Icraft）。
  剩下与代码无关、需上板才能做的一件：**JTAG/SD 烧录流程实操**（文档已有，见 §0.5 第 4 条坑）。
- **产出**：
  1. `core/standard/vision/vision_frame.py`（§4 的缺件）+ 测试；
  2. 视觉链路的**算子清单与吞吐表**（每个算子：输入/输出位宽、每像素运算数、可否并行）；

- **验收**：`encode/decode` 往返逐位一致；算子清单里每个算子都有"PL/PS + 位宽"两栏，
  没有一项写"待定"。

- 用 **C**（不是 Python）写，因为 C 模型和 RTL 才是逐位可比的；
  Python 版本留作"语义真值"，用真实录像比对两者。
- **产出**：`core/fpga/ref/vision_ref.c`（+ `ref_api.h` 协同仿真接口 + Python 对照测试）。
- **验收结果**（`data/vision/run4/screen.mp4`，两套不重叠的彩色激励各 40 帧）：
  - 缺口中心误差 **中位 0.00 px / max 0.00 px** ✓；
  - 缺口条数与墙段条数**逐帧完全一致**（160/160、320/320 与 300/300、605/605）；

    亚像素圆拟合 vs 连通域矩质心的**估计器差异**，不是 bug（另见"还没决定"）；
  - 单线程 C 跑 320 帧 ≈ 1.0 s（远超 30 fps）✓。
- **⚠ 上板必须记住**：Python 的 `WallWithGapParams.rescaled(w, h)` 会按分辨率
  缩放长度/面积类参数（640×360 → s=0.75）。**PS 必须算好缩放后的参数写进
  配置寄存器**，做 0 次或 2 次都会错（两种都踩过）。

> **⚠ 一处规划订正**：原文写"流式、无整帧存"。实测 PL BRAM 9.3 Mb ≈ 1190 KB，
> 灰度 300 KB + 两张 1 bit 掩膜 77 KB ≈ 32%，**存整帧是允许的**。
> C 模型与 RTL 都改成"存整帧 + 多遍回读"，把算法语义保持得和 Python 一致；
> 真正的单遍流式版留到需要压时延的时候再做（见 §2.1）。

## 7. 板卡已定：逐条核对结果

原先的选板判据，现在对**复旦微悟净 PSOC Lite（JFMQL30TAI676H）**逐条核对：

| # | 判据 | 实际情况 | 结论 |
|---|---|---|---|
| 1 | 相机接口能否直连 PL | USB2.0 HOST 在 **PS** 侧（4 路 Type-A）；PL 另有 **MIPI CSI J16**（2 lane，BANK12）与 **2 路 SDI 输入** | ⚠ **当前方案（USB 相机）相机挂 PS**，不是最省时延的路径；见下面的取舍 |
| 2 | BRAM 够不够 | **9.3 Mb（1190 KB）** vs 需要 115 KB | ✓ 余量 10 倍 |
| 3 | 综合工具链可得 | 手册是硬件手册，**未提及工具链名称/版本** | ⏳ **待跟厂商确认**（P0 必办） |
| 4 | PS 侧能跑 Linux | 官方 demo 含 Linux 开发；PS 四核 1 GHz + 1 GB DDR3 | ✓（内核/USB UVC 支持仍待确认） |
| 5 | PL↔PS 带宽与 DMA | **4× 高速 AXI 64-bit + 8 路 DMA** | ✓ 远够 |
| 6 | 调试与可复现构建 | JTAG（PS/PL 各一）+ USB-UART + SD 卡启动 | ✓ 可用；构建脚本要我们自己固化成脚本 |

### 7.1 相机路径的取舍（**已按官方 demo 更新**）

你定的是 **USB 相机**（挂 PS）。但官方 demo 揭示了一条**验证过的 PL 直连路径**：

| 方案 | 路径 | 优点 | 代价 |
|---|---|---|---|
| **A（你定的）USB 相机** | 相机 → PS(USB2.0) → 内存 → PL（AXI/DMA） | 相机现成、Linux UVC 生态好、`core/vision` 的 V4L2 代码几乎直接可搬 | 多一次拷贝；USB 只有 ~30 fps（实测 32.8 ms/帧）；时延多一段 |
| **B SDI 相机** | 相机 → PL（2 路 3G-SDI 输入） | **官方 demo 就是这条**（`sdicamera+yolov5+hdmi`），PL 侧 SDI 接收已由厂商跑通 | 要 SDI 相机（工业相机，贵） |
| **C MIPI 相机** | 相机 → PL BANK12（CSI J16） | 少一次拷贝、可更高帧率 | 要买模组；CSI-2 接收要自己写或抄 demo |
| **D 先不接相机** | **PL 内部 VTC 测试图形** → PL 流水线 | 官方 demo 里的 `vtc=true` 分支；**没有相机也能把 PL 通路跑起来** | 只是测试图形，不是真实场景 |

**建议的顺序**：P0–P2 与相机无关（已完成）→ **P3 先用我们自己的 `vision_selftest`
（几何手算得出来，比借官方 VTC 更强：借来的图案只有"有没有图像"，我们的图案
连缺口中心、角色质心都有确定答案）→ P3/P4 再用 D 把相机通路点亮**（借官方 VTC 分支，
零相机成本）→ 再用 A（你的 USB 方案）跑真实闭环 → 若时延或帧率不够，再考虑 B/C。

这样做的好处是：PL 侧的算子与相机来源**解耦**（只要先定义好"像素流"这一层接口），
D→A→B 换的都是前端，不是算法。

## 8. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| **整帧存灰度** | 放不进 BRAM，被迫降分辨率 | §2.1 已定死：流式 + 只存掩膜/行缓冲；P1 的 C 模型必须先按这个形状写 |
| **定点误差吃掉缺口判据** | "该过的缺口判成过不去" | §2.3 的误差预算 + P1 逐帧比对；先量化再定点 |
| **流水线没做，只做了加速** | 30 fps 相机只能到 15 fps | P1 就按 ping-pong 设计；预算表 §1 已把采集与计算并行写明 |
| **相机接口板相关** | P4 返工 | 选板第 1 条判据；P0 先定 |
| **时戳/掉帧** | 速度、对齐全错（已实测 1.37% 漂移） | 帧里带 `seq` + 硬件时戳；沿用 `docs/vision/reconcile.md` §3.2 的检测方法 |
| **把 ROS2 引进来** | 丢掉"可逐条翻成 Verilog"的最大优势 | `cpu/navigation2` 只作参考，不进交付（§5） |
| **只对少量帧比对** | 边界帧的 bug 溜过去 | P2 要求 ≥300 帧逐位一致，且激励用真实录像而非合成图 |

## 9. 明确**不做**的

1. **不引入 ROS2 / OpenCV 到板端数据通路**（参考项目只用来借方法）。
2. **不把彩色整帧传进 PS**（§2.2）。
3. **不猜板卡协议**：链路/寄存器/字节序/握手一律留 `[HARDWARE_INTERFACE_TBD]`，
   填在 `PlannedTransport` 一处。
4. **不在 P0–P2 之前动 `gap_avoid.py` 的定点化** —— 那是独立一大步
   （`CPP_PORT.md` §4/§5 已有顺序），和视觉移植并行但不耦合。
5. **不做"整帧图像传给 PS 处理"**的方案：那等于把 FPGA 当搬运工，
   实测 33 ms 的采集预算会被吃光。
