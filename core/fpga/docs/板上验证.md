## 1. 2026-10-13 · 首次上板：PL-only 自检位流跑通

### 1.1 结论

```
board_selftest.bit   5,980,028 B
Slice LUTs 12,174 / 78,600 = 15.49%      Block RAM 82.5 (31.13%)
All user specified timing constraints are met
JTAG 烧写 → PROGRAM_OK
板上现象：led[0] (J1) 与 led[1] (M6) **都在闪，频率约 2~3 Hz / 1 Hz**
```

### 1.2 这条位流里跑的是什么

**原封不动的 `vision_selftest`**（`auto_run=1` 自转）：

```
vision_tpg（手算得出几何的合成图案）
    → vision_top（视觉流水，被 320 帧合成 + 32 帧真实照片逐位对账过）
    → 几何帧字节流
```

**不依赖相机、不依赖 PS、不需要标定。** 帧源只是从"外部像素"换成了片上图案发生器，
流水线本身一个字节都没改。

顶层 `core/fpga/rtl_board/vision_board_top.v` 只做三件事：
IBUFDS + MMCM（200 → 50 MHz）、上电复位、把两个状态引到 LED。

| LED | 引脚 | 含义 |
|---|---|---|
| `led[0]` | J1 | 自由计数器最高位，约 2~3 Hz —— **时钟 / MMCM / 逻辑活着** |
| `led[1]` | M6 | 每 32 个 `frame_done` 翻转一次，约 1 Hz —— **一帧真的从头跑完了** |

`COOLDOWN = 200000` 拍，一帧约 `5.6e5 + 2e5 = 7.6e5` 拍 ⇒ 50 MHz 下约 **66 fps**
⇒ `led[1]` 约 66/64 ≈ **1.03 Hz** ✓ 与实测一致。

### 1.3 能证明什么

* MMCM 200→50 MHz 锁定、复位释放正常；
* **综合后的电路在真硅上把一帧从头跑到尾，而且连续跑**（`frame_done` 反复触发）
  —— 没有死锁、状态机走得到 `S_PACK`/`S_DONE`；
* 帧存的三块 BRAM 在硅上按预期工作（否则流水线读不到像素，走不完一帧）；
* 时序约束（50 MHz）在真实器件上成立。

### 1.4 ⚠️ 证明不了什么（重要）

**LED 只证明"帧跑完了"，不证明"帧的字节是对的"。**

流水线的**几何输出**（墙段 / 缺口 / 角色那 9×n + 表头字段）在真硅上是否与协同
仿真逐位一致，这条位流**没测**。真硅上仍可能出问题的地方至少有两类：

1. **BRAM 推断/映射与仿真不同**（综合把 `gray_mem/wall_mem/bright_mem` 映射成
   80 个 RAMB36 + 5 个 RAMB18，读写时序与 Verilator 的行为模型不完全等价）；
2. 时序虽收敛（WNS 为正）但**跨时钟/复位边界**的行为差异。

要证到字节级，必须把几何帧**读回来**比对。三条路：

| 路 | 做法 | 代价 |
|---|---|---|
| **A. 片上 CRC 自检** | 顶层对流出的几何帧字节算 CRC32，与协同仿真里算出的常数比较，一致就让 `led[1]` 常亮（不闪） | 加约 40 行 RTL + 一次协同仿真取常数。**不需要 PS、不需要 ILA** |
| **B. ILA** | 综合后插 `create_debug_core` + `connect_debug_port`，从 JTAG 抓 `frame_done/busy/cur_frame_idx/dout_*` | 能看到过程，但深度 1024 抓不下整帧，只能抽查 |
| **C. 走 PS** | PS 起来后经 AXI 读帧窗口，和协同仿真的期望字节逐位 diff | 最强（整帧逐位），但要等 PS 系统可用 |

**A 是这个阶段性价比最高的一步** —— 它把"LED 说跑完了"升级成"**跑出来的字节和
协同仿真一样**"，而且完全不依赖 PS 和相机。

### 1.6 这一轮踩到的坑（都值得记住）

| 坑 | 现象 | 解法 |
|---|---|---|
| `create_ip` 在纯 non-project batch 下 | `ERROR: [Common 17-53] No open project`，**11 秒就退出** | 建 `create_project -in_memory`；但注意 in-memory 项目里生成的 IP **又进不了** `synth_design`（`Synth 8-439 module 'ila_0' not found`） |

| 板子没上电 | 连续 5 次扫描都是 `all zeroes`，看起来像硬件坏了 | **先确认板子电源**。上电后立刻恢复 |

### 1.7 顺带确认的一件事

`vision_axi` 的 135 个端口**真实部署里来自 PS7**（AXI-Lite 从口 + `din_*` 视频输入），
**不是外部引脚**。所以拿它直接出位流会被 DRC 挡下：

```
ERROR: [DRC NSTD-1] 135 out of 135 logical ports 无 IOSTANDARD
ERROR: [DRC UCIO-1] 135 out of 135 logical ports 无 LOC
（`ZPS7-1 PS7 block required` 只是 WARNING）
```

**不要**把这两条降级成 Warning 去换位流 —— 那会让 FPGA 驱动 135 个电平未定义的
引脚，**可能烧板**。正路是把端口收敛（本文件的做法），或者做 PS7 块设计让它们变成
内部连接。

## 2. 片上逐位自检（CRC32）—— 代码已就绪，等一轮重建 + 上板

### 2.1 思路：**不需要在片上实现 CRC**

几何帧的**最后 4 个字节本身就是 `vision_top` 打包时算的 CRC32**（小端）。
所以板上只要把每帧的「字节数 + 这 4 个字节」与协同仿真里提取的常数比一比，
就能证明"真硅跑出来的字节 = 仿真里那份"。CRC32 撞上不同内容的概率 2⁻³²。

比在片上再实现一遍 CRC32 省事得多，也少一个"我实现的 CRC 对不对"的新风险。

### 2.2 期望常数从哪来

`core/fpga/cosim/tb_tpg.cpp` 里加了一行打印（逐场景收集完字节之后）：

```
EXPECT_SCENE <图案> LEN <字节数> CRC 0x........
```

实测（`./obj_dir/Vvision_selftest 8`，比对项 403 / 不符 0）：

| 图案 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 帧长 | 184（八个一样） |
| CRC32 | `A9670ED9` | `621801BE` | `1EEBDE91` | `0BC5C6CA` | `76D2BFA9` | `C71A351A` | `A5440B40` | `AEC7F26E` |

这 8 组常数**只对 `vision_selftest` 的合成图案成立**（换语料就全变）。

### 2.3 ⚠️ 写这块时抓到的 off-by-one（别再踩）

`vision_selftest.v` 里：

```verilog
auto_start <= 1'b1;              // 第 62 行
auto_idx   <= auto_idx + 16'd1;  // 第 63 行  ← 与上面**同一拍**
...
wire        run     = auto_run ? auto_start : start;   // 第 74 行
wire [15:0] idx_now = auto_run ? auto_idx   : frame_idx; // 第 75 行
```

`auto_start` 是寄存器，所以它在**下一拍**才为 1；而 `auto_idx` 在那一拍**已经加过了**。
⇒ tpg 在 `start` 那拍看到的是 **k+1**，**硬件跑的第一帧用的是图案 1，不是图案 0**。

按"第几帧"（`done_cnt[2:0]`）去索引期望常数会**整体错一位，8 个图案一个都对不上**。

**修法不是补偏移，而是按图案号索引**：`cur_frame_idx` 就是 `idx_now`，而且在
`frame_done` 时**稳定**（下一个 `start` 要等 cooldown）。于是：

```verilog
wire [2:0] pat = cur_frame_idx[2:0];
case (pat) 3'd0: exp_crc = 32'hA9670ED9; ... endcase
ok_mask <= ok_mask | (8'd1 << pat);
```

这样不依赖"第几帧 = 哪个图案"这个推断，换 pattern 顺序也不会错。

### 2.4 另一个容易错的点：同拍

`frame_done` 可能与**最后一个 `dout_vld` 同拍**（`tb_tpg.cpp` 就是先收字节、再看
`frame_done`）。所以判比较时要**把本拍正在送的字节算进去**：

```verilog
wire [15:0] nb_now = dout_vld ? (fbytes + 16'd1) : fbytes;
wire [31:0] tl_now = dout_vld ? {dout_data, ftail[31:8]} : ftail;
```

两种相对时序（同拍 / 差一拍）都要对。

### 2.5 LED 语义（有歧义的都排除了）

| 现象 | 含义 |
|---|---|
| **`led[1]` 常亮** | **八个图案的帧长 + CRC32 全部与协同仿真一致** —— 本次上板目标达成 |
| `led[1]` 约 1 Hz 闪 | 帧在跑，但字节没全对上（或还没跑满 8 帧） |
| `led[0]` 闪、`led[1]` 不亮 | 时钟没问题，流水线卡住 |
| `led[0]` 不闪 | 时钟 / MMCM 没起来（与流水线无关） |

失败是**亮/闪可分辨**的，不会出现"灯不亮分不清是死是活"。

### ⚠️ 但同一读数里有一条对不上，必须复核

同一次读数里 `led[0]`（J1）也被报成"常亮"。而 `led[0] = hb[23]` 是 24 位自由
计数器最高位，50 MHz 下**必然约 3 Hz 方波** —— 它就该在闪；**昨天读的还是"两个都在闪"**。

两者不能同时成立：

* `led[0]` 在闪 → 一切自洽，上面的结论成立；
* `led[0]` 真的常亮 → `hb` 没在计数，但那样就没有 `frame_done`，
  `ok_mask` 恒 0、`frame_tgl` 恒 0，`led[1]` 应该是**灭**的 —— 与"`led[1]` 常亮"矛盾。

（PROGRAM_OK），可以复看。** 复核前，上面的"字节级一致"记为**待复核**。

## 3. 远程读回（ILA）—— 位流已建成，但 JTAG 侧还没打通

### 3.1 为什么做这个

两个 LED 只够回答"跑没跑完 / 字节对不对"，**而且要有人看着板子**。
远程操作时没有观测手段，而 **JTAG 是唯一能远程打通的信道** ——
所以目标是：把 `ok_mask` / `cur_frame_idx` / `frame_done` 插成片上探针，
从 JTAG 读回来，**不需要眼睛**。

### 3.2 三条路都试过，只有第三条能出位流

| 路 | 结果 |
|---|---|
| ① `create_ip` + `synth_design`（**in-memory** 项目） | ✗ `ERROR: [Synth 8-439] module 'ila_0' not found` |

## 4. 2026-10-14 · 真硅上暴露的 AXI 写死锁（RTL 已修，位流待重建）

`vision_axi.v` 里那段告警注释指向本节。

### 4.1 现象：读全对，**一写就挂**

`bd_vision` 位流加载后，用 `/dev/mem` 访问 `0x43C00000`：

- **读**完全正常：配置寄存器逐项读出 `40/110/60/195/45/10/90`，
  与 `VR_DEFAULT_REF_PARAMS` 一致；
- **第一次写就挂**：CPU 直接卡死，板子网络掉线（`No route to host`），
  只有彻底断电才能恢复。复位键无效。

### 4.2 根因：`s_awready`/`s_wready`/`s_arready` 三合一

原实现把三个 ready 全绑在 `idle_all` 上：

```verilog
wire idle_all = !aw_v && !w_v && !b_v && !ar_v && !r_v;
assign s_awready = idle_all;  assign s_wready = idle_all;  assign s_arready = idle_all;
```

主控先给 AW 是**合法且常见**的（AXI 允许 AW 与 W 不同拍），但：

```
主控给 AW → awready=1 → aw_v<=1
下一拍 idle_all 立刻变 0 → s_wready 跟着掉
→ w_v 永远捕捉不到 → wr_commit 永不成立 → bvalid 永不返回 → 总线挂死、CPU 卡住
```

**不是主控不规范，是实现错了。**

### 4.3 为什么协同仿真 11490 项全绿也没抓到

`tb_axi.cpp` 的 `axi_write()` 恰好**总是同一拍**把 AW 和 W 一起给出——
走不到这条路径。**这是把"主控行为"理想化造成的结构性盲区**，
和后面 4.5 的字节选通、以及 §5 的启动竞态是同一类错误。

已给 tb 加 `--w-delay`（**默认 1**），从此"AW/W 不同拍"每次跑测试都会走到。
反向验证：旧 RTL + `--w-delay 1` → 186 项不符 + `✗ 写 CTRL 启动超时`；
旧 RTL + `--w-delay 0` → 通过（正是那个盲区）。

### 4.4 修法

AW/W 各自只看自己那一半，都不与读并发：

```verilog
wire rd_idle = !ar_v && !r_v;
wire wr_idle = !b_v;
assign s_awready = !aw_v && wr_idle && rd_idle;
assign s_wready  = !w_v  && wr_idle && rd_idle;
assign s_arready = !ar_v && rd_idle && !aw_v && !w_v && !b_v;
```

**没有循环依赖**：`aw_v`/`w_v` 只依赖自己的 ready，`ar_v` 依赖全部。

### 4.5 同一轮发现的第二个盲区：配置寄存器块不认字节选通

配置寄存器块（`0x000..0x07F`）写的是
`reg_wdata <= wstrb_merge(32'd0, w_d, w_s)`——**未选通的字节被清零**，
而 `vision_top` 里这些寄存器是**整字写**，所以对 `0x044` 写 1 个字节会把
其余 3 字节静默写成 0；同一个从口上 `SEQ/STAMP` 却是就地 `wstrb_merge`。
`tb_axi.cpp` 又把 `s_wstrb` 恒定为 `0xF`，所以从没走到过。

修法：写提交时只锁存原始 `w_d/w_s`，下一拍（`reg_we=1`）拿 `cfg_rdata`
读该寄存器**旧值**再合并。无循环依赖、无竞争——仲裁保证读写严格串行，
写那一拍不可能有读在飞；整字写下 `wstrb_merge` 恒等，行为不变
（真实照片项数 6498 → 6521，差值正是新增的 23 项自检）。

### 4.6 当前状态

RTL 已修并提交（`36d1eb3`、`07668c0`），协同仿真全绿
（真实照片 6521/0、合成 247469/0、自检 403/0）。
**板上位流尚未重建**——IP 里内嵌了一份 `vision_axi.v` 副本，
必须重跑 `bd_pack.tcl` → `bd_vision.tcl` → `bootgen`，顺序见 §5.4 的同款命令。

## 5. 2026-10-14 · 上电进不去系统的真正原因：没有 udev，白等 90 秒

**这是"板子慢/进不去"的根因，已修复并上板验证。**

### 5.1 症状

上电后长时间连不上：SSH 要 90 秒以上才通，串口看着像卡在
`Getty on ttyPS0`。`systemd-analyze` 实测（修复前）：

```
Startup finished in 7.246s (kernel) + 1min 30.813s (userspace) = 1min 38.059s
```

内核只花 7 秒，**用户态 1 分 30 秒**。

### 5.2 根因

1. 这个厂商 rootfs **根本没装 systemd-udevd**（不是没启动，是连 unit 文件
   都没有）：`systemctl is-enabled systemd-udevd.service` →
   `Failed to get unit file state ...: No such file or directory`。
2. 没有 udev，systemd 永远收不到"设备已就绪"通知，`dev-*.device` 永远不会
   active，也不会立刻失败，而是**干等到默认 90 秒 JobTimeout**。
3. 内核 cmdline 有 `console=ttyPS0,115200n8`，`systemd-getty-generator`
   据此生成 `serial-getty@ttyPS0.service`，而
   `/lib/systemd/system/serial-getty@.service` 里写着
   `BindsTo=dev-%i.device` / `After=dev-%i.device` → 它去等
   `dev-ttyPS0.device` → 等满 90 秒超时。
4. 厂商自己又启了一个 `getty@ttyPS0.service`
   （`/etc/systemd/system/getty.target.wants/` 里的软链），它**没有** BindsTo。
   `systemctl show -p BoundBy dev-ttyPS0.device` 确认**只有 serial 那个**绑它。

**两个 getty 抢同一个串口**，其中一个注定失败，还把 `Reached target
Multi-User System` 卡在超时那一秒。失败那次的时间线：

```
03:28:20 Started Getty on ttyPS0.                        ← 厂商那个，正常
03:29:41 dev-ttyPS0.device: Job .../start timed out.     ← 干等 88 秒
03:29:41 Timed out waiting for device /dev/ttyPS0.
03:29:41 Dependency failed for Serial Getty on ttyPS0.
03:29:41 Reached target Multi-User System.               ← 超时同一秒才到
```

### 5.3 ⚠️ 两个容易误判的点

- **这不是偶发**：每次上电都会发生，只是因为最后总能起来，被当成"板子慢"。
  它会偶发地更糟——驱动探测快于 systemd 时设备已存在，就碰巧不等，是竞态。
- **JTAG 不能当判据**：这块国产克隆片（`JFMQL30TAI676H`）的 DAP 报
  `AXI AP transaction error (DAP status 30000021)`，XSCT **枚举不出
  Cortex-A9**，但板子完全正常。判断死活只能看串口。

### 5.4 修法（已上板，一条命令）

## 6. 位流重建后的上板验证：一条命令 + 两个必须防的坑

### 6.1 为什么顺序是刻意的

`core/board/tools/deploy_and_verify.sh` 按**从最安全到最危险**排：

| 步 | 动作 | 风险 | 证明什么 |
|---|---|---|---|
| 3 | `read_frame 1 --watch` | **零**（不写任何寄存器） | 位流加载成功、AXI 读通路通、地址被译码 |
| 4 | `axi_soak` | **会写**，旧位流上会挂死 | AXI 写死锁 + 字节选通两项修复在真硅上生效 |

关键是第 3 步：它是只读的，所以在**不冒任何风险**的前提下就能先把"位流到底
装进去没有"确认掉。第 4 步的 Phase B 金丝雀先做**单次**配置寄存器写 ——
要挂就挂在那一行，失败点最清楚。

### 6.2 第 3 步的预期结果（不是"失败"）

`--watch` 的预期输出是**"帧计数都没动"**。这不是故障，而是设计使然：

```
$ ./read_frame 1 --watch
帧 0: [--watch] 等了 500 ms 帧计数都没动 —— 没有别的源在启动帧（这是正常的）
```

**已经核实的依据**（不是猜的）：

- `vision_axi.v` 里 `start_pulse` 唯一来源是 `ADDR_CTRL` bit0 的写；
- `rtl_bd/vision_axi_ip.v` **没有任何** start/auto 逻辑；
- `rtl_bd/tpg_source.v` 的输出只有 `din_vld/din_sof/din_eol/din_r/din_g/din_b`
  和 `frame_idx/tpg_busy/tpg_done`，**没有 start 类信号**；
- `synth/bd_vision.tcl` 里 `tpg_0 → vision_0` 只连了 `foreach s {din_vld din_sof
  din_eol din_r din_g din_b}` —— `frame_idx/tpg_busy/tpg_done` **全部悬空**。

所以 `bd_vision` 里**必须由 PS 写 CTRL bit0 才会出帧**。反过来说：`read_frame`
原版"只等 frame_done 翻转、从不写 start"**从来不可能跑通**（§4 的位流第一次
AXI 写就把板子挂死了，所以这个工具此前从未成功运行过）。已在 6.4 修好。

如果哪天真在 `--watch` 下拿到帧，那说明有别的源在启动帧 —— 值得追一下。

### 6.3 坑 A：D: 上会一直留着上一轮的位流，**必须防"烧了旧的"**

`bd_vision.bit` / `bd_vision.bit.bin` 不会因为改了 RTL 就消失。只判断
"文件存在"的话，烧上去的就是**上一轮的旧位流** —— 而它正好含 AXI 写死锁。

所以脚本里有一道守卫：**位流必须比它所依赖的 RTL 新**（另可传 `EXPECT_MD5`
精确校验）。这道守卫当场就生效了：

```
！！位流比 core/fpga/rtl/vision_axi.v 还旧 —— 这是上一轮的旧产物，重建没完成，拒绝烧写
   bin: 2026-10-14 22:20:14    RTL: 2026-10-14 22:44:51
```

没有它，这一轮就会白挂死一次板子（还得物理断电）。

### 6.4 坑 B：kill 掉后台 job，**Windows 的 vivado.exe 会活下来**

`job_kill` 杀掉的是 WSL 侧那个 bash 包装脚本，**Windows 的子进程 vivado.exe
不受影响**。它会一直占着 `bd_prj`，于是下一次 `bd_pack.tcl` 在第 15 行就退出：

```
file delete -force $prj
error deleting ".../bd_prj/bd_prj.runs/impl_1/init_design.pb": permission denied
```

（实测那个 vivado.exe 以 1.4 GB 内存活了 9 个多小时。）
launcher 里已加"启动前先 `taskkill vivado` + 清 `bd_prj`"的清理步骤，并在
继续之前确认目录真的删掉了。

### 6.5 md5 纪律：证明"修复真的进了位流"，而不只是"构建成功了"

重跑 `bd_pack.tcl` 的全部意义就是刷新**内嵌在 IP 里的那份 `vision_axi.v`
副本** —— 漏了这一步，位流看着构建成功，里面却还是旧 RTL。所以每一步都按
md5 对，而不是靠"日志没报错"：

```
源（WSL 侧，已提交）      : 6010cb6bf75be842e817dcb86607a9f0
IP 仓库里的副本           : 6010cb6bf75be842e817dcb86607a9f0
本次 BD 生成的 IP 实例副本: 6010cb6bf75be842e817dcb86607a9f0
```

第三份（`bd_prj/.../ipshared/4fe0/src/vision_axi.v`）才是**真正被综合进位流**
的那一份，时间戳必须是本次构建。并直接 grep 它的内容确认两处修复都在：

```bash
grep -q "wstrb_merge(cfg_rdata, reg_wdata, reg_strb)" "$BD"   # WSTRB 修复
grep -q "assign s_awready = !aw_v && wr_idle && rd_idle;" "$BD" # 写死锁修复
```

### 6.6 为什么字节选通必须上板打（仿真过了还不够）

仿真覆盖的是**时序组合**；而"真实主控的 WSTRB 到底长什么样"是**我们对主控
的假设** —— Zynq GP 口对 8/16 位窄访问会产生什么样的字节选通，只有 CPU 自己
知道。`axi_soak` 的 Phase D 就是用真正的 8/16 位 `volatile` 访问去打，oracle
照 AXI-Lite 的字节使能定义在 C 里**独立**算（不复用 RTL 的 `wstrb_merge`）。
配置块（`0x044`，走"读旧值再合并"）与就地合并的 `SEQ/STAMP` 两条路径都要过。

## 7. 2026-10-15 · 第一次真正跑通 AXI 通路：两处修复确认 + 第三个同类 bug

§4 的两个修复进了位流（`bd_vision`，md5 `8c80a438…`）之后，
`core/board/tools/deploy_and_verify.sh` 一条命令跑完整条验证。

### 7.1 结果

| 步 | 内容 | 结果 |
|---|---|---|
| 3 | `read_frame --watch`（纯读） | 预期"帧计数不动"✓ —— 位流加载成功、AXI 读通路通 |
| 4-B | **金丝雀：单次写** | ✓ **写死锁修复在真硅上生效**（3000 轮压测 0 失配） |
| 4-D | 配置块 `0x044` 字节/半字通道 | ✓ **WSTRB 修复生效**（末值 `0xDEADBEEF`） |
| 4-D | `SEQ`/`STAMP` 字节/半字通道 | ✗ **真 bug，见 7.2** |
| 4-F | 端到端 8 帧 | ✓ 8/8，**8 个图案各命中一次**，内嵌 CRC 自洽 |

`ctrl=0x00001A02`（帧计数 26）—— 能打出来就说明**整轮写没有挂死 CPU**。

### 7.2 第三个 bug：窄传输的**地址**没被译码（读写两侧都是）

```
✗ SEQ lane1 字节 @0x0C4  AXI=0x112233A0  期望=0x1122A1A0   ← 完全没写进去
   而 P_MIN_AREA(配置块) 的逐字节/半字写 → 全对
```

原因：RTL 用 `case (aw_a)` 拿**完整字节地址**去比字对齐的常量。主控对 `0x0C5`
做字节写时给的是 `AWADDR=0x0C5, AWSIZE=0, WSTRB=0x2`（Zynq GP 口对
`*(volatile uint8_t*)` 就是这么发的），`0x0C5` 比不中 `ADDR_SEQ=0x0C4`
→ 掉进 `default` → **整笔写被静默丢弃**。只有 lane0（地址恰好对齐）能进去。

配置块反而一直是对的：它是**范围判断 + `aw_a[6:2]`**，天然忽略低 2 位。
**同一个从口上两种译码语义并存。**

**读侧同样错**：`case (ar_a)` 也一样，读 `0x0C5` 会返回 0 而不是 `SEQ` 的值。
（这一点是真硅上先用写侧发现的，随后在协同仿真里加了窄读用例才把它一起证实。）

修法：译码一律按**字地址** `aw_a[ADDR_W-1:2]` / `ar_a[ADDR_W-1:2]`
（`W_CTRL`/`W_SEQ`/`W_STAMP0`/`W_STAMP1`/`W_FLEN`/`W_DBG`/`W_DBGDAT`/`W_FRAME`…）。
配置块的范围判断保持用字节地址 —— `ADDR_CONFIG+0x080` 是字对齐的，
对任何窄地址都等价于"字地址 < 32"，无需改。

### 7.3 ⚠ 为什么这个 bug 协同仿真没抓到（**第三次同一个元模式**）

`tb_axi` 的选通自检**早就覆盖了 SEQ 的字节写**：

```cpp
axi_write_s(A_SEQ, 0x0000BB00u, 0x2u);   // 字对齐地址 + 选通掩码
```

但那发的是"**字对齐地址 + 选通掩码**"（稀疏写），**也是合法的 AXI 行为**，
RTL 处理得了。真实主控对 `0x0C5` 的字节写发的是**非对齐地址**。两种都合法，
**RTL 只支持了其中一种，而测试台只发了另一种**。

至此真硅上暴露的三个 bug 是**同一个元模式的三次重复**：

| # | 盲区 | 测试台的理想化假设 |
|---|---|---|
| ① | AW/W 握手死锁 | 假设 AW 和 W **总是同一拍**给出 |
| ② | 配置块不认 WSTRB | 假设 `s_wstrb` **恒为 0xF** |
| ③ | 窄传输地址不译码 | 假设地址**总是字对齐** |

三次都是"**测试台把主控行为理想化**"，三次都是"仿真全绿、真硅才暴露"。
所以 `tb_axi` 现在对每种寄存器都同时覆盖**两种合法写法**：
`axi_write_s()`（对齐 + 选通）与 `axi_write_narrow()`（非对齐地址 + 对应选通），
外加**窄读**。

反向验证：把 RTL 换回修复前那一版跑新用例 → **17 项不符**
（配置块全对，`SEQ` 窄写 +1/+2/+3 与两个半字、`SEQ` 窄读 +1/+2/+3、
`STAMP0` 窄读 +3 全错），正是预期的失败点。

### 7.4 另一个教训：压测写过的寄存器**必须复原**

第一版窄读用例给 `STAMP0` 写了 `0x13572468` 却没复原，而 **`SEQ` 和 stamp
都会进帧头**（`SEQ` 在字节 8..11，stamp 在 24..31），于是帧比对报出
**每帧 8 字节不符**（32 帧 × 8 = 256，合成 320 帧 × 8 = 2560）。
是帧比对自己把这个疏忽抓出来的。现在 `SEQ`/`STAMP0`/`STAMP1`
都进保存/复原列表，并逐字复核。

（`axi_soak` 的 Phase E 本来就把这三者显式归零 —— 它们的复位默认值就是 0，
所以板上那次帧比对是干净的。）

### 7.5 我的工具也有一个错：把"内嵌 CRC"当成"整帧 CRC32"

第一次上板读帧时 8 帧全部报 `CRC 0x2144DF1C`、一个都对不上。看起来像 RTL 错，
实际是**工具错**：期望表是帧**内嵌**的那个 CRC 字段（帧最后 4 字节，小端），
不是"对整帧再算一遍 CRC32"。看 `cosim/tb_tpg.cpp` 提取期望常数的写法就清楚：

```c
for (k = 0; k < 4; k++) crc |= bytes[nb-4+k] << (8*k);
```

原版 `read_frame.c` 也是这么写错的，只是它**从来没跑通过**（上一轮第一次 AXI 写
就把板子挂死了），所以这个错一直没暴露。

改成比内嵌字段后，**8/8 全中，8 个图案各命中一次**，并且顺手加了一条不需要
任何期望表的**自洽检查**：内嵌字段是否等于"对前 `len-4` 字节算的 CRC32" ——
8 帧全部自洽，独立证明了帧没被截断、没读飞。

> 教训：一个"从来没跑通过"的工具，它的期望值也从来没被验证过。

### 7.6 第四个同类隐患：读写**同拍**时 `cfg_addr` 被读地址抢走

这一条**不是真硅暴露的，是靠推理协议找出来的** —— 前三个的教训值得直接用一次。

`s_awready` / `s_arready` 只看**已寄存的** `aw_v` / `ar_v`：

```verilog
assign s_awready = !aw_v && !b_v && !ar_v && !r_v;
assign s_arready = !ar_v && !r_v && !aw_v && !w_v && !b_v;
```

所以主控在**同一拍**同时给出 `AWVALID` 和 `ARVALID`（AXI **允许**；从口可以节流，
但**不能写错寄存器**）时，两笔都会被接收。随后 `reg_we=1` 那一拍 `rd_cycle`
（`ar_v || r_v`）仍为真，`cfg_addr` 就被读地址抢走：

| 组合 | 后果 |
|---|---|
| 写配置寄存器 A + 同拍读配置寄存器 B(≠A) | **写静默落进 B**（A 没变、B 被改） |
| 写配置寄存器 + 同拍读 `CTRL` | `cfg_addr=31`(CFG_STATUS) → **写被丢弃** |
| 窄写 + 同拍读 | `cfg_wdata` 的 WSTRB 合并读到**错寄存器的旧值** |

写**非配置块**寄存器（`SEQ`/`STAMP`/`CTRL`…）不会拉高 `cfg_we`，所以那种组合
本来就无害 —— 这一点是反向验证时确认的（一开始我以为 `SEQ` 也会被牵连，**推理错了**，
测试纠正了我）。

修法（一行）：`reg_we` 那一拍无条件用写地址。

```verilog
assign cfg_addr = reg_we    ? reg_addr            // 写提交那一拍：写优先
                : rd_conf   ? {1'b0, ar_a[6:2]}
                : rd_status ? 6'd31               // CFG_STATUS
                :             reg_addr;
```

没有副作用：读数据是在 `ar_commit` 那一拍采的，而 `reg_we` 比 commit 晚一拍，
所以那一拍 `reg_we` 还是 0，读地址照旧生效。

新增 tb 用例 `axi_write_read_same_cycle()`（awvalid+wvalid+arvalid 一起给），
反向验证：修复前的 RTL 上 **3 项不符** ——
"写 P_MIN_AREA 没生效"、"写 P_MIN_AREA 时落进了被读的那个配置寄存器"、
"读 CTRL 时写被丢弃"。

> 至此四个 bug 全是同一个元模式：**测试台把主控行为理想化**。
> 与其等真硅一个个撞出来，不如把 AXI 主控**合法但非理想**的行为逐条列出来覆盖：
> ① AW/W 不同拍 ② 部分字节选通 ③ 非字对齐地址 ④ 读写同拍。
