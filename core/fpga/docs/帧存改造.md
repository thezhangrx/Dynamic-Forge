# 帧存改造 —— 从装不下到装得下（以及暴露出来的第二个问题）

> 起因：第一次跑综合，`vision_axi` 在 `xc7z030ffg676-2` 上**超器件容量 331%**，
> 位流根本生成不了。
>
> **两轮改造的最终结果**（全部由 620 帧逐位对账守着，行为一个 bit 没变）：
>
> | | 原始 | 第一轮：帧存进 BRAM | 第二轮：除法器多周期 | |
> |---|---|---|---|---|
> | Slice LUTs | 260 336（**331%**） | 77 410（98.5%） | **69 118（87.94%）** | ✅ 装得下 |
> | Block RAM | 2.5（0.94%） | 80（30%） | **82.5（31%）** | |
> | **WNS** | **−85.900 ns** | −85.900 ns | **−11.728 ns** | ✅ 改善 86% |
> | TNS | −1 427 934 | −1 427 934 | **−20 959** | |
> | CARRY4 | 2 237 | 2 238 | **705** | |
>
> **时序仍未收敛**（约束 5 ns、实际约 16.7 ns ≈ 60 MHz），但关键路径已经
> 换了三次、每次都更浅。剩下的瓶颈在 CCL 的标签选择环（见 §9.4）。

## 1. 症状

第一次综合（2026-10-12 13:09→14:08，59 分钟）`report_utilization`：

```
| Slice LUTs*                | 260336 |     0 |     78600 | 331.22 |
|   LUT as Logic             | 136244 |     0 |     78600 | 173.34 |
|   LUT as Memory            | 124092 |     0 |     26600 | 466.51 |
|     LUT as Distributed RAM | 124092 |     0 |           |        |
| Block RAM Tile             |    2.5 |     0 |       265 |  0.94 |
| F7 Muxes                   |  35570 |     0 |     39300 |  90.51 |
```

**两条各自都超**：LUT 当内存用超 4.67 倍，LUT 当逻辑用还超 1.73 倍。
而 **BRAM 只用了 0.94%** —— 一个 9.3 Mb 的仓库空着，货全堆在工作台上。

## 2. 根因：帧存的**异步读**

```verilog
reg [7:0]  gray_mem   [0:WIDTH*HEIGHT-1];
wire [7:0] gray_rd = gray_mem[rd_addr];   // ← 组合读
reg        wall_mem   [0:WIDTH*HEIGHT-1];
wire       wall_rd = wall_mem[rd_addr];   // ← 组合读
```

**BRAM 只有同步读口**（地址要打一拍）。组合读 → Vivado 只能推断成**分布式 RAM
（LUTRAM）**，也就是拿 LUT 当内存。而三张图共：

| 数组 | 位宽 × 深度 | bit |
|---|---|---|
| `gray_mem` | 8 × 230 400 | 1 843 200 |
| `wall_mem` | 1 × 230 400 | 230 400 |
| `bright_mem` | 1 × 230 400 | 230 400 |
| **合计** | | **2 304 000** |

器件里 LUTRAM 的容量上限是 **26 600 个 LUT ≈ 1.7 Mbit** —— **物理上就装不下 2.3 Mbit**。
所以这不是"布局不好"，是**必须换存储类型**。

> ⚠ 这一条**推翻了早先的一个判断**。原判据表里写的是
> "BRAM 够不够：9.3 Mb vs 需要 115 KB → 余量 10 倍 ✓" —— 那是**按能进 BRAM 算的**，
> 前提不成立。实测 BRAM 只用了 0.94%，全压在 LUT 上爆掉。

## 3. 定案实验（4 组，避免拍脑袋）

改之前先用小模块把 Vivado 的映射规则**测出来**，而不是猜
（`D:\FPGAWORKS\memtest\`，代码见附录）：

| 变体 | 配置 | LUT as Memory | Block RAM |
|---|---|---|---|
| A | 1-bit × 230 400，**异步读** + `ram_style="block"` | 7 200 | **0** |
| B | 1-bit × 230 400，**同步读** + `ram_style="block"` | **0** | **8** |
| C | 8-bit × 230 400，**同步读** + `ram_style="block"` | **0** | **64** |
| D | 8-bit × 230 400，1 写 + **2** 同步读 | 0 | **128** |
| E | 1-bit × 230 400，1 写 + **2** 同步读 | 0 | **16** |

**两条硬结论：**

1. **`ram_style="block"` 救不了异步读** —— A 照样落 LUTRAM、BRAM 用 0 个。
   **同步读是必要条件**，`ram_style` 是充分条件，两个都要。
2. 多一个读口 → Vivado **复制 BRAM**（不是退回 LUTRAM）：D/E 正好是 C/B 的 2 倍。

第 2 条决定了 §4 的"单一读地址总线"设计：**给每张图各配独立读口 = BRAM 从 80 涨到 160**。

## 4. 改法：预读地址 + 单一读总线

### 4.1 预读地址（关键）

`rd_addr` 是**纯计数器**（`+1` / `−WIDTH` / 跳新基址），**不依赖读回来的数据**。
所以可以把"状态机本拍将要赋给 `rd_addr` 的那个值"**提前一拍**喂给 BRAM：

```verilog
wire [AW-1:0] rd_nxt = <原本要赋给 rd_addr 的表达式>;   // 组合
always @(posedge pix_clk) rd_addr <= rd_nxt;             // 照旧寄存
always @(posedge pix_clk) gray_rd <= gray_mem[rd_nxt];   // 用"下一地址"预读
```

于是

```
gray_rd(t) = gray_mem[rd_nxt(t-1)] = gray_mem[rd_addr(t)]
```

—— **与原来的异步读逐拍等价**。状态机一行不用改，两个扫描器的判据一个字不用动。

**为什么不用"延迟消费端"**（Project F 的通用做法：给每个控制信号配移位寄存器）：
本项目有 **620 帧、4.3 亿次比对、逐位一致** 的基线。延迟消费端要动状态机每一处索引与
判定，漏一处就**静默出错**；预读只动一个地方（地址生成），漏了会被逐位对账当场抓住。
取舍见 `参考项目.md` §4。

代价：`rd_nxt` 必须与状态机原来对 `rd_addr` 的 **6 处**赋值**逐字一致**（vision_ccl 里另有 4 处）。
这 10 条条件写错**不会静默通过** —— 620 帧逐位对账会报差异。

### 4.2 单一读地址总线

三个使用者在**不同时刻**要数据，共用一条读口：

```verilog
wire [AW-1:0] mem_ra = dbg_owns_read ? dbg_idx[AW-1:0]      // 调试口（只在帧间）
                     : ccl_owns_read ? ccl_addr_nxt[AW-1:0] // CCL（S_CCL）
                     : rd_nxt;                              // 行带/列扫描器
```

* 行带扫描（`S_SPAN`）与列扫描（`S_COL_SCAN`）**从不同时**运行 → 共用 `rd_nxt`
* CCL 只在 `S_CCL` 跑，那时扫描器已停 → 让给 `ccl_addr_nxt`
* 调试口 sel=0/1/2 读掩膜：**只在帧间（IDLE/DONE）有效** → 让给 `dbg_idx`

**⚠ 功能取舍**：掩膜像素的调试读**帧内无效**（读回来的是扫描器的数据）。
这是为了让设计装得下而做的取舍，已写在 `vision_top.v` 的调试口注释里。

### 4.3 调试口必须一起改

调试口原来是**组合**读：

```verilog
4'd0: dbg_data = {24'b0, gray_mem[dbg_idx]};   // ← 一处组合读就能把整张图打回 LUTRAM
```

必须改成寄存读（复用上面的 `gray_rd/wall_rd/bright_rd`）。
**这一处不改，§4.1 和 §4.2 全白做。**

## 7. 还没解决：时序（第二个问题，已精确定位）

```
WNS = -85.900 ns   (约束 5.000 ns)
TNS = -1 427 934 ns
失败端点 29 429 / 173 748
```

改动前 WNS 是 −85.904 ns —— **几乎没变**，说明瓶颈**不在内存**。

最差路径：

```
Slack (VIOLATED) : -85.900ns
  Source:       u_vision/sg_rn_reg[8]/C          ← 墙段几何（sg_*）
  Destination:  u_vision/obs_words_reg[244][8]/D
  Logic Levels: 438   (CARRY4=404  DSP48E1=2  LUT1=2 LUT2=2 LUT3=18 LUT4=2 LUT5=4 LUT6=4)
```

**404 个 CARRY4 串成一条链 = 组合整数除法器的移位减法链。**
`sg_rn` 正是 `vo_scale_round()` 的输入，而它里面写的是：

```verilog
vo_scale_round = (n * 64'd2 + d) / (d * 64'd2);    // 64 位除法，一拍算完
```

约 90 ns ≈ 11 MHz。**即使把约束降到 10 MHz 也不过。**

### 7.1 下一步方向（未做）

| # | 办法 | 说明 |
|---|---|---|
| 1 | **多周期（迭代）除法器** | 移位减法，一个结果 ~32–64 拍。帧内有 23 万拍余量，**加几百拍无所谓** |
| 2 | 多处除法**共用一个**迭代除法器 | `vo_scale_round` 有 3 处调用、`vo_atan2_q6` 1~2 处 |
| 3 | 常数除法改乘移位 | 两处 `/ 100`（`r_band_row_pct`、`r_wall_col_pct`）可换成"乘倒数再移位" |

做这些**会改变拍数、但不该改变结果** —— 仍然由那 620 帧逐位对账守着。

## 9. 第二轮：组合除法器（帧存修好之后暴露出来的）

帧存搬进 BRAM 之后，`Slice LUTs` 从 331% 降到 98.5%，但 **WNS 一点没动**（−85.904 → −85.900 ns）
—— 这说明**瓶颈根本不在内存**。

### 9.1 定位

`report_timing` 的最差路径：

```
Slack (VIOLATED) : -85.900ns
  Source:       u_vision/sg_rn_reg[8]/C          ← 墙段几何
  Destination:  u_vision/obs_words_reg[244][8]/D
  Logic Levels: 438   (CARRY4=404  DSP48E1=2  LUT1=2 LUT2=2 LUT3=18 LUT4=2 LUT5=4 LUT6=4)
```

**404 个 CARRY4 串成一条链** —— 那是 Verilog 的 `/` 综合出来的**组合阵列除法器**的
移位减法链。链路是：`sg_rn → vo_scale_round → atan2（里面又一次除法）→ obs_words`，
**两个除法器串联**。约 90 ns ≈ 11 MHz。

### 9.2 改法：`vision_div` 迭代除法器

新增 `core/fpga/rtl/vision_div.v`：恢复余数法，**每拍处理 1 位**，`WN=40 / WD=20`
→ 40 拍一个结果。帧内有 23 万拍余量，每帧几百个墙段，多花几万拍无所谓。

**为什么结果仍然逐位一致**：C 的 `/`、Verilog 的 `/`、恢复余数法，对无符号数都给出
`floor(num/den)`。所以那 620 帧照样守得住。

改动分两处，都用同一套"多周期序列"的写法：

| 位置 | 原来 | 现在 |
|---|---|---|
| `vision_top` 墙段几何 | 3 个 `vo_scale_round` + `atan2` 里的除法，全组合 | `S_SG_CYQ → LQ → RQ → ANG` 四个状态，每步一次迭代除法 |
| `vision_ccl` 角色质心 | 2 个 `vo_scale_round`，组合 | `C_DONE → C_PDIV`，一台除法器先后算 `player_x`、`player_y` |

**顺带把 atan2 里的两处常数除法也去掉了**：
`(dv * frac) / 4096`、`(v+2)/4` —— 被除数恒非负（AT 表单调递增、frac ≥ 0、符号分支已拆开），
所以 `>>> 12`、`>>> 2` 与整除等价，不占逻辑。

### 9.3 踩过的两个坑（都靠调试钩子当场抓住）

1. **退化分支留下"已发起"标志 → 死锁**
   四个状态的第一步都是"置 `sgr_started`，然后要么发起除法、要么走退化分支直接跳走"。
   跳走时忘了清标志，下一个状态就带着 `sgr_started=1` 进去**死等 `div_done`**。
   症状：`frame_done` 永远不出，自检 0 帧。

2. **漏了 `<< 8`**
   C 的调用是 `vr_atan2_q6(rq - lq, dx << 8)` —— 第二个参数是 **`x_q8`**，
   我一开始把裸的 `dx` 当除数了。症状很特别：**只有帧里的"角度"字段不符**，
   cyq/lq/rq 全对。
   定案靠的是 RTL 侧 `+dumpseg` 与 C 侧 `VR_DEBUG_SEG=1` 那对**故意做成同格式**的调试输出
   （见 `core/fpga/cosim/README.md` 的"命令行开关"）—— 这是它第一次真正派上用场。

### 9.4 结果，以及还没收敛的部分

| | 帧存修好 | +分段除法 | **+CCL 除法** |
|---|---|---|---|
| Slice LUTs | 77 410（98.49%） | 72 409（92.12%） | **69 118（87.94%）** |
| LUT as Logic | 68 518 | 63 517 | **60 226** |
| CARRY4 | 2 238 | 1 423 | **705** |
| **WNS** | −85.900 ns | −46.498 ns | **−11.728 ns** |
| TNS | −1 427 934 | −21 811 | **−20 959** |
| 失败端点 | 29 429 | 12 956 | 14 218 |

**关键路径换了三次**：组合除法（404 CARRY4）→ CCL 质心除法 → **CCL 的标签选择环**：

```
Slack (VIOLATED) : -11.728ns
  Source:      u_vision/u_ccl/sel_i_reg_rep[0]__4/C
  Destination: u_vision/u_ccl/best_vld1/CEB2
```

那是 `C_SEL` 状态里的
`if (score_num * best_den > best_num * {32'b0, wh_c})`
—— **32×32 乘法比较**，外加读 `parent[sel_i]` / `cmp_*[sel_i]` 那些大数组的巨型多路选择。

**下一步**（未做）：把 `C_SEL` 的打分比较也拆成多周期（寄存器打拍，或改成串行比较），
以及那几张大数组的读出加流水。**时序仍未收敛，还不能说"能上板跑 200 MHz"。**

## 10. 时序：**200 MHz 这个目标是错的**

### 10.1 实测每帧拍数

改之前一直在追"时序不过"——但我从没问过**到底需要多快**。给 `tb_vision.cpp` 加了个
纯诊断的拍数计数器（不参与任何比对），实测：

```
总拍数 1999957，每帧 499989 拍；30 fps 需要 ≥ 15.0 MHz
```

**每帧约 50 万拍**（640×360 = 23 万像素的输入相位 + 约 27 万拍的分析相位）。于是：

| | 数字 |
|---|---|
| 30 fps 的**真实要求** | **15 MHz** |
| 当前设计达到（WNS 反推：5 + 11.728 = 16.728 ns） | **≈ 60 MHz** |
| **余量** | **4 倍** |

### 10.2 结论

`vision.xdc` 里原来写的是 `create_clock -period 5.000`（200 MHz）——**那是我照板子
`sys_clk` 拍的，不是需求**。需求由帧率决定：

```
所需频率 = 每帧拍数 × 帧率
```

**既然已经有 4 倍余量，"把 C_SEL 打分环拆成流水"这件事就不该现在做** ——
它是高风险改造（那个比较有跨标签的**顺序依赖**，不能简单流水化），而收益是
余量从 4 倍变成 8 倍。**先拿实现的真实数字，再决定。**

约束已改成 **20 ns（50 MHz）= 3.3 倍余量**，注释里写了推导过程。

> 这一条值得单独记：**"时序不过"这个说法本身可能是假的** —— 它取决于约束定得对不对。
> 定约束之前先问"需要多快"。

## 12. 与并行会话的一次交叉验证（指纹变更说明）

同一台机器上还有一个会话在跑 **`core/board/`（PS 侧驱动 + 板子全流程仿真）**。
它也动了验证链上的文件：

| 文件 | 时间 | 改了什么 |
|---|---|---|
| `core/fpga/ref/vision_ref.c` | 20:46 | 在 `vr_extract_walls` 里补两道**结构性过滤**，对齐 `core/vision/to_standard.py` 的语义真值 |
| `core/fpga/rtl/vision_top.v` | 20:56 | RTL 侧对应的过滤（`MIN_SEG_TO_STANDARD = 24`、`half_w >= half_h`） |

两道过滤是：

1. **`DEFAULT_MIN_SEGMENT_PX = 24`** —— 检测器为了找缺口会把墙切成很多小碎片（实测出现过 8 px、17 px），它们不是真障碍。注意这和 `r_min_seg_px`（默认 8）是**两回事**：后者是检测参数，24 是"转标准结构"的结构性过滤，**两道都要**。
2. **不变量 `half_w >= half_h`** —— 段短于厚度时 `half_w` 会小于 `half_h`，PS 侧 `decode_vision_frame().validate()` 会当场抛异常。**真实照片实测 32 张里 6 张触发**（如 hw=5.0 < hh=8.5）。

### 12.1 我做的核对（这是两个会话最有价值的一次互检）

拿 **改动后的 RTL + 改动后的 C** 重跑全量对账：

```
320 帧：比对项 221 605 409，不符 0，有差异的帧 0
       几何帧指纹 5b119febe6015a37      ← 与 3530c161ee7463d4 不同
AXI 20 帧：11 490 项，不符 0
自检 8 场景：403 项，不符 0
```

**读出三件事：**

1. **指纹变了**（比对项少 180 个）→ **过滤在合成的 320 帧上确实生效了**，掉了若干段。所以
   "合成图永远产不出这种段"这句话**只对其中一类退化段成立**，靠长度削的那道在合成图上也会触发。
2. **`不符 0`** → **RTL 与 C 仍然逐位一致**。两个会话各自的改动**互相自洽** ✓
   这是任何一个会话单独都拿不到的证据。
3. **每帧拍数从 499 989 涨到 521 230（+4.2%）** → 30 fps 的要求从 15.0 MHz 升到 **15.6 MHz**。
   相对当前约 60 MHz 仍有 **3.8 倍余量**，结论不变。

### 12.2 教训：合成图逐位对账有**结构性盲区**

`export_frames.py` 自己的文档就写着：

> 用合成图做逐位比对，只能证明"我的 RTL 和我的合成器一致"，证明不了"它对真实输入的行为和 Python 一致"。

这次就是活例子：**620 帧全绿**，却漏掉了"真实照片里 32 张有 6 张会产出违反协议不变量的段"。
**光靠合成帧再跑一万帧也补不上这个洞** —— 必须拿**真实照片**喂。
