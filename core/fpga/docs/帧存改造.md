# 帧存改造 —— 从装不下到装得下（以及暴露出来的第二个问题）

> 起因：第一次跑综合，`vision_axi` 在 `xc7z030ffg676-2` 上**超器件容量 331%**，
> 位流根本生成不了。
>
> **两轮改造的最终结果**（全部由 620 帧逐位对账守着，行为一个 bit 没变）：
>
> | | 原始 | 第一轮：帧存进 BRAM | 第二轮：除法器多周期 | |
> |---|---|---|---|---|
> | Slice LUTs | 260 336（**331%**） | 77 410（98.5%） | **69 118（87.94%）** | ✅ 装得下 |
> | Block RAM | 2.5（0.94%） | 80（30%） | **82.5（31%）** | |
> | **WNS** | **−85.900 ns** | −85.900 ns | **−11.728 ns** | ✅ 改善 86% |
> | TNS | −1 427 934 | −1 427 934 | **−20 959** | |
> | CARRY4 | 2 237 | 2 238 | **705** | |
>
> **时序仍未收敛**（约束 5 ns、实际约 16.7 ns ≈ 60 MHz），但关键路径已经
> 换了三次、每次都更浅。剩下的瓶颈在 CCL 的标签选择环（见 §9.4）。

## 1. 症状

第一次综合（2026-10-12 13:09→14:08，59 分钟）`report_utilization`：

```
| Slice LUTs*                | 260336 |     0 |     78600 | 331.22 |
|   LUT as Logic             | 136244 |     0 |     78600 | 173.34 |
|   LUT as Memory            | 124092 |     0 |     26600 | 466.51 |
|     LUT as Distributed RAM | 124092 |     0 |           |        |
| Block RAM Tile             |    2.5 |     0 |       265 |  0.94 |
| F7 Muxes                   |  35570 |     0 |     39300 |  90.51 |
```

**两条各自都超**：LUT 当内存用超 4.67 倍，LUT 当逻辑用还超 1.73 倍。
而 **BRAM 只用了 0.94%** —— 一个 9.3 Mb 的仓库空着，货全堆在工作台上。

## 2. 根因：帧存的**异步读**

```verilog
reg [7:0]  gray_mem   [0:WIDTH*HEIGHT-1];
wire [7:0] gray_rd = gray_mem[rd_addr];   // ← 组合读
reg        wall_mem   [0:WIDTH*HEIGHT-1];
wire       wall_rd = wall_mem[rd_addr];   // ← 组合读
```

**BRAM 只有同步读口**（地址要打一拍）。组合读 → Vivado 只能推断成**分布式 RAM
（LUTRAM）**，也就是拿 LUT 当内存。而三张图共：

| 数组 | 位宽 × 深度 | bit |
|---|---|---|
| `gray_mem` | 8 × 230 400 | 1 843 200 |
| `wall_mem` | 1 × 230 400 | 230 400 |
| `bright_mem` | 1 × 230 400 | 230 400 |
| **合计** | | **2 304 000** |

器件里 LUTRAM 的容量上限是 **26 600 个 LUT ≈ 1.7 Mbit** —— **物理上就装不下 2.3 Mbit**。
所以这不是"布局不好"，是**必须换存储类型**。

> ⚠ 这一条**推翻了早先的一个判断**。原判据表里写的是
> "BRAM 够不够：9.3 Mb vs 需要 115 KB → 余量 10 倍 ✓" —— 那是**按能进 BRAM 算的**，
> 前提不成立。实测 BRAM 只用了 0.94%，全压在 LUT 上爆掉。

## 3. 定案实验（4 组，避免拍脑袋）

改之前先用小模块把 Vivado 的映射规则**测出来**，而不是猜
（`D:\FPGAWORKS\memtest\`，代码见附录）：

| 变体 | 配置 | LUT as Memory | Block RAM |
|---|---|---|---|
| A | 1-bit × 230 400，**异步读** + `ram_style="block"` | 7 200 | **0** |
| B | 1-bit × 230 400，**同步读** + `ram_style="block"` | **0** | **8** |
| C | 8-bit × 230 400，**同步读** + `ram_style="block"` | **0** | **64** |
| D | 8-bit × 230 400，1 写 + **2** 同步读 | 0 | **128** |
| E | 1-bit × 230 400，1 写 + **2** 同步读 | 0 | **16** |

**两条硬结论：**

1. **`ram_style="block"` 救不了异步读** —— A 照样落 LUTRAM、BRAM 用 0 个。
   **同步读是必要条件**，`ram_style` 是充分条件，两个都要。
2. 多一个读口 → Vivado **复制 BRAM**（不是退回 LUTRAM）：D/E 正好是 C/B 的 2 倍。

第 2 条决定了 §4 的"单一读地址总线"设计：**给每张图各配独立读口 = BRAM 从 80 涨到 160**。

## 4. 改法：预读地址 + 单一读总线

### 4.1 预读地址（关键）

`rd_addr` 是**纯计数器**（`+1` / `−WIDTH` / 跳新基址），**不依赖读回来的数据**。
所以可以把"状态机本拍将要赋给 `rd_addr` 的那个值"**提前一拍**喂给 BRAM：

```verilog
wire [AW-1:0] rd_nxt = <原本要赋给 rd_addr 的表达式>;   // 组合
always @(posedge pix_clk) rd_addr <= rd_nxt;             // 照旧寄存
always @(posedge pix_clk) gray_rd <= gray_mem[rd_nxt];   // 用"下一地址"预读
```

于是

```
gray_rd(t) = gray_mem[rd_nxt(t-1)] = gray_mem[rd_addr(t)]
```

—— **与原来的异步读逐拍等价**。状态机一行不用改，两个扫描器的判据一个字不用动。

**为什么不用"延迟消费端"**（Project F 的通用做法：给每个控制信号配移位寄存器）：
本项目有 **620 帧、4.3 亿次比对、逐位一致** 的基线。延迟消费端要动状态机每一处索引与
判定，漏一处就**静默出错**；预读只动一个地方（地址生成），漏了会被逐位对账当场抓住。
取舍见 `参考项目.md` §4。

代价：`rd_nxt` 必须与状态机原来对 `rd_addr` 的 **6 处**赋值**逐字一致**（vision_ccl 里另有 4 处）。
这 10 条条件写错**不会静默通过** —— 620 帧逐位对账会报差异。

### 4.2 单一读地址总线

三个使用者在**不同时刻**要数据，共用一条读口：

```verilog
wire [AW-1:0] mem_ra = dbg_owns_read ? dbg_idx[AW-1:0]      // 调试口（只在帧间）
                     : ccl_owns_read ? ccl_addr_nxt[AW-1:0] // CCL（S_CCL）
                     : rd_nxt;                              // 行带/列扫描器
```

* 行带扫描（`S_SPAN`）与列扫描（`S_COL_SCAN`）**从不同时**运行 → 共用 `rd_nxt`
* CCL 只在 `S_CCL` 跑，那时扫描器已停 → 让给 `ccl_addr_nxt`
* 调试口 sel=0/1/2 读掩膜：**只在帧间（IDLE/DONE）有效** → 让给 `dbg_idx`

**⚠ 功能取舍**：掩膜像素的调试读**帧内无效**（读回来的是扫描器的数据）。
这是为了让设计装得下而做的取舍，已写在 `vision_top.v` 的调试口注释里。

### 4.3 调试口必须一起改

调试口原来是**组合**读：

```verilog
4'd0: dbg_data = {24'b0, gray_mem[dbg_idx]};   // ← 一处组合读就能把整张图打回 LUTRAM
```

必须改成寄存读（复用上面的 `gray_rd/wall_rd/bright_rd`）。
**这一处不改，§4.1 和 §4.2 全白做。**

## 7. 还没解决：时序（第二个问题，已精确定位）

```
WNS = -85.900 ns   (约束 5.000 ns)
TNS = -1 427 934 ns
失败端点 29 429 / 173 748
```

改动前 WNS 是 −85.904 ns —— **几乎没变**，说明瓶颈**不在内存**。

最差路径：

```
Slack (VIOLATED) : -85.900ns
  Source:       u_vision/sg_rn_reg[8]/C          ← 墙段几何（sg_*）
  Destination:  u_vision/obs_words_reg[244][8]/D
  Logic Levels: 438   (CARRY4=404  DSP48E1=2  LUT1=2 LUT2=2 LUT3=18 LUT4=2 LUT5=4 LUT6=4)
```

**404 个 CARRY4 串成一条链 = 组合整数除法器的移位减法链。**
`sg_rn` 正是 `vo_scale_round()` 的输入，而它里面写的是：

```verilog
vo_scale_round = (n * 64'd2 + d) / (d * 64'd2);    // 64 位除法，一拍算完
```

约 90 ns ≈ 11 MHz。**即使把约束降到 10 MHz 也不过。**

### 7.1 下一步方向（未做）

| # | 办法 | 说明 |
|---|---|---|
| 1 | **多周期（迭代）除法器** | 移位减法，一个结果 ~32–64 拍。帧内有 23 万拍余量，**加几百拍无所谓** |
| 2 | 多处除法**共用一个**迭代除法器 | `vo_scale_round` 有 3 处调用、`vo_atan2_q6` 1~2 处 |
| 3 | 常数除法改乘移位 | 两处 `/ 100`（`r_band_row_pct`、`r_wall_col_pct`）可换成"乘倒数再移位" |

做这些**会改变拍数、但不该改变结果** —— 仍然由那 620 帧逐位对账守着。

## 9. 第二轮：组合除法器（帧存修好之后暴露出来的）

帧存搬进 BRAM 之后，`Slice LUTs` 从 331% 降到 98.5%，但 **WNS 一点没动**（−85.904 → −85.900 ns）
—— 这说明**瓶颈根本不在内存**。

### 9.1 定位

`report_timing` 的最差路径：

```
Slack (VIOLATED) : -85.900ns
  Source:       u_vision/sg_rn_reg[8]/C          ← 墙段几何
  Destination:  u_vision/obs_words_reg[244][8]/D
  Logic Levels: 438   (CARRY4=404  DSP48E1=2  LUT1=2 LUT2=2 LUT3=18 LUT4=2 LUT5=4 LUT6=4)
```

**404 个 CARRY4 串成一条链** —— 那是 Verilog 的 `/` 综合出来的**组合阵列除法器**的
移位减法链。链路是：`sg_rn → vo_scale_round → atan2（里面又一次除法）→ obs_words`，
**两个除法器串联**。约 90 ns ≈ 11 MHz。

### 9.2 改法：`vision_div` 迭代除法器

新增 `core/fpga/rtl/vision_div.v`：恢复余数法，**每拍处理 1 位**，`WN=40 / WD=20`
→ 40 拍一个结果。帧内有 23 万拍余量，每帧几百个墙段，多花几万拍无所谓。

**为什么结果仍然逐位一致**：C 的 `/`、Verilog 的 `/`、恢复余数法，对无符号数都给出
`floor(num/den)`。所以那 620 帧照样守得住。

改动分两处，都用同一套"多周期序列"的写法：

| 位置 | 原来 | 现在 |
|---|---|---|
| `vision_top` 墙段几何 | 3 个 `vo_scale_round` + `atan2` 里的除法，全组合 | `S_SG_CYQ → LQ → RQ → ANG` 四个状态，每步一次迭代除法 |
| `vision_ccl` 角色质心 | 2 个 `vo_scale_round`，组合 | `C_DONE → C_PDIV`，一台除法器先后算 `player_x`、`player_y` |

**顺带把 atan2 里的两处常数除法也去掉了**：
`(dv * frac) / 4096`、`(v+2)/4` —— 被除数恒非负（AT 表单调递增、frac ≥ 0、符号分支已拆开），
所以 `>>> 12`、`>>> 2` 与整除等价，不占逻辑。

### 9.3 踩过的两个坑（都靠调试钩子当场抓住）

1. **退化分支留下"已发起"标志 → 死锁**
   四个状态的第一步都是"置 `sgr_started`，然后要么发起除法、要么走退化分支直接跳走"。
   跳走时忘了清标志，下一个状态就带着 `sgr_started=1` 进去**死等 `div_done`**。
   症状：`frame_done` 永远不出，自检 0 帧。

2. **漏了 `<< 8`**
   C 的调用是 `vr_atan2_q6(rq - lq, dx << 8)` —— 第二个参数是 **`x_q8`**，
   我一开始把裸的 `dx` 当除数了。症状很特别：**只有帧里的"角度"字段不符**，
   cyq/lq/rq 全对。
   定案靠的是 RTL 侧 `+dumpseg` 与 C 侧 `VR_DEBUG_SEG=1` 那对**故意做成同格式**的调试输出
   （见 `core/fpga/cosim/README.md` 的"命令行开关"）—— 这是它第一次真正派上用场。

### 9.4 结果，以及还没收敛的部分

| | 帧存修好 | +分段除法 | **+CCL 除法** |
|---|---|---|---|
| Slice LUTs | 77 410（98.49%） | 72 409（92.12%） | **69 118（87.94%）** |
| LUT as Logic | 68 518 | 63 517 | **60 226** |
| CARRY4 | 2 238 | 1 423 | **705** |
| **WNS** | −85.900 ns | −46.498 ns | **−11.728 ns** |
| TNS | −1 427 934 | −21 811 | **−20 959** |
| 失败端点 | 29 429 | 12 956 | 14 218 |

**关键路径换了三次**：组合除法（404 CARRY4）→ CCL 质心除法 → **CCL 的标签选择环**：

```
Slack (VIOLATED) : -11.728ns
  Source:      u_vision/u_ccl/sel_i_reg_rep[0]__4/C
  Destination: u_vision/u_ccl/best_vld1/CEB2
```

那是 `C_SEL` 状态里的
`if (score_num * best_den > best_num * {32'b0, wh_c})`
—— **32×32 乘法比较**，外加读 `parent[sel_i]` / `cmp_*[sel_i]` 那些大数组的巨型多路选择。

**下一步**（未做）：把 `C_SEL` 的打分比较也拆成多周期（寄存器打拍，或改成串行比较），
以及那几张大数组的读出加流水。**时序仍未收敛，还不能说"能上板跑 200 MHz"。**

## 10. 时序：**200 MHz 这个目标是错的**

### 10.1 实测每帧拍数

改之前一直在追"时序不过"——但我从没问过**到底需要多快**。给 `tb_vision.cpp` 加了个
纯诊断的拍数计数器（不参与任何比对），实测：

```
总拍数 1999957，每帧 499989 拍；30 fps 需要 ≥ 15.0 MHz
```

**每帧约 50 万拍**（640×360 = 23 万像素的输入相位 + 约 27 万拍的分析相位）。于是：

| | 数字 |
|---|---|
| 30 fps 的**真实要求** | **15 MHz** |
| 当前设计达到（WNS 反推：5 + 11.728 = 16.728 ns） | **≈ 60 MHz** |
| **余量** | **4 倍** |

### 10.2 结论

`vision.xdc` 里原来写的是 `create_clock -period 5.000`（200 MHz）——**那是我照板子
`sys_clk` 拍的，不是需求**。需求由帧率决定：

```
所需频率 = 每帧拍数 × 帧率
```

**既然已经有 4 倍余量，"把 C_SEL 打分环拆成流水"这件事就不该现在做** ——
它是高风险改造（那个比较有跨标签的**顺序依赖**，不能简单流水化），而收益是
余量从 4 倍变成 8 倍。**先拿实现的真实数字，再决定。**

约束已改成 **20 ns（50 MHz）= 3.3 倍余量**，注释里写了推导过程。

> 这一条值得单独记：**"时序不过"这个说法本身可能是假的** —— 它取决于约束定得对不对。
> 定约束之前先问"需要多快"。

## 12. 与并行会话的一次交叉验证（指纹变更说明）

同一台机器上还有一个会话在跑 **`core/board/`（PS 侧驱动 + 板子全流程仿真）**。

```
320 帧：比对项 221 605 409，不符 0，有差异的帧 0
       几何帧指纹 5b119febe6015a37      ← 与 3530c161ee7463d4 不同
AXI 20 帧：11 490 项，不符 0
自检 8 场景：403 项，不符 0
```

**读出三件事：**

1. **指纹变了**（比对项少 180 个）→ **过滤在合成的 320 帧上确实生效了**，掉了若干段。所以
   "合成图永远产不出这种段"这句话**只对其中一类退化段成立**，靠长度削的那道在合成图上也会触发。
2. **`不符 0`** → **RTL 与 C 仍然逐位一致**。两个会话各自的改动**互相自洽** ✓
   这是任何一个会话单独都拿不到的证据。
3. **每帧拍数从 499 989 涨到 521 230（+4.2%）** → 30 fps 的要求从 15.0 MHz 升到 **15.6 MHz**。
   相对当前约 60 MHz 仍有 **3.8 倍余量**，结论不变。

## 13. 合并后的 RTL 装不下 —— 定位过程与结论（2026-10-13 上午）

### 13.1 症状

`impl.log`（`D:\FPGAWORKS\vivado_impl\impl.log`）：

ERROR: [Place 30-640] 需要 117,036 Slice LUT（LUT as Logic 108,672），器件只有 78,600

### 13.2 逐步排除（每一步都用实验，不靠推测）

| 步骤 | 假设 | 结论 | 依据 |
|---|---|---|---|

| 3 | 我的两个除法器 | ❌ **排除** | 层级报告：`u_sgdiv` **534** + `u_pdiv` **78** = 612 个 LUT |
| 4 | `vision_ccl` | ❌ **排除** | 层级报告：`u_ccl` 只占 **5,810** |

**105,436 个 `Logic LUT` 全在 `vision_top` 自身。**

### 13.3 二分实验：`MAX_SEGS` 384 → 96

只改一个常量（`vision_top.v:110`），其余全同：

| | `MAX_SEGS=384`（真） | `MAX_SEGS=96`（诊断） | 差 |
|---|---|---|---|
| Slice LUTs | 116,979 | 101,387 | **−15,592** |
| Logic LUTs | 108,615 | 93,119 | −15,496 |
| **FFs** | **56,776** | **41,584** | **−15,192** |
| LUTRAMs | 8,364 | 8,268 | −96 |

**寄存器的降幅几乎和 LUT 一样大** —— 说明 `seg_*` 是**寄存器实现的**，深度减到 1/4 就少 15,192 个 FF。

### 13.4 关键：`MAX_SEGS = 384`，但实际峰值是 **2**

给 `tb_vision.cpp` 加了个纯观测计数器（不参与比对），跑 60 帧：

```
观测到的 n_segs 最大值 2，seg_i 最大值 2（MAX_SEGS 现在是 384）
```

**192 倍的过度分配。** 注释写的是"一带最多 WIDTH/2 段"（= 320），但实测是 2。

### 13.5 寄存器账算平了 —— 三个"该进 RAM 却进了寄存器"的数组

`vision_top` 的 **56,305 个 FF** 是：

| 数组 | 规模 | 位数 |
|---|---|---|
| `obs_words` | 512 × 32 | 16,384 |
| `gap_words` | 512 × 32 | 16,384 |
| `seg_cy` | 384 × 32 | 12,288 |
| `seg_x0` / `seg_x1` | 384 × 10 × 2 | 7,680 |
| **合计** | | **52,736** |
| 实测 | | **56,305** |

**几乎正好对上。** 而 **105,436 个 `Logic LUT` 主要就是这些数组的读出多路器** ——
它们都被**组合变址读**（`obs_words[dbg_idx]`、`seg_cy[seg_k - 9'd1]` …），
推论不成 RAM，只能拿 LUT 搭 **512:1 / 384:1** 的多路器。

### 13.6 修复方向（**已定位，待执行**）

**和 §4 给三张帧存用的手法完全一样：同步读 + `ram_style="block"`。**

| 目标 | 现在 | 改后 |
|---|---|---|
| `obs_words` | 16,384 FF + 大 mux | **1 个 BRAM36** |
| `gap_words` | 16,384 FF + 大 mux | **1 个 BRAM36** |
| `seg_*` | 19,968 FF + 大 mux | **1 个 BRAM36** |
| `MAX_SEGS` | 384（实测峰值 2） | 按**证明过的上界**收紧，不是按观察值 |

**BRAM 才用了 30%（80/265）—— 空着 185 个。**

**这不是"砍功能"，是"把缓冲搬到它本来就该待的地方"。** 与 §4 定下的原则一致：
**功能正确性不是能和面积交换的筹码，能换的是实现方式。**

### 13.7 ⚠️ 还没解决的

**`MAX_SEGS=96` 时仍然是 101,387（129%）—— 还是装不下。**
所以除了这些数组，**还有大约 2 万个 LUT 没找到出处**。
下一步要么继续二分，要么先把数组搬进 RAM 再重新测量（搬完数字会大变，届时再看剩余）。

### 13.8 顺带记下一个潜在隐患

`n_segs` 是 9 位（最大 511），而 `MAX_SEGS = 384`。若某帧的段数超过 384，
`seg_x0[n_segs] <= ...`（`vision_top.v:620`）会**越界写**。
实测峰值是 2，所以现在不会触发 —— 但收紧 `MAX_SEGS` 时必须配一个**饱和保护**，
不能只是"把常量改小"。

## 14. 第二轮修复：`MAX_SEGS` 收紧（已做）与 `obs/gap` 单写口（待做）

### 14.1 `MAX_SEGS` 384 → 32：**有证明的行为不变改动**（已完成）

**上界证明**（写在 `vision_top.v` 的常量声明处）：

```
* seg_push 只接受 长度 >= MIN_SEG_TO_STANDARD (=24) 的段，
  而 24 是**硬常量**，不受运行时配置影响（r_min_seg_px 可以配得更小，但 24 那道永远在）；
* 被接受的段之间至少隔 1 个 flags==0 的列（它们是 flags 的游程）；
* 索引范围 x_max - x_min + 1 <= WIDTH = 640。
⇒ 24k + (k-1) <= 640  ⇒  k <= 25
```

取 **32** 留余量。**验证**：改完 320 帧逐位对账

```
比对项 221605409，不符 0，有差异的帧 0
几何帧指纹 5b119febe6015a37      ← 与改动前【逐位相同】
```

实测峰值 `n_segs = 3`，与证明一致。

> **§13.8 的越界写担心是错的** —— `seg_push` 里**本来就有**饱和保护
> `(n_segs < MAX_SEGS)`。所以那个隐患不存在，收回。

### 14.2 `obs_words` / `gap_words` 为什么进不了 RAM（已查明）

`impl_failed.log` 给出了 Vivado 的原话：

```
WARNING: [Synth 8-4767] Trying to implement RAM 'gap_words_reg' in registers.
Reason is one or more of the following :
	1: RAM has multiple writes via different ports in same process.
	   If RAM inferencing intended, write to one port per process.
```

**根因**：这两个数组在一个 always 块里有**多个写语句** ——

* `obs_words`：**10 个**（9 个字段各一条 + "整墙朝向对齐"的回写一条）
* `gap_words`：**9 个**（9 个字段各一条）

Vivado 因此判定"多写口"，**拒绝推断 RAM**，把 512×32 **拆成 16 384 个寄存器**
（×2 个数组 = **32 768 个 FF**），再加一片读出多路器。

**注意读口没问题**：打包器 `obs_words[pk_widx]` 和调试口 `obs_words[dbg_idx]` 都是**组合读**——
**分布式 RAM（LUTRAM）天生支持异步读**，不需要改测试台。

### 14.3 修法：收敛成单写口（**已实施，实测收益见 §14.4**）

```verilog
// 一个 process、一个写口 —— Vivado 才会推断成 RAM
reg        owr_en;  reg [8:0] owr_addr;  reg [31:0] owr_data;
always @(posedge pix_clk) if (owr_en) obs_words[owr_addr] <= owr_data;
```
由一个小**字段计数器**逐字段写（每条记录 9 拍），
`owr_data` 用 9:1 选择器从各字段值里选。

| | 改前 | 改后（实测） |
|---|---|---|
| `obs_words` 512×32 | 16 384 FF + 读出多路器 + **每位的 10 路写选择器** | LUTRAM |
| `gap_words` 512×32 | 16 384 FF + 读出多路器 + **每位的 10 路写选择器** | LUTRAM |

**代价**：每帧约多 157 拍（实测 521 230 → 521 387），可忽略。
**收益**：**−78 732 LUT、−32 395 FF**。完整实测表与原因见 §14.4。

## 14.4 单写口的真实收益：**比预估大一个数量级**（已实测）

§14.3 的估算是"每个数组约 256 个 LUT"，实际收益是 **−78,732 LUT**。

| 版本 | Slice LUTs | 占比 | 寄存器 | LUTRAM |
|---|---|---|---|---|
| `diag_sv`（原：多写口 + `MAX_SEGS=384`） | 116,979 | 148.83% | 56,776 | 8,364 |
| `diag_ms32`（`MAX_SEGS=32`，仍多写口） | 99,400 | 126.46% | 38,136 | 8,236 |
| **`diag_sg`（单写口 + `MAX_SEGS=32`）** | **20,668** | **26.30%** | **5,741** | **9,636** |
| `diag_sg_area`（再叠 `AreaOptimized_high`） | 20,403 | 25.96% | 5,714 | 9,636 |
| **`diag_final`（本轮全部修复：累加器加宽 + `prv_lv` + 输出清零）** | **20,786** | **26.45%** | **5,807** | **9,648** |

`diag_sg` → `diag_final` 只多了 **118 个 LUT**（修三个真实照片缺陷的代价），
而 F7/F8 宽选择器从 **12,478 / 5,338** 掉到 **1,775 / 304** ——
这正是那批 512:1 变址读多路器消失的直接证据。`Block RAM 82.5`（31.13%）、`DSP 46`。

**为什么差这么多**：`obs_words[n_obs*9 + k] <= …` 是 **9 条变址写语句**
（`obs_words` 还有第 10 条"整墙朝向"回写）。Vivado 推断不出 RAM，就把
1056 个 32 位寄存器**逐位**实现 —— 而每一位的输入都是一个
"保持 / 写字段0 / 写字段1 / … / 写字段8"的 **10 路选择器**。
1056 × 32 位 × 约 2.3 个 LUT/位 ≈ **7.8 万 LUT**，账目正好对上。
改成单写口后它变成真 RAM，这 7.8 万全部消失。

> **§13 的诊断是错的**（部分）：它把"装不下"主要归给 `seg_*` 与 `MAX_SEGS=384`。
> `MAX_SEGS` 那条是真的，但只值 −17,579 LUT；**主因一直是这两个多写口数组**。
> 教训：比例失衡到 331% 时，先怀疑**被推断成寄存器的大数组**，而不是某个常量。

**结论：装得下，而且余量约 4 倍**（20,668 / 78,600 = 26.3%）。
另外 `AreaOptimized_high` 只再省 265 个 LUT（1.3%），**不值得**为它牺牲综合可预测性，
所以最终走默认指令。

**这个改动是行为不变的**：320 帧合成语料 `不符 0`、指纹仍是 `5b119febe6015a37`；
AXI 通路 11,490 项、自检 403 项同样 `不符 0`。每帧只多约 157 拍（521,230 → 521,387）。

## 14.5 补上验证盲区：真实照片语料

### 14.5.1 为什么必须补

`data/fpga/stim_color` 那 320 帧来自**录屏**（`data/vision/run4/screen.mp4`）。
它在结构上是"良性"的：段永远够长、标签表永远填不满、几乎每帧都选得出玩家。
于是 **620 帧逐位对账全绿，也不代表算法在真实输入下正确**——
这一点 `export_frames.py` 自己的注释就写了，但一直没有对应语料。

对照组：C 参考模型早就有真实照片的守卫测试
（`core/fpga/tests/test_ref_robustness.py`，用的 `data/vision/*.jpg`）。
**但 RTL 从来没有被真实照片激励过。**

新增 `core/fpga/ref/export_photos.py`：把 32 张真实照片导成 **640×360 P6 PPM**
（RTL 的 `WIDTH/HEIGHT` 是编译期常量，测试台不做缩放，尺寸必须正好；
缩放策略是"等比覆盖 + 居中裁剪"，不拉伸 —— 拉伸会人为制造或抹掉要测的那种段）。

结果：**真实照片第一次进 RTL，32 帧全部死锁**。

### 14.5.2 三个只在真实输入下出现的缺陷（已全部修掉）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| ① | **32 帧全部不出帧**，`n_segs=0`，卡在 `S_CCL` 等 `ccl_done` | `C_SEL` 的 `sel_i` 只有 `clog2(256)=8` 位，而 `n_label` 会饱和到 **256**；判据 `{1'b0,sel_i} >= n_label` **恒为假** → 绕圈死循环 | 改成"先处理 sel_i，再用 **9 位**判是否还有下一个" |
| ② | 只有 `obs[4]`（cyq）一个字段不符，2/32 张触发（如算出 y=453，图只有 360 高） | `sg_total` 只有 **16 位**，而一段最多覆盖 `640×360=230400` 个墙像素 → **回绕**；它是除数 | 累加器按 C 的 `long` 语义加宽到 32 位（`total` 18 位、`sumy` 27 位、`ln/rn` 13 位都够） |
| ③ | 21/32 帧各有 18 处不符，首个恒在**字节 32**（player_x 最低位） | 没选中玩家时 RTL 不清 `player_*/blob_*`（它们是寄存器），保留了**上一帧**的值；C 是 `memset` + 提前 return | `C_DONE` 的 `!best_vld` 分支里逐项清零 |

顺带修掉一个**同源**问题：`C_MATCH` 直接用 `prv_lb[j_prev]`，而 C 是
`if (prev[j].label < 0) continue;`。标签表打满时未被建标签的游程 `cur_lb`
保持**上一行的陈旧值**，会被搬进 `prv_lb` 再参与并查集合并。
补了 `prv_lv`（"上一行这条有没有标签"）作为跳过条件。

### 14.5.3 定位手法（值得留给下一次）

1. **先加超时诊断，别猜**。给 `tb_vision.cpp` 补了 `dump_stuck()`：
   卡死时打印 `state`（带名字）、各计数器，以及 **CCL 子模块内部**的
   `state/n_cur/n_label/i_cur/j_prev/find_target`。第一句诊断就把范围从
   "整条链"缩到 `C_SEL` + `n_label=256`。
2. **连通域全表对账**。`vr_ref_process_ex()` 只回**被选中的**那个连通域，
   分不清"表算错了"还是"判据判错了"。于是写了
   `core/fpga/ref/dump_cc.c`（`#include "vision_ref.c"` + `-DVR_NO_MAIN`，
   于是文件作用域的 `static` 也能读），配合 tb 的 `--dump-cc`，
   把两边的 `(n, x0, x1, y0, y1)` 集合逐帧 diff —— 结果 **0 差异**，
   一举排除 CCL，把范围锁死到"选优之后"。

### 14.6.1 比特流**没有**生成，原因不能绕过

`write_bitstream` 被 DRC 挡住：

```
ERROR: [DRC NSTD-1] Unspecified I/O Standard: 135 out of 135 logical ports
ERROR: [DRC UCIO-1] Unconstrained Logical Port: 135 out of 135
（`ZPS7-1 PS7 block required` 只是 WARNING）
```

**不要**把这两条降级成 Warning 去换一个比特流。本设计的 135 个端口是
AXI-Lite 从口 + 视频输入（`din_*`），**真实部署里它们来自 PS7**
（PS 跑 Linux → 读相机 → 走 AXI 把帧送进 PL），**不是外部引脚**。
降级 DRC 等于让 FPGA 去驱动 135 个电平未定义的引脚 —— **可能烧板子**。

### 14.6.2 两条正确出路（都没做）

| 路 | 做法 | 素材 | 障碍 |
|---|---|---|---|
| **A. PS7 块设计**（正路） | PS7 + AXI 互联 + 本模块；135 个端口变内部连接，外部只剩板子自己的引脚 | `D:\FPGAWORKS\board_bits\fpai_demo_fpga`：`ps_ai.bd`、`ps_ai_wrapper.sv`、`ip_user_files/mem_init_files/ps7_init.tcl`、`constrs_1/impl_constraints.xdc`（板级引脚表） | 那套 `.bd` 是 **Vivado 2020.2** 的，与手上的 **2018.3** 不兼容，要在 2018.3 里**重建** |
| **B. PL-only 上板自检顶层** | 内部接固定测试图案源，只用板子已知引脚（`sys_clk_p/n` = C8/C7、`led[0/1]` = J1/M6） | 引脚与 IOSTANDARD 见 `impl_constraints.xdc` | 要新写一个顶层；能验证"综合后的电路真的跑得完一帧"，但验不了完整数据通路 |

**`core/fpga/synth/impl.tcl` 已按这个结论改好**：只要 `<out_dir>/board_pins.xdc`
