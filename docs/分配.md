先说一个重要结论：

> **赛事规则并没有规定“哪些代码必须人工一行一行写，哪些代码禁止 Agent 写”。**
>
> 相反，指南明确写了：比赛全过程可以开放使用各类 Agent 和大模型，用于**选题、方案制定、算法实现以及高效开发**，并要求在成果中说明 AI 工具具体用于哪些环节、占整体工作量多少。
>
> 但是，参赛作品又必须由参赛队**自主完成**，最终还要提交可复现工程、说明文档、测试数据，并能够说明关键设计决策、问题解决过程和团队贡献。

所以真正合理的原则不是：

> “Agent 写代码，队员写代码。”

而应该是：

> **Agent 可以大量承担实现工作，但项目的核心设计、关键技术、硬件实现、实验验证和最终技术判断必须由你们掌握。**

# 一、你们整个项目可以分成四种工作

我建议你把代码和工作划成：

**A 类：可以高度依赖 Agent**

**B 类：可以让 Agent 主写，但必须人工审核**

**C 类：Agent 可以辅助，但必须由队员主导**

**D 类：最好由队员亲自完成并掌握**

这样最符合你们这个比赛。

# 三、B 类：Agent 可以主写，但你们必须审核

这些已经开始接近核心工程。

## 1. CPU ↔ FPGA 通信代码

* buffer

* register access
* driver/user-space interface
* 状态打包/解包

# 2. 你的核心算法

比如你现在的：

$$
\hat S_{t+1:t+H}
$$

未来轨迹预测；

然后：

$$
D(x,y,t)
$$

危险场；

再进一步：

$$
a^*=\arg\max_a U(a)
$$

任务决策。

这一部分最好由你主导。

Agent 可以帮你：

* 找算法
* 写数学代码
* 实现 baseline
* 做实验
* 优化代码

但：

> **“我们到底提出了什么方法？”**

必须是你们自己的。

# 3. 自适应计算预算

这也是很重要的创新部分。

例如：

$$
T_{\text{compute}}\leq T_{\text{deadline}}
$$

然后根据：

* 弹幕数量
* 场景复杂度
* 剩余计算时间

动态决定：

* prediction horizon
* candidate action 数
* 并行度
* precision

这个设计最好由你们自己决定。

Agent 可以帮你写实现。

但不能出现：

> Agent 给我们生成了一套动态预算算法，我们也不知道为什么这样设计。

那答辩时非常危险。

# 五、D 类：我建议你们亲自掌握，尤其是 FPGA 核心

这就是我认为你们**最不能完全外包给 Agent**的部分。

不是说规则禁止 Agent 写，而是因为它决定了你们项目的技术含量和答辩能力。

---

# 1. 核心 FPGA IP

例如：

### Bullet State Update

$$
x_i'=x_i+v_{xi}\Delta t
$$

$$
y_i'=y_i+v_{yi}\Delta t
$$

### Collision Detection

$$
(x_i-x_p)^2+(y_i-y_p)^2
<
(r_i+r_p)^2
$$

### Future Prediction

$$
S_t\rightarrow S_{t+1}\rightarrow...\rightarrow S_{t+H}
$$

这些是你们真正的 FPGA 开发内容。

比赛指南明确要求至少完成一项 FPGA 开发，而且重点考察：

* 功能正确性
* 接口定义
* 资源占用
* 时序性能
* 系统集成
* 加速效果。

所以这些东西不能变成：

> “Agent 给我生成一个 Verilog 文件，我下载到板子上成功了。”

你们至少要亲自理解并掌握：

**数据位宽、定点数、流水线、并行度、BRAM、DSP、FSM、时序、接口。**

---

# 2. FPGA 优化

这一部分尤其应该自己做。

例如：

软件：

$$
T_{\text{CPU}}
$$

FPGA：

$$
T_{\text{FPGA}}
$$

然后研究：

$$
Speedup=
\frac{T_{\text{CPU}}}{T_{\text{FPGA}}}
$$

你们还需要分析：

$$
LUT,\ FF,\ BRAM,\ DSP
$$

和：

$$
Latency,\ Throughput
$$

比赛指南明确鼓励：

* 流水线
* 并行计算
* 片上缓存
* DMA

并要求进行软件和 FPGA 的性能对比。

这个部分非常值得你们亲自迭代。

---

# 3. 最终实验

这个几乎必须是你们自己掌握的。

例如：

> 5000 个弹幕时 FPS 多少？

> CPU 多少 ms？

> FPGA 多少 ms？

> 资源多少？

> prediction horizon 从 100 ms 改成 500 ms 后效果怎样？

> adaptive budget 是否真的提高实时稳定性？

这些数据必须来自你们真实跑出来的实验。

**Agent 可以帮你写 benchmark 程序，但不能替你“生成实验结果”。**

# 十、我给你们一个非常实用的判断标准

以后你不知道一个东西该不该让 Agent 写，就问：

> **“这个东西如果评委突然把代码指着问我，我能不能解释它为什么这么设计？”**

如果答案是：

**能 → 可以大量交给 Agent。**

**不能 → 先自己搞懂，再让 Agent 辅助。**

还有一个更强的标准：

> **这个东西是不是我们项目创新点、核心技术点或者评分依据？**

如果是，就提高人工参与程度。

对你们这个项目，我会特别建议把 **“Simulator、数据工程、训练脚本、普通 CPU 应用、测试、文档”尽可能 Agent 化；把“系统架构、核心预测/决策算法、FPGA 核心 IP、CPU-FPGA 数据通路、性能优化、真实实验”牢牢掌握在三个人手里。**
