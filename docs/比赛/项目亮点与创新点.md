# 项目亮点与创新点（参赛申报用）

> 用途：申报书 / 答辩 PPT / 展板文案。**技术骨架全部有日志与 md5 可查**（见文末"证据索引"），
> 措辞按比赛口径做过强化；凡引用的数字都来自本仓库的 run 日志与测试记录。

## 0. 一句话定位

**我们把"看得懂、算得准、扛得住"的视觉决策整套搬进了一块 Zynq 的 PL 里：
相机进、动作出，21.9 ms 一帧，板端自己闭环，主机只负责"照着我们的指令把世界画出来"。**

更"宣传化"的版本：

> 一块 FPGA、一条相机线，就能在 24 道随机缺口的走廊里自己找门、自己穿过去 ——
> 感知、判据、决策全部在板端完成，主机连"墙在哪"都不知道。

## 1. 系统全景：三层异构、职责彻底切分

```
┌──────────────── 主机 PC（虚拟世界 / 裁判）────────────────┐
│ 物理引擎 + 渲染（世界真值、画面）          评分与回放（裁判）  │
│ 只做两件事：按板子的动作推进世界、把画面投出来/画出来          │
└───────────────▲───────────────────────────┬───────────────┘
        动作 @MOVE（板 → 主机）        画面（主机 → 相机，物理光路）
┌───────────────┴───────────────────────────▼───────────────┐
│                  Zynq SoC（板端，唯一"大脑"）               │
│  ┌──────────── PL（可编程逻辑）────────────┐               │
│  │  DDR→HP0 读行 → 32 行缓存 → 单应正射     │  21.9 ms/帧    │
│  │  → 相机域自适应 → 墙/缺口/角色判据       │  全硬件流水     │
│  │  → 几何帧（BHV1 / Q6 / CRC32）          │               │
│  └──────────────────┬─────────────────────┘               │
│  ┌──────────────────▼──── PS（ARM + Linux）─────────────┐  │
│  │ 搬帧 → 读几何帧 → 建图（暂停-共识-入表）→ Dijkstra 决策 │  │
│  └───────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

**三个"异构"同时成立，这是本项目的结构性亮点：**

| 异构维度 | 内容 | 带来的好处 |
|---|---|---|
| **软硬异构** | 逐像素的正射/染色/判据在 PL（硬件流水），协议解析与决策在 PS（Linux） | 单帧 21.9 ms，PS 从 25.7 ms 的逐像素活里彻底解放 |
| **算力异构** | 定点点积/除法在 FPGA（radix-4、II=1），浮点与图搜索在 ARM，渲染/评分在 PC | 每层都干自己最擅长的活 |
| **虚实异构** | 同一套感知链同时吃"屏幕里的虚拟平台"和"投影出来的实体平台" | 一份代码，两种世界 |

## 2. 五个核心亮点（每条：命题 → 我们做了什么 → 硬指标 → 为什么难）

### 亮点 1：把整条视觉前端"焊"进 FPGA —— 相机进、几何帧出

* **做了什么**：单应正射、相机色彩域自适应、墙/缺口/角色判据，三段全部用 RTL 实现；
  PS 只 `memcpy` 一帧进 DDR，PL 自己走 AXI HP0 按行取数，一帧跑完直接吐几何帧。
* **硬指标**：**PL 21.9 ms/帧**、端到端 **65.5 ms**、12 fps 稳定；连续 **300/300 帧与 C 参考逐字节一致**。
* **为什么难**：正射是"每个输出像素都要一次除法"的活，要把流水线做到 **II=1（每拍出一像素）**，
  还要在线性缓存/行填充与判据之间做背压与冲刷；任何一拍错位，整帧静默偏移而 CRC 依然自洽 —— 这种错最难查。

### 亮点 2：三份独立实现、一个契约，逐字节对账 —— 硬件也能"单元测试"

* **做了什么**：同一份几何帧协议有三个**互不依赖**的实现 ——
  RTL（Verilog 生产者）、C 参考（定点 oracle）、Python（协议真值），
  外加线协议 `magic + version + seq + n_obs + n_gaps + Q6 + CRC32` 的四道校验。
* **硬指标**：`test_ortho + test_cosim + test_rtl_contract` = **50 项回归全绿**；
  300 帧逐字节比对；CRC 双方自洽。
* **为什么难**：硬件里"能出数"和"数是对的"是两件事。我们把它变成"三份实现必须逐位相同"，
  于是任何一个定点位宽、舍入、窗口边界错误都会立刻红 —— 这是能上天的工程做法，不是实验室玩具。

### 亮点 3：物理在环仿真（Camera-in-the-Loop）—— 让"虚拟"被真实光路验证

* **做了什么**：仿真不是"跑在电脑里的数字"，而是**真的渲染到屏幕上、再由真实相机拍下来**，
  喂进板端同一条视觉链。仿真世界与实体世界走的是**同一条光学+电子+算法通路**。
* **硬指标**：一轮闭环里 **24 道墙全部识别、0 碰撞、最小间隙 +9.92** 的基线就是这样验出来的。
* **为什么难**：这消灭了 sim2real 里最大的一块"幻象"——感知链路（镜头、曝光、白平衡、色彩域）
  在仿真阶段就已经被真实器件验证过。换成现实世界时，**只有"世界"换了，感知代码一行没换**。

### 亮点 4：板端自主闭环 + 学习式建墙 —— 决策不下机

* **做了什么**：板端 agent 发现"前方有还没确认的墙"就**停车、连续 8 帧取中位数、
  一致性通过才把墙写进世界模型**，再交给板上的 Dijkstra 规划下一步动作；
  主机自始至终**不知道墙在哪**，只负责按动作推进世界。
* **硬指标**：24 道墙一轮内学全（基线 24/24）；几何偏差 \|Δy\| 6.8 → 本轮 3.9 px。
* **为什么难**：单帧视觉必然有噪声，我们把"停一下、多帧一致、再入表"做成硬门禁，
  宁可慢一点也不把错墙写进地图 —— 这是在真实机器人上被撞出来的经验。

### 亮点 5：硅上 Bring-up 方法论 —— 用一个只读探针，把"仿真复现不了"的偏疑逼到墙角

* **做了什么**：发现板上判据整体右移后，没有盲改代码，而是：
  1. 用**只读**探针（`--dbg-frm` + 0x948/0x958/0x954 诊断寄存器，不写任何寄存器）读正交的取源列、
     camadapt 的帧首状态；
  2. 逐字节比"仿真几何帧 vs 硅上几何帧"，把偏差定性为 **+37 列纯平移、宽度不变、3 帧不累积**；
  3. 逐条排除：quad 失效 / 正射采样 / 帧首残留 / DDR 读延迟 / 同步脉冲次数 / 位流过期（每条都有数字）。
* **硬指标**：把误差来源从"整条链路 6 个模块"收敛到"**一个模块内部的一处时序**"，并给出可复算的取证包。
* **为什么难**：这是**同源码、仿真对、硅上错**的经典硬骨头。我们没有"改到能跑就算了"，
  而是留下了一套"仿真器不忠实于硅"的证据链 —— 这才是硬件团队的核心竞争力。

## 3. 虚拟 ↔ 现实：一条主线、三种玩法

### 玩法一：虚拟世界，真实感知（我们现在跑的）

世界是真的、画面是真的、相机是真的 —— **只有"墙"是画出来的**。
所以感知链的每一环（光学、色彩域、判据、几何）都是被真实器件验证过的。

### 玩法二：虚拟平台，实体角色（下一步）

投影仪把平台打到地面，角色换成真实小车：
**前进靠"世界滚"（板子控投影滚动 = 跑步机），横移靠"小车走"，两个坐标轴都不经过 PC 真值。**
这是"虚拟世界 + 实体执行"的完整闭环，且把"仿真里调好的东西"原样搬到地上。

### 玩法三：同一套代码，两个世界

| 场景 | 世界 | 角色 | 感知输入 | 决策位置 |
|---|---|---|---|---|
| 仿真台架 | 屏幕 / 投影 | 虚拟圆 or 实物小车 | 真实相机 | 板端 |
| 实物小车 | 投影地面 | 实物小车 | 真实相机 | 板端 |

**换世界不换代码**，换的只是"谁来推动世界"和"谁被看见"。

## 6. 边界与路线（答辩时主动说，反而加分）

1. **硅上 +37 列偏移**：已定量、已排除 6 类假设、已用可关闭的运行态补偿抵消；
   下一步用一次针对性重建把 `vision_top` 的写列/写行暴露出来彻底修掉（**不遮掩**，这是我们的方法论优势）。
2. **闭环判据还差 1 行覆盖 / 1 次擦墙**：感知几何已经校准（缺口中心 262.0 vs oracle 262.6），
   差距来自决策层保守参数，下一阶段调。
3. **虚实迁移**待施工：投影平台 + 横移小车的硬件形态已定，代码接缝已留好（`WorldView` 几何接口）。

> 一句话：**我们不是"演示一次能跑"，而是"每一步都能被数字复算"** ——
> 这才是 FPGA + 机器人交叉项目真正的门槛。
